SCOPE

확정된 범위

2

DECISION

D-F3A-1 조합기와 포트의 모양

"F3a가 포트를 정의한다"를 고른 순간 배타적인 선택 하나가 따라온다. 지금 정의할 수 있는 포트는 범용 조합 포트뿐인데, 범용이려면 core가 Reactor를 못 보므로 인자가 블로킹 람다가 된다. 그러면 진짜 병렬 상한이 연산자가 아니라 스레드 풀에서 나온다.

배타 관계"F3a가 포트를 갖는다"와 "조합이 진짜 논블로킹이다"는 지금 동시에 성립하지 않는다. 도메인 포트(searchAll(query, targets))라면 논블로킹이 되지만, 그 반환 타입은 F5 소관이라 지금 정할 수 없다. 아래 세 안은 이 긴장을 각각 다른 쪽으로 푼다.

병렬이 어디서 나오는가 — 같은 요청, 다른 실행

안 A 블로킹 람다 + Reactor

장점. 포트가 완전 범용이라 F3·F5가 무엇을 만들든 안 바뀐다. F3a 혼자서 가짜 태스크로 상한·타임아웃·흡수를 전부 테스트할 수 있다.

단점. 상한이 flatMap(n)과 boundedElastic 크기 두 곳에 생겨, 어느 쪽이 진짜 상한인지 코드만 보고 알 수 없다. WebClient를 논블로킹으로 쓰는 의미도 절반 사라진다.

안 B 도메인 게이트웨이

장점. 세 축이 전부 Reactor 연산자 하나씩으로 드러나고, Spring 공식이 다중 호출에 권하는 "조합 후 1회 대기" 형태와 정확히 같다. Mono가 모듈 경계를 넘지 않는다.

단점. 포트 반환 타입이 F5의 표준 모델이라 지금 정하면 거의 확실히 F4·F5에서 고친다. F3a 단독으로는 공급사가 없어 완료 기준을 실증하기 어렵다.

안 C가상 스레드 조합. 포트는 안 A와 같고 조합 수단만 Semaphore + newVirtualThreadPerTaskExecutor()다.

장점. 상한이 Semaphore(n) 한 곳에만 있어 가장 읽기 쉽다. Java 25 · MVC · 가상 스레드라는 확정 스택과 가장 자연스럽고, JEP 491로 pinning 우려도 사라졌다. 조합기에서 Reactor 의존이 빠진다.

단점. 공급사 클라이언트마다 block()하게 되는데, Spring 공식 「Synchronous Use」는 다중 호출에 개별 block이 아니라 조합 후 1회를 권한다. WEB_CLIENT 프록시가 주는 Mono를 각자 즉시 소비해 버리는 셈이라, 그룹 등록으로 얻은 논블로킹 I/O를 스스로 되돌린다.

FOURTH OPTION

안 D — 포트를 미루고 조합기만 내놓는다

세 안이 각각 무언가를 잃는 이유가 같다. 셋 다 "F3a가 지금 포트를 정의한다"를 전제로 깔고, 그 전제를 지키려다 논블로킹을 버리거나(A·C) 정할 수 없는 타입을 정한다(B). 전제를 하나만 풀면 잃는 것이 없어진다.

푸는 방법F3a는 결과 타입만 core에 두고, 조합기는 supplier-client 안의 평범한 클래스로 둔다. 포트 인터페이스는 도메인 타입이 실제로 생기는 F3·F5가 정의하고, 그 구현이 이 조합기를 쓴다. 고르신 의도(core 의존이 F3a에서 생기고 결과 표현을 F3a가 정한다)는 그대로 지켜지고, 못 정하는 것 하나만 미룬다.

안 D의 단점포트 없이 구현 클래스만 있는 상태가 F3까지 이어진다. 그동안 api-app은 이 조합기를 부를 수 없고(runtimeOnly라 컴파일 참조가 막혀 있다), 조합기는 테스트에서만 호출된다. "쓰는 데가 없는 코드를 먼저 만든다"는 지적이 가능하다 — 다만 이건 F3a를 F3 앞에 따로 둔 순간부터 있던 성질이지 안 D가 만든 것은 아니다.

CONFIRMED

확정 — F3a 는 조합기까지다

이 절은 한 번 뒤집혔다 (기록)처음에는 F3a가 목록 포트와 표준 모델까지 정의하기로 했다. 두 공급사 목록 응답이 구조가 같아 표준 타입을 F2의 검증된 계약에서 그대로 뽑아낼 수 있다는 이유였다. 그런데 F4 절과 대조하니 정면으로 부딪혔다 — 아래 표가 그 충돌이고, 이어지는 4.3이 최종 결론이다. 뒤집힌 과정을 지우지 않는 이유는 같은 실수를 다시 하지 않기 위해서다.
#F4가 이미 자기 것이라고 적어 둔 것내가 F3a에 넣었던 것

2"maxOccupancy는 저장하지 않으므로 목록 모델에서 제외"표준 타입에 넣음 — 명백한 오류

4"포트 반환 형태: 예외 vs 값" — F4의 미결 항목Outcome으로 이미 확정
배운 것2번이 결정적이었다. 표준 모델을 F3a에서 발명하자마자 틀렸다 — 두 공급사가 둘 다 maxOccupancy를 주니 표준에 넣는 게 맞다고 봤는데, F4는 저장하지 않는다는 이유로 빼기로 이미 정해 뒀다. 무엇을 저장하고 무엇을 안 하는지 아는 쪽이 표준 모델을 정해야 한다. 아래 표는 그 판단 없이 만든 것이라 참고로만 남긴다.

4.3 최종 — F3a는 조합기까지, 포트와 표준 모델은 F4

F3a가 내는 것은 타입을 모르는 조합기다. T가 무엇인지는 F4가 호출 지점에서 정한다.

경계 — 누가 무엇을 아는가
// F3a — supplier-client. T 가 무엇인지 모른다.
public record SupplierCall<T>(Supplier supplier, Mono<T> mono) {}

public <T> List<Outcome<T>> runAll(List<SupplierCall<T>> calls)

// F4 — 여기서 비로소 T 가 표준 목록 모델로 정해진다
List<SupplierCall<StandardCatalog>> calls = List.of(
    new SupplierCall<>(A, aClient.hotels()    .map(aTranslator::toStandard)),
    new SupplierCall<>(B, bClient.properties().map(bTranslator::toStandard)));
//                        └ AHotelsResponse          └ BEnvelope<BPropertiesData>
//                          서로 다른 타입이 각자 .map() 에서 표준으로 바뀐다
왜 조합기 안에서 변환하면 안 되나runAll의 T는 한 호출 안에서 하나의 타입이다. Outcome<AHotelsResponse>와 Outcome<BEnvelope<…>>를 한 리스트에 담을 방법은 없다. 그래서 변환은 조합기에 들어오기 전, 각자의 호출 체인 안에서 끝난다. 반대로 조합기가 변환하려면 공급사별 타입을 알아야 하고 if (supplier == A) 같은 분기가 공용 클래스에 생긴다 — OOP-4 위반이자, F4가 적어 둔 "신규 공급사 추가 시 고칠 지점은 어댑터 1개 + Supplier 값 1개" 구조를 깨는 일이다.
무엇하는 일소관
번역 어댑터 (ACL)원본 → 표준. .map(aTranslator::toStandard)가 이걸 부른다F4
포트 어댑터Supplier 키로 Fetcher를 골라 Call을 만들고, 결과를 D12 유형으로 번역해 포트 타입으로 돌려준다F4
조합기병렬 · 타임아웃 · 예산 · 실패 흡수. 타입을 모른다F3a
그래서 Outcome 은 core 가 아니다F4의 포트는 D12 유형을 쓰는 자기 결과 타입을 반환한다. Outcome<T>(Throwable을 든)는 조합기 ↔ F4 어댑터 사이에서만 오가고 둘 다 supplier-client에 있다 — core를 넘지 않으므로 core에 둘 이유가 없다. 결국 F3a가 core에 넣는 것은 없고, core 의존은 SupplierCall이 Supplier 값을 참조해서 생긴다.

클래스 — 무엇이 무엇을 참조하는가

시퀀스 — 호출 1건이 지나는 길과, 한쪽이 실패할 때

F3a 시점의 실제 모습위 흐름에서 F3a가 만드는 것은 가운데 한 칸뿐이고, 공급사 호출은 아직 존재하지 않는다. 그래서 이 시퀀스는 테스트가 심는 가짜 SupplierCall로만 재현된다 — 지연을 흉내 내는 Mono.delay, 절대 안 끝나는 Mono.never, 구독 수를 세는 카운터. 웹 서버가 필요 없다는 뜻이기도 하다. 실제 소켓을 여는 검증은 공급사가 생기는 F3이 정한다.

CHAIN

연산자마다 역할 하나씩

처음 그린 체인은 block(budget) 하나에 예산 관리와 최후 방어를 겸하게 뒀다. 그러면 예산을 넘는 순간 dispose()가 먼저 불려 이미 성공한 공급사의 결과까지 사라진다. 부분 실패를 값으로 흡수하려고 만든 장치가 통째로 무력화되는 자리였다.

FanOutExecutor#runAll — 확정 체인
List<Outcome<T>> arrived = Flux.fromIterable(calls)
    .flatMap(call -> call.mono()
            .timeout(perCall)                            // ① 공급사 1곳의 상한
            .map(v  -> Outcome.success(call.supplier(), v))
            .onErrorResume(e -> Mono.just(                 // ② 실패를 값으로
                    Outcome.failed(call.supplier(), classify(e)))),
        maxConcurrent)                                   // ③ 동시 호출 상한
    .take(budget)                                        // ④ 전체 예산 — 정상 완료
    .collectList()
    .block(hardStop);                                    // ⑤ 방어망 (터지면 버그)

return reconcile(calls, arrived);                        // ⑥ 안 온 곳을 명시적 실패로
#연산자이것만 한다없으면
①.timeout(perCall)공급사 한 곳의 상한느린 한 곳이 전체를 끌고 간다
②.onErrorResume(값)실패를 값으로 바꾼다한 곳의 오류가 나머지를 취소시킨다
③.flatMap(fn, n)동시 구독 상한생략 시 256 — 사실상 무제한
④.take(budget)전체 예산. 오류가 아니라 정상 완료예산 방어를 ⑤에 겸하게 되어 도착분이 날아간다
⑤.block(hardStop)값을 꺼낸다 + 체인 고장 시 방어인자 없는 block()이면 영원히 안 끝난다
⑥reconcile④가 자른 공급사를 Failed(BudgetExceeded)로 채운다그 공급사가 조용히 사라진다
④가 핵심Flux.take(Duration)은 시간이 지나면 오류가 아니라 정상 완료하고, 그때까지 도착한 원소를 그대로 지킨다(reactor-core 3.8.7에 take(java.time.Duration) 존재 확인). 예산을 block이 아니라 여기서 표현하는 것이 이 설계의 유일한 비자명한 선택이다.
⑥이 없으면 생기는 사고④가 자르면 아직 안 끝난 공급사는 리스트에서 그냥 빠진다. 호출자는 2건을 요청했는데 1건만 받고, B가 왜 없는지 알 방법이 없다 — 조사 문서가 Mono.empty()에 대해 경고한 것과 같은 종류의 사고다. 그래서 요청 목록과 대조해 빠진 곳을 채운다. 돌려주는 리스트의 크기는 언제나 요청한 호출 수와 같다는 것이 이 포트의 계약이다.

예산 부등식 — 기동 시 검증

perCall과 budget은 성격이 다르다. 전자를 넘기면 그 공급사만 실패 값이 되고, 후자를 넘기면 남은 전부가 잘린다. 그리고 ③의 상한이 걸리면 호출이 배치로 나뉘므로 조건이 한 겹 더 붙는다.

budget  >  ⌈ 공급사 수 ÷ maxConcurrent ⌉ × perCall

— 공급사 2곳에 maxConcurrent=1 이면 perCall이 두 번 직렬로 흐른다

기동 시점에는 공급사 수를 모르므로(F3a에서는 Fetcher가 0개다) 최소 조건 budget > perCall 만 바인딩 시점에 강제하고, 위 부등식 전체는 프로퍼티 문서로 남겨 F3이 공급사를 붙일 때 지키게 한다. 지금 없는 공급사 수를 미리 계산하는 코드는 넣지 않는다.

F3a 는 실패를 분류하지 않는다실패 종류를 이름 붙이는 일은 F4의 D12가 하고, 그 유형이 F8의 reason 체계가 된다. F3a가 분류 enum을 따로 만들면 체계가 둘이 되어 F8이 어느 쪽을 쓸지 애매해진다. 그래서 Outcome.Failed는 Throwable cause와 Duration elapsed만 들고 넘긴다.

다만 F4가 구분할 수 있도록 원인이 타입으로 갈리게 한다 — perCall 초과는 Reactor가 던지는 TimeoutException 그대로, 예산에 잘린 경우는 F3a가 만드는 BudgetExceededException. 둘 다 "시간 초과"지만 호출이 나갔다 늦은 것과 아예 기다려 주지 못한 것이라 의미가 다르다.

CONTRACT

포트 계약 — 한쪽이 죽어도 나머지는 내려간다

이 feature가 존재하는 이유를 세 줄로 줄이면 이것이다. 구현도 리뷰도 이 세 줄을 기준으로 본다.

  • 돌려주는 리스트 크기는 언제나 요청한 호출 수와 같다. 잘려서 안 온 공급사도 Failed(BudgetExceededException)으로 채워 넣는다 — 조용히 빠지는 항목이 없다.
  • 공급사 쪽 실패는 예외가 아니라 Failed 값이다. 타임아웃·연결 실패·예산 초과 전부 값으로 내려온다.
  • 한 곳이 실패해도 나머지 결과는 그대로 돌아온다. 실패 하나가 성공한 호출을 취소시키지 않는다.

예외가 나가는 자리는 한 군데뿐이고, 그것은 의도다

block(hardStop)이 터지면 예외가 나가고 도착분도 잃는다. 이 자리는 그대로 둔다. take(budget)이 있는 한 도달하지 않으며, 도달했다면 그것은 공급사 장애가 아니라 우리 코드나 설정이 고장 난 것이기 때문이다.

무엇이 잘못됐나어떻게 나가나왜 그렇게
공급사가 느리다 · 죽었다Failed 값 → 부분 응답이 feature가 만들어진 이유 그 자체
예산 안에 못 들어왔다Failed(BudgetExceededException) 값도착분은 지키고 못 온 곳만 표시
우리 체인·설정이 고장 났다예외 → 5xx (형태는 F8)"공급사 전부 장애"로 포장하면 거짓말이 된다
여기서 catch-all 을 쓰면 안 되는 이유세 번째 행을 catch (Exception e)로 삼켜 "전 공급사 실패"로 바꾸면 응답은 200이 되고 운영자는 공급사를 들여다보는데 진짜 원인은 우리 쪽에 있게 된다. 버그를 장애로 위장하는 것이라 CLN-6에 정면으로 걸린다.

F3에 넘기는 계약 — SPI 에 문서로 못 박는다

fetch() 는 즉시 Mono 를 돌려줘야 한다공급사별 Fetcher의 fetch()가 본문에서 먼저 블로킹하면 Mono가 만들어지기 전이라 .timeout(perCall)이 붙을 자리가 없다. 그러면 어떤 장치도 그 호출을 자르지 못하고 위 세 줄이 통째로 무너진다. 컴파일로는 잡히지 않는 종류라 SPI 인터페이스 자바독에 계약으로 적고, F3 리뷰의 확인 항목으로 넘긴다.
