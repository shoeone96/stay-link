1

SCOPE

범위와 경계

이 어댑터는 공급사 코드까지만 안다. 내부 식별자도, 자사 API 응답 모양도 모른다.

포함F5가 만드는 것

재고·요금 포트와 표준 모델(AvailabilityOffer·Money) · A·B HTTP 메서드와 DTO · 번역기 2개(총액 합산·최솟값·날짜 검증) · 공급사별 묶음 분할 · 포트 어댑터 · 부분 실패 결과 타입 · 공급사별 한도 yaml

제외다른 곳이 하는 것

코드↔내부 id 역매핑과 미매핑 처리(F7) · 자사 API 응답 조립·정렬(F7) · soldOut 파생(F7) · 재시도·서킷(F9) · 캐시(F10) · fan-out 값 재산정(F9) · 부분 기간 제안

DDD 전술 패턴 — 적용하지 않는다이 범위에는 불변식을 지키는 Aggregate가 없다. 외부 API를 내부 모델로 정규화하는 Adapter/ACL이 전부이며, core에 생기는 값들은 LAY-7의 Result 타입과 자기 검증하는 VO(DDD-4)다. F3와 같은 판단이다.
부분 기간을 제안하지 않는 진짜 이유연박 중 일부 날짜만 재고가 있어도 "2박은 됩니다"를 만들지 않는다. 막는 것은 재고가 아니라 요금이다 — 재고는 날짜별로 보존되지만, B가 기간 총액만 주므로 부분 기간 요금을 만들 수 없다.

TRANSLATOR

번역기 내부 — 새로 생기는 로직 전부

F5에서 실제로 새로 짜는 판단은 전부 이 안에 있다. 나머지는 배선이다.

이 검증이 A에서만 의미가 다른 이유3박 요청에 2줄만 오면 A는 총액이 278,300으로 조용히 틀리고, B는 totalPrice가 공급사 계산값이라 안 틀린다. 그런데 A의 278,300은 예외를 던지지 않는다 — 그냥 작은 숫자이고, 가격 오름차순 정렬이면 제일 위에 뜬다.

탈락한 안 — 사유를 남긴다

  • BigDecimal D-F5-1 이 범위에 나눗셈이 없어 scale·RoundingMode 가 아무 일도 하지 않고, JSON 에 453600.00 처럼 없던 소수 자릿수가 새어 나간다.
  • javax.money / Joda-Money D-F5-1 Boot 4.1.1 BOM 이 moneta·joda-money 본체를 관리하지 않아 비관리 의존성이 core 시그니처에 박힌다.
  • sealed 세 번째 변형 PARTIAL D-F5-7 소비자 F7 은 "받은 offer 는 쓰고 실패는 사유로 싣는다"만 하므로 분기 본문이 같아진다 — 타입만 늘고 분기는 안 갈린다.
  • 묶음 단위 결과를 그대로 올리기 D-F5-7 "A의 3묶음 중 1묶음 실패 = A는 부분 실패"를 소비자가 매번 계산해야 한다.
  • Flux.buffer / window / parallel().runOn() D-F5-9 리액티브 소스용 연산자인데 우리 소스는 메모리 List 다. 동시 상한이 두 겹이 된다.
  • 날짜 개수만 비교 D-F5-8 "3개인데 하나가 범위 밖"을 통과시킨다.
  • DUPLICATED 판정 신설 D-F5-8 실재 근거가 확인 안 된 사유(레이스) 하나뿐이었다. D 순회로 바꾸니 판정 자체가 불필요해졌다.

마지막으로 닫은 세 개

전부 확정 ① 포트는 searchAll(query) 하나 — 조합기의 budget은 "검색 1건 전체"에 걸려야 한다. F7이 공급사별로 따로 부르면 예산이 호출마다 따로 걸려 검색 하나가 최악 2배가 된다.
② AvailabilityQuery가 Map<Supplier, List<String>>를 든다 — F7이 미리 갈라서 넘긴다. 어댑터가 코드로 공급사를 알아내려면 DB를 봐야 하므로 애초에 선택지가 아니었다.
③ 묶음 분할은 어댑터 — Fetcher가 안에서 자르면 스톱워치(per-call) 하나를 여러 호출이 나눠 쓰게 되어, 앞 호출이 느리면 뒤 호출이 시간을 뺏긴다. 실패해도 어느 묶음인지 몰라 FailedChunk가 담을 내용을 잃는다.
