# supplier-resilience 기동 검증 (F9)

status: 완료
date: 2026-09-07 (KST)
대상: `feature/f9-supplier-resilience` @ `408e397`

단위 테스트(267건)가 덮지 못하는 것을 확인하기 위해 **실제로 띄우고 공급사를 죽였다 살렸다** 하며
관측한 기록이다. 프록시가 만드는 URL·직렬화·설정 바인딩·풀 획득처럼 목으로 대체하면 실행되지 않는
경로가 여기서만 실행된다.

## 구성

| | |
|---|---|
| 모의 공급사 A | `localhost:9091` — 숙소 2곳 (`A-3201`·`A-3305`) |
| 모의 공급사 B | `localhost:9092` — 숙소 1곳 (`P-88410`) |
| 자사 API | `localhost:8080` — `api-app` |
| DB | MySQL (compose 자동 기동), 목록 동기화 배치 1회 선행 |

**관측용 오버라이드 하나** — `--supplier.resilience.wait-duration-in-open-state=10s`.
설정값(60s)은 그대로 두고 실행 인자로만 낮췄다. 회복 확인에 매번 1분을 기다리지 않기 위함이며,
이 값은 어느 전이의 **판정식에도 들어가지 않는다**(§3.7 전이 표의 ②만 지배).

검색 조건은 `checkIn=2026-10-07 · checkOut=2026-10-08 · adults=2 · children=0` 로 고정했다.

## 결과 요약

| # | 조작 | 기대 | 결과 |
|---|---|---|---|
| 1 | 정상 | 200, 둘 다 `OK` | **통과** — `results=5`, `supplierA=OK(3) supplierB=OK(2)`, 243ms |
| 2 | A 프로세스 종료 | 첫 실패는 아직 `UNAVAILABLE` | **통과** — 최소 호출 수를 채우기 전에는 열리지 않았다 |
| 3 | 계속 호출 | 표본이 차면 `CIRCUIT_OPEN` | **통과** — 사유가 갈렸다 |
| 4 | A 재기동 | 다음 호출이 전이를 일으키고 그 호출이 탐침 1번 | **통과** — 첫 호출이 곧바로 `OK(3) results=5` |
| 5 | A 를 5초 지연으로 | 시도별 상한에 걸려 `TIMEOUT`, 그 뒤 차단 | **통과** — 아래 「관측 3」 |
| 6 | B 까지 실패 | 502 `ALL_SUPPLIERS_FAILED`, 서킷은 각자 | **통과** — A·B 가 독립적으로 열렸다 |
| 7 | VU 40 × 40초 부하 (A 지연 유지) | 예산 준수, 탐침 초과 즉시 거부 | **통과** — 31,539건 중 **3건만** 타임아웃 비용을 냈다. 아래 「관측 5」 |

## 관측 1 — 사유가 갈린다 (D-F9-8)

```
supplierA=OK(3)                    supplierB=OK(2)  results=5
supplierA=FAILED(0)[UNAVAILABLE]   supplierB=OK(2)  results=2   ← A 죽음, 아직 CLOSED
supplierA=FAILED(0)[CIRCUIT_OPEN]  supplierB=OK(2)  results=2   ← 열렸다
supplierA=FAILED(0)[CIRCUIT_OPEN]  supplierB=OK(2)  results=2
```

**이 두 줄이 갈리는 것이 D-F9-8을 뒤집은 이유다.** 기존 값(`UNAVAILABLE`)으로 접었다면 두 줄이 글자까지
같아져, 「공급사별 성공률」의 재료인 이 줄만 보고는 **공급사 장애인지 자사 차단인지 구분할 수 없다.**
지금은 첫 줄이 "A가 응답하지 못했다", 다음 줄부터가 "우리가 부르지 않았다"다.

같은 로그가 두 가지를 더 보여 준다.

- **최소 호출 수가 임계보다 먼저 걸린다** — 실패율이 100%인데도 첫 실패는 열지 않았다 (§3.7 전이 ①)
- **B는 그대로 `OK(2)`, 결과 2건이 나간다** — 502가 아니라 200 + 부분 결과 (공급사별 격리)

## 관측 2 — 회복은 호출이 깨운다 (§3.7)

```
22:33:55  supplierA=FAILED(0)[CIRCUIT_OPEN]  results=2   ← 차단 중
   (A 재기동)
22:35:55  supplierA=OK(3) supplierB=OK(2)    results=5   ← 첫 호출이 전이 + 탐침 성공
22:36:21  supplierA=OK(3) supplierB=OK(2)    results=5
```

**타이머가 상태를 바꾼 것이 아니다.** A가 살아난 뒤 도착한 **첫 검색이** `OPEN`→`HALF_OPEN` 전이를
일으키고, 그 호출 자신이 탐침 1번이 되어 성공했다. 그리고 **그 탐침의 결과가 버려지지 않고 그대로
응답에 실렸다**(`results=5`) — 설계에 적은 "탐침은 합성 호출이 아니라 진짜 검색이다"가 그대로다.

## 관측 3 — 차단의 진짜 이득 (D-F9-5·6, §4.1)

연결 거부(프로세스 종료)로는 이것이 보이지 않는다. localhost 연결 거부는 원래 즉시라서
**차단과 미차단의 소요가 같기 때문**이다. A를 **5초 지연**으로 두면 갈린다.

```
3.967s  supplierA=FAILED(0)[TIMEOUT]        elapsedMs=3944
3.977s  supplierA=FAILED(0)[TIMEOUT]        elapsedMs=3965
2.130s  supplierA=FAILED(0)[CIRCUIT_OPEN]   elapsedMs=2126   ← 1시도 하다 열림
0.018s  supplierA=FAILED(0)[CIRCUIT_OPEN]   elapsedMs=14
0.020s  supplierA=FAILED(0)[CIRCUIT_OPEN]
0.019s  supplierA=FAILED(0)[CIRCUIT_OPEN]
```

네 가지가 한 번에 확인된다.

| 확인된 것 | 근거 |
|---|---|
| **시도별 상한 유도값이 실측과 맞다** | `(4s − 0.3s) ÷ 2 = 1.85s`, 2시도 + 백오프 ≈ 3.94s. 로그가 `elapsedMs=3944`다. 종이 위 계산이 그대로 나왔다 |
| **2단 상한이 맞물린다** | 3.97s < `per-call` 4s. 재시도를 포함한 총 소요가 전체 상한을 넘지 않는다 |
| **차단이 4초를 18ms로 만든다** | 220배. 그만큼 검색이 죽은 공급사를 기다리지 않는다 |
| **`TIMEOUT`이 서킷 표본이 된다** | **시도별 상한을 서킷 안쪽에 둔 D-F9-4의 필수 짝이 작동했다.** 바깥에 뒀다면 느린 공급사는 서킷을 영영 열지 못한다 |

## 관측 4 — 전원 실패와 서킷의 독립성 (D-F7-3)

B까지 503을 내게 하면:

```
supplierA=FAILED(0)[TIMEOUT]       supplierB=FAILED(0)[UNAVAILABLE]   results=0  elapsedMs=3953
supplierA=FAILED(0)[CIRCUIT_OPEN]  supplierB=FAILED(0)[UNAVAILABLE]   results=0  elapsedMs=113
supplierA=FAILED(0)[CIRCUIT_OPEN]  supplierB=FAILED(0)[CIRCUIT_OPEN]  results=0  elapsedMs=200
```

```json
HTTP 502
{"code":"ALL_SUPPLIERS_FAILED","message":"All suppliers failed to respond","data":null}
```

**두 서킷이 각자의 속도로 열린다.** A가 먼저 열리고 B는 아직 `UNAVAILABLE`이며, 그다음 줄에서 B도
열린다. 상태가 공급사별로 분리돼 있다는 것이 한 줄 안에서 보인다. 소요는 3.97s → 6ms로 떨어진다.

## 관측 5 — 부하 상태 (VU 40 × 40초, A는 5초 지연 유지)

`k6/app-search.js`로 동시 부하를 걸었다. 순차 호출에서는 슬롯이 남아돌아 보이지 않던 것들이 여기서 보인다.

```
요청 31,539 · 788 rps · 40초
p(50) 43ms · p(90) 81ms · p(95) 101ms · max 2.16s
budget 안에 응답 ..... 100% 통과 (임계: p(95) < 5s)
```

**사유별 건수가 이 설계의 값을 그대로 말한다.**

| 사유 | 건수 | 뜻 |
|---|---|---|
| `supplierA=FAILED(0)[CIRCUIT_OPEN]` | **31,553** | 차단이 막아 준 호출 |
| `supplierA=FAILED(0)[TIMEOUT]` | **3** | 실제로 3.9초를 지불한 호출 |
| `supplierA=FAILED(0)[UNAVAILABLE]` | 1 | 서킷이 열리기 전 첫 실패 |

**31,539건 중 3건만 타임아웃 비용을 냈다.** 서킷이 없었다면 전부 호출당 약 3.9초를 기다렸을 것이고,
p(95)는 100ms가 아니라 초 단위가 됐을 것이다. §4.1이 "죽은 공급사가 무는 비용은 재시도가 아니라
**첫 호출이 검색을 붙드는 것**"이라고 한 것을 부하 상태에서 직접 잰 수치다.

> **§4.1의 근거가 이 실측으로 교체됐다** (리뷰 round-1 #2). 원래 그 절은 "죽은 공급사가 붙든 커넥션 풀
> 슬롯은 살아 있는 공급사가 써야 할 것"이라고 적었는데, reactor-netty의 풀은 **원격 호스트별로 갈려**
> 그 문장이 성립하지 않는다. 결론은 유지되고 근거가 **공급사 간 자원 경쟁 → 검색의 대기 시간**으로
> 바뀌었으며, 위 수치가 그 대기 시간을 직접 잰 것이다.

### 부하에서만 보인 것 셋

```
22:41:47.630  circuit=A:availability OPEN -> HALF_OPEN
22:41:47.630  circuit=B:availability OPEN -> HALF_OPEN
22:41:47.630  cause=CallNotPermittedException elapsedMs=1
22:41:47.630  cause=CallNotPermittedException elapsedMs=0
22:41:47.630  cause=CallNotPermittedException elapsedMs=0     (동일 밀리초에 다수)
```

1. **레지스트리 키가 `<공급사>:<용도>`로 실제 동작한다** — 로그에 `A:availability`·`B:availability`로
   찍힌다. D-F9-7은 단위 테스트의 변이 검사로만 고정돼 있었는데, 여기서 실물로 확인됐다.
2. **half-open 탐침 초과 거부가 대기 없이 즉시 일어난다** — 전이 직후 40 VU가 동시에 몰리는데 탐침
   2자리만 통과하고 나머지는 `elapsedMs=0~1`로 거부된다. "줄을 서지 않는다"가 실측으로 확인됐다.
3. **상태 전이가 로그로 남는다** — §4.1에서 AWS의 유보론("modal behavior는 테스트하기 어렵다")에 대한
   대응 ①로 약속한 것이다. 부하 중 전이 시점이 밀리초 단위로 남는다.

### 커넥션 풀 획득 대기는 관측되지 않았다 — 그리고 그것이 결과다

> **fix-1 로 두 군데가 바뀌었다** (리뷰 round-1 #1). ① 획득 대기가 `per-call ÷ 2`(2s)가 아니라
> **`min(용도별 attemptTimeout) ÷ 2`** 다 — 검색 경로에서 **925ms**. 값이 아니라 **유도 기준**이 바뀐
> 것이라 `per-call` 을 조정해도 부등식이 따라 움직인다. ② **관측 방법이 생겼다** — 전에는 풀 대기가
> 걸려도 `TIMEOUT` 으로 기록돼 공급사 지연과 구분되지 않았는데, 이제 요약 로그의 `reason` 이
> **`POOL_EXHAUSTED`** 로 갈린다.

풀 관련 경고가 **0건**이다. 하지만 이것을 "풀이 충분하다"로 읽으면 안 된다.
**서킷이 포화 조건 자체를 만들지 않았다.** A로 나가는 호출이 31,553건 차단됐으므로 그 슬롯을 애초에
쓰지 않았다. 풀 대기를 실제로 보려면 서킷을 끄고 같은 부하를 걸어야 하며, 이번 검증 범위 밖이다.

D-F9-6이 "실제 상한은 커넥션 풀 하나"라고 한 것과 모순되지 않는다 — 풀이 유일한 상한인 것은 맞고,
**서킷은 그 상한에 도달하지 않게 하는 장치**다. 두 결정이 이 수치에서 맞물린다.

### 502가 나온 79건

k6가 79건의 비-200을 기록했다(0.25%). 직전 시나리오에서 **B의 서킷도 열려 있었고**, 부하 시작 시점에
두 서킷이 모두 열린 상태여서 그 짧은 구간이 전원 실패로 판정된 것이다(D-F7-3). B의 탐침이 성공하며
곧 닫혔고 이후 200으로 돌아왔다. 서킷 상태가 요청 사이에 **살아 있다**는 방증이기도 하다.

## 단위 테스트가 덮지 못해 여기서만 잡히는 것

- **설정 바인딩** — `supplier.resilience.*` 아홉 값이 실제로 읽히고 실행 인자 오버라이드가 먹는다
- **프록시가 만드는 요청** — 날짜 직렬화·쿼리 파라미터가 계약대로 나간다 (`results=5`가 그 증거)
- **요약 로그의 최종 모양** — `SupplierErrorCode`가 그 줄에 어떤 글자로 찍히는지
- **실제 소요** — 유도값 1.85s가 계산이 아니라 **관측**으로 확인된다

## 남은 것

- **커넥션 풀 획득 대기는 여전히 미관측이다.** 서킷이 포화 조건을 만들지 않기 때문이다(관측 5).
  다만 fix-1 이후 **재는 방법이 분명해졌다** — 서킷을 끄고(그래야 포화가 만들어진다) 동시 호출을
  호스트당 50 이상으로 올린 뒤 두 가지를 본다: ① 요약 로그에 `reason=POOL_EXHAUSTED` 가 나오는가
  ② **그때 그 공급사의 서킷이 열리지 않는가.** 두 번째가 이 수정의 요점이다 — 자사 병목이 서킷 표본이
  되지 않아야 한다. 풀 크기 50 의 타당성은 여전히 실측 근거가 없고 §6.1 이연 항목의 입력이다.
- **수집(catalog) 경로의 서킷은 정상 경로만 봤다.** 배치를 1회 돌렸을 뿐 목록 공급사를 죽여 보지 않았다.
  레지스트리 키가 용도까지 나뉘는 것 자체는 관측 5에서 `A:availability` 형태로 확인됐지만,
  **`A:catalog` 가 `A:availability` 와 독립적으로 열리는지**는 아직 단위 테스트로만 고정돼 있다.
