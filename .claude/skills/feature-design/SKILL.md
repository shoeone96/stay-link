# feature-design: 기능 설계 (메인 세션 대화형)

메인 세션이 **설계 리뷰 파트너**로서 사용자와 설계를 마무리하고 산출물을 저장한다. 구현 단계(`dev-cycle`)는 이 산출물만 읽으므로, 여기서 결정되지 않은 것은 구현에서 결정되지 않는다.

## 절대 원칙

1. **시작 시 Skill 도구로 `coding-standard`와 `test-standard`를 명시적으로 로드한다.** description 매칭에 맡기지 않는다.
2. **코드를 쓰지 않는다.** 설계 문서만 만든다. 테스트 코드도 쓰지 않는다 (TDD-1).
3. **정답 단정 금지 — 구현을 막는 결정은 안 3개를 그려서 고르게 한다.** 텍스트 나열이 아니라 **클래스 다이어그램과 호출 시퀀스**로 보이고, 안마다 장점·단점을 함께 제시한 뒤 추천 + 근거를 말하고 사용자가 고른다. 사용자 안에 결함이 보이면 대안보다 **결함을 먼저** 말한다. 세 안이 다 마땅치 않다고 하면 네 번째 안을 만든다.
4. **그림이 결정보다 먼저 나온다.** `design.html`은 md 저장 뒤의 보고서가 아니라 **고르기 위한 도구**다. 스케치를 먼저 보이고, 선택이 끝난 뒤 md를 쓴다.
5. **테스트 리스트는 사용자 confirm 필수.** confirm 전에는 저장하지 않는다.
6. **산출물은 두 개다** — 개발용 `01-design.md`(마크다운, **SSOT**)와 검토용 `design.html`(시각화). `01-design.md`에는 **구현에 필요한 모든 내용**이 들어가야 한다(이걸 읽고 구현이 가능해야 하며 에이전트는 이 파일만 읽는다). `design.html`은 사용자가 눈으로 보는 용도이며 **결정의 원본이 아니다** — 결정이 바뀌면 md를 먼저 고치고 html을 다시 만든다.
7. **탈락한 안의 사유를 버리지 않는다.** 결정 카드에 고른 안의 근거만 남기면 나중에 "왜 그걸 뺐지"를 재구성할 수 없다. 안마다 한 줄씩 남긴다.
8. **파일 저장 전 전문 미리보기 → 승인.** `01-design.md`는 이 스킬만 쓴다. 구현 중 설계 변경 요청은 `02-implementation.md`의 "설계 이탈 요청"으로 올라오며, 사용자 판단 후 이 스킬이 결정 카드로 반영한다.
9. **저장소 산출물 금지어 규칙 준수.** 프로젝트 `CLAUDE.md`와 `.claude/publish-checks.md`의 금지어 규칙을 문서에 적용한다.
10. **프로젝트 CLAUDE.md의 기록 규칙**(예: ai-history 자동 기록)을 종료 시 수행한다.
11. **설계는 feature 브랜치 위에서 한다.** 기능 폴더명이 확정되면 곧바로 `main`에서 `feature/f<N>-<feature>` 브랜치를 만들고(규칙 원본: 프로젝트 CLAUDE.md 「브랜치·PR」), `01-design.md`는 그 브랜치에서 저장한다. `main` 위에서 설계 문서를 쓰지 않는다. 이미 워크트리가 그 브랜치를 들고 있으면 checkout만 확인하고 넘어간다.

## 워크플로우

1. ① **요구사항 접수** — `$ARGUMENTS` 또는 대화에서 기능명·수용 기준·관련 설계 문서(`docs/*.html` 등)·프로젝트 CLAUDE.md 제약을 확인한다. 기능 폴더명을 kebab-case로 사용자와 확정한다(예: `property-mapping`). 폴더명이 확정되면 `docs/features/README.md` 상태표에서 번호 `N`을 찾아 브랜치를 만든다: `git checkout main && git pull` → `git checkout -b feature/f<N>-<feature>` → `git push -u origin feature/f<N>-<feature>`. 브랜치가 이미 있으면 checkout 만 한다. 브랜치를 만든 직후 상태표에서 상태가 `PR`인 직전 feature가 `main`에 병합되어 있으면 그 행을 `완료(병합)`(구현 열에 병합일)으로 갱신해 두고, 이 브랜치의 첫 커밋에 포함한다(병합 후 `main` 직접 커밋 금지). `docs/features/<feature>/01-design.md`가 이미 있으면 Read 하고 이어서 수정한다. 모호한 점은 AskUserQuestion 1회로 묶어 묻는다.
2. ② **범위 확정** — 포함/제외 목록. DDD 전술 패턴 적용 여부를 `coding-standard` 「적용하지 않을 때」로 판단해 명시한다 (Transaction Script면 그렇게 쓴다).
3. ③ **도메인 모델** — Aggregate/Entity/VO와 불변식을 DDD-n 근거와 함께 제안하고 합의한다. 도메인 관행 질문이 나오면 `domain-analysis`로 안내한다.
4. ④ **레이어 배치 초안** — 패키지·클래스 목록과 의존 방향 (LAY-n). 포트 인터페이스의 소유 레이어를 명시한다. 여기까지는 초안이며, 갈리는 지점은 ⑤로 넘긴다.
5. ⑤ **설계 스케치 → 선택** ← **이 스킬의 중심 단계.** 아래 「설계 스케치」 규약대로 `design.html`을 만들어 사용자에게 보이고, 구현을 막는 결정을 하나씩 닫는다. 선택이 끝나기 전에는 md를 쓰지 않는다.
6. ⑥ **적용 패턴** — 패턴 / 격리하는 변화 / 검토한 대안 (PAT-6). 없으면 "없음"과 이유.
7. ⑦ **MECE 테스트 리스트** — `test-standard` 「테스트 리스트 형식」대로 `T-NN` ID, 레이어별·Normal/Boundary/Invalid/Interaction·기법 태그. 케이스 수는 최소로, 값 변형은 한 행에 묶어 Parameterized 표시 (TST-1·2). 사용자 confirm.
8. ⑧ **결정 카드 정리** — ⑤에서 닫은 것과 남은 미결을 `D-?N` 형식으로 목록화한다. **고른 안의 근거뿐 아니라 탈락한 안의 사유도 한 줄씩 적는다**(원칙 7).
9. ⑨ **저장 (md)** — 아래 템플릿으로 전문 미리보기 → 승인 → `docs/features/<feature>/01-design.md` Write.
10. ⑩ **HTML 확정본** — ⑤의 스케치를 **확정된 설계**로 갱신한다(3안 비교 그림 → 고른 안의 그림). 아래 「저장 전 자가 검사」를 통과해야 한다. 커밋은 사용자 지시 시 이 feature 브랜치에 한다.
11. ⑪ **종료 안내** — "구현은 `/clear` 또는 새 세션에서 `/dev-cycle <feature>`, 구현·커밋이 끝나면 `/feature-pr <feature>`로 `main` PR"을 안내하고 프로젝트 기록 규칙을 수행한다.

## 설계 스케치 (⑤)

### 대상 — 구현을 막는 결정만

결정 카드 전부에 3안을 그리면 그림이 수십 장이 되어 설계가 아니라 그림 그리기가 된다.
**「구현 차단 = 예」인 결정만** 스케치한다. 나머지는 표로 고른다.

목표 개수는 **카드 5~8개, 그림 6~12장**이다. 넘으면 기능을 쪼개는 게 맞는지 먼저 의심한다.

### 안 하나에 들어가는 것

| 요소 | 내용 |
|---|---|
| 클래스 다이어그램 | 클래스 이름 · **주요 필드** · **주요 메서드 시그니처** · 관계(의존·구성·상속). 이 안에서만 생기는 클래스를 강조색으로 |
| 호출 시퀀스 | 요청 1건이 그 클래스들을 **어떤 순서로** 지나는가. 실패 경로가 갈리면 그것도 |
| 장점 | 이 안이 무엇을 쉽게 만드는가. 2줄 이상, 구체적으로 |
| 단점 | 이 안이 무엇을 어렵게 만드는가. **"단점 없음"은 쓰지 않는다** — 못 찾았으면 더 본다 |

### 그림 한 장에 안 3개를 나란히

**안마다 별도 figure를 만들지 않는다.** 클래스 다이어그램 3개를 한 SVG에 3열로 그려
같은 자리의 박스가 어떻게 다른지 눈으로 비교되게 한다 (`figure.fig-wide`, viewBox 1120).
시퀀스도 안마다 다를 때만 한 장에 나란히 그린다 — 안 사이에 차이가 없으면 그리지 않는다.

카드 하나당 그림은 **1~2장**이다.

### 진행 방식

1. 카드 하나의 3안을 `design.html`에 섹션으로 추가하고 `open`으로 띄운다.
2. **AskUserQuestion**으로 고르게 한다. `preview`에 각 안의 클래스 스케치를 텍스트로 넣어 터미널에서도 비교되게 한다.
3. 고른 뒤 그 섹션을 **확정 표시**로 바꾸고(탈락 안은 접어 두되 사유는 남긴다) 다음 카드로 간다.
4. 사용자가 세 안 모두 마땅치 않다고 하면 **네 번째 안**을 만든다. 억지로 셋 중 하나를 고르게 하지 않는다.
5. 앞 카드의 선택이 뒤 카드의 선택지를 바꾸면 그 자리에서 말하고 다시 그린다.

## 설계 문서 템플릿 (`01-design.md`, 섹션 고정)

```markdown
# <기능명> 설계

status: 확정 | 수정중
updated: YYYY-MM-DD

## 1. 요구사항 재해석·범위
- 해결하려는 문제 / 수용 기준 / 포함 / 제외 / DDD 적용 여부와 이유

## 2. 도메인 모델
- Aggregate / Entity / VO 목록, 불변식, 근거 규칙 ID

## 3. 레이어 배치
- 패키지·클래스 목록, 의존 방향
- **클래스 관계와 주요 시그니처** — 에이전트는 이 파일만 읽으므로 html의 그림에 기대지 않는다.
  텍스트 트리 + 필요하면 mermaid `classDiagram`·`sequenceDiagram` (md에서는 mermaid 허용)
- 포트 소유 레이어

## 4. 적용 패턴
- 패턴 / 격리하는 변화 / 검토한 대안

## 5. 테스트 리스트
| ID | 레이어 | 분류 | 케이스 | 기법 | 기대 결과 |

## 6. 결정 카드
| ID | 질문 | 검토한 안 | 결정 | 탈락 사유 | 구현 차단 |
- 「검토한 안」은 이름 나열, 「탈락 사유」는 고르지 않은 안마다 한 줄

## 7. 참고 문서
- 관련 설계 문서·프로젝트 규칙 경로
```

## 검토용 HTML (`design.html`)

**`toss-design` 스킬로 만든다** (전역 CLAUDE.md 절대 규칙). 목적은 "읽는 문서"가 아니라 **"보는 문서"** 다 —
표와 문장은 md에 있으므로, HTML은 **md만으로 안 보이는 것을 그림으로 드러내는 데만** 쓴다.

**반드시 넣는 그림** (전부 직접 작성한 inline SVG. mermaid 금지):

| 그림 | 무엇을 보여주나 |
|---|---|
| **클래스 다이어그램** | 클래스 이름·주요 필드·주요 메서드와 관계. **기능마다 최소 1장.** ⑤의 3안 비교 그림이 확정본에서 이 자리로 온다 |
| **시퀀스 다이어그램** | 요청 1건이 참여자들을 지나는 **호출 순서**. **추가하는 기능마다 1장** — 장애 시나리오가 아니라 기능 단위로 그린다. 병렬 구간·실패 응답을 색으로 구분 |
| 구성도 | 무엇이 어디에 있고 무엇이 무엇을 호출하는가 (의존 방향) |
| 플로우차트 | 요청·작업 1건이 지나는 단계와 분기, 각 분기의 결과 |
| 시간 흐름 (해당될 때) | 상태가 시간에 따라 바뀌는 것 — 여러 레인을 같은 시간 축에 겹쳐 **모서리가 어긋나는 지점**을 보이게 |
| 데이터 모델 (해당될 때) | 엔티티·값 객체와 관계. 테이블이 바뀌면 `docs/db-schema.html`이 원본이므로 여기서는 참조만 |

작성 규칙:

- **클래스 다이어그램 멤버는 한 줄에 하나** (`+ cancel()` / `+ changeShippingInfo()` 따로). 규약은 `toss-design`의 「박스 텍스트 오버플로 방지」.
- **가독성 우선** — 박스 라벨은 `foreignObject` 자동 줄바꿈(`.fo`)을 기본으로 쓴다. 라이프라인 5개 이상이거나 시간 축이 길면 `figure.fig-wide`(viewBox 1120).
- 그림마다 `figcaption`에 **"이 그림에서 읽어야 할 것" 한 문장**을 쓴다. 그림만 두고 설명을 빼지 않는다.
- 결정 카드는 **요약 표**로만 싣는다(ID·결정·근거 한 줄). 전문은 md에 있다.
- 푸터에 "결정의 원본은 `01-design.md`" 를 명시해 SSOT를 흐리지 않는다.
- 저장 후 브라우저로 띄워(`open`) 사용자가 바로 볼 수 있게 한다.

### 저장 전 자가 검사 (⑩, 하나라도 걸리면 고치고 다시)

- [ ] **md에 있는 표를 html에 복사하지 않았는가** — 응답 필드표·시드표·시나리오 대본 같은 것은 md에만 둔다. html이 md의 재렌더링이 되면 실패다
- [ ] 클래스 다이어그램이 있는가
- [ ] 추가하는 기능마다 시퀀스 다이어그램이 있는가
- [ ] 그림마다 `figcaption` 한 문장이 있는가
- [ ] **html에만 있고 md에는 없는 결정이 없는가** (원칙 6)
- [ ] 그림 수가 본문 분량에 비해 지나치게 적지 않은가 — "보는 문서"인지 확인

## 하지 않는 것

- 프로덕션·테스트 코드 작성 (dev-cycle 소관)
- `design.html`에만 있고 `01-design.md`에는 없는 결정 (SSOT 분리, 원칙 6)
- **md를 먼저 저장하고 html을 나중에 만드는 순서** (원칙 4 위반)
- 구현 차단 카드를 그림 없이 텍스트 나열로만 닫는 것 (원칙 3 위반)
- 숙박 도메인 관행·정책 판단 (domain-analysis), 기술 레퍼런스 조사·비교 (tech-research)
- `02-implementation.md`·`03-review.md` 수정
