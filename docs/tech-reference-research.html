STORAGE STRUCTURE

멀티 공급사 저장 — 어댑터 구조와 필드 매핑

이종 공급사 응답을 표준 모델로 바꿔 저장하는 구조는 두 가지 결정으로 나뉜다 — 변환 계층을 어디에 둘 것인가, 필드 매핑을 무엇으로 관리할 것인가.

추천도메인 포트 + 공급사별 어댑터(경량 헥사고날 + ACL 통합)로 변환 계층을 두고, 필드 매핑은 코드 기반 정적 매퍼(수동 변환, 필요 시 MapStruct)로 관리한다. DB 매핑 테이블은 현 규모에서 YAGNI.

구조의 원전 — ACL과 Normalizer

Azure Architecture Center는 Anti-Corruption Layer를 "의미론이 다른 서브시스템 사이에 Facade/Adapter 층을 두어 요청을 번역하고, 외부 시스템 의존이 자사 설계를 제약하지 못하게 하는 패턴"으로 정의한다[1]. AWS Prescriptive Guidance도 적용 조건을 "두 시스템의 의미론(semantics)이 달라 데이터를 교환해야 할 때"로 명시한다[2] — 공급사 2개의 이종 API를 자사 표준 모델로 바꾸는 stay-link가 정확히 이 시나리오다.

구조 원형은 EIP의 Normalizer 패턴이다: "의미는 같지만 포맷이 다른 메시지를 타입별 Message Translator로 라우팅해 공통 포맷으로 만든다"[4]. Message Translator 자체가 "GoF Adapter 패턴의 메시징 등가물"로 정의되어 있어[6], "공급사별 어댑터가 변환을 책임진다"는 설계는 패턴 카탈로그의 원전 정의와 일치한다.

표준 모델(Canonical Data Model)의 정량 근거도 원전에 있다: 표준 모델 없이 N개 시스템을 잇는 변환기는 N×(N-1)개가 필요하지만, 표준 모델을 두면 2N개로 줄어든다 — EIP 원문의 예시로 6개 앱 기준 30개 → 12개[5]. 공급사 추가 시 "어댑터 1개만 추가"라는 확장성 주장의 근거다. 국내 프로덕션 실사례로는 카카오뱅크가 세컨더리 어댑터(Redis·JPA·Kafka 포트-아웃 구현체)를 모듈로 분리한 멀티모듈 헥사고날을 공개했는데[8], 공급사 2개·단일 서비스 규모에서 멀티모듈은 과하다 — 단일 모듈 안에서 패키지 규율로 같은 경계를 유지하는 것이 적정선이다.

필드 매핑 — 코드 기반이냐, DB 매핑 테이블이냐

"공급사 필드명 → 자사 컬럼명" 매핑을 DB에 저장하는 configuration-driven 방식은 실재하는 패턴이다. AWS 공식 사례 두 건이 원전인데, 하나는 보안 로그를 표준 스키마(OCSF)로 바꾸는 ETL에서 매핑을 CSV로 정의해 DynamoDB에 저장하고 코드 수정 없이 소스를 추가하는 구조[9], 다른 하나는 메타데이터 테이블로 파이프라인을 구성하는 재사용 ETL 프레임워크다[10]. 그러나 두 사례 모두 소스가 수십~수백 개이고 매핑 변경이 배포보다 잦은 데이터 플랫폼 맥락이다.

주의 — YAGNI공급사 2개 규모에서 DB 매핑 테이블은 타입 변환·중첩 구조를 행으로 표현하기 어렵고, 컴파일 타임 검증을 잃으며, 매핑 데이터 자체가 새 운영 부담이 된다. 매핑 테이블이 정당화되는 조건(소스 수십 개 + 매핑 변경이 배포보다 잦음)을 문서에 남겨두고, 지금은 코드 기반으로 간다.

코드 기반을 택할 때 MapStruct는 @Mapping(target, source)으로 이름이 다른 필드를 컴파일 타임 코드 생성으로 매핑하고, unmappedTargetPolicy를 ERROR로 올리면 매핑 누락을 빌드에서 잡는다(기본값은 WARN)[11]. 다만 공급사 응답이 중첩·이종 구조라 수동 변환 메서드로도 충분하며, 의존성 추가는 매핑 메서드가 실제로 늘어난 뒤에 결정해도 늦지 않다.

HTTP CLIENT

WebClient 사용 패턴

WebClient를 고르는 정직한 근거는 성능이 아니라, 공급사 병렬 fan-out을 zip · timeout · retry 연산자로 선언적으로 조합할 수 있다는 것이다.

추천공급사 fan-out 계층에만 WebClient를 쓰고, 단발 동기 호출이 생기면 RestClient를 쓰는 이원 구성. RestTemplate은 Spring Framework 7.0부터 deprecated라 신규 채택 근거가 없다[15].

Java 25에서는 JEP 491(JDK 24 반영)로 synchronized로 인한 virtual thread pinning이 해소되어[20], "RestClient + Virtual Thread 병렬 호출"이라는 동기 대안도 기능상 충분하다. 그럼에도 WebClient를 택하는 이유는 부분 실패 허용 · 타임아웃 예산 · 재시도를 연산자 조합으로 표현할 수 있어서다. 이 선택이 잃는 것: reactor-netty 의존성과 리액티브 러닝커브, block() 경계 관리 책임, direct buffer 기반의 native memory 관리 포인트[22].

공식 문서로 확인된 핵심 패턴

  • Bean 구성 — Boot이 자동 구성하는 WebClient.Builder(프로토타입 빈)를 주입받아 공급사별 baseUrl 인스턴스를 각각 빈으로 만든다[16].
  • Connection pool 기본값 — Reactor Netty는 호스트당 최대 활성 채널 500 / pending 획득 대기 1,000 / 획득 타임아웃 45초. ConnectionProvider.builder()로 조정한다[18].
  • 타임아웃 계층 — connect(CONNECT_TIMEOUT_MILLIS) / response(responseTimeout) / read·write 핸들러 / 전체 메서드(timeout() 연산자)[13]. 우아한형제들 사례가 "Connection·Read·Method 세 가지를 모두 설정해야 한다"를 실전 교훈으로 남겼다[21].
  • 에러 핸들링 — retrieve()는 4xx/5xx에서 WebClientResponseException(상태코드별 서브클래스)을 던지고, onStatus(...)가 자사 도메인 예외로 변환하는 공식 지점이다[14].
  • fan-out과 blocking 경계 — 전 공급사 결과를 결합하면 Mono.zip, 도착 순 처리면 Flux.merge. zip은 하나가 에러면 전체 에러이므로 공급사별 onErrorResume으로 빈 결과 대체(부분 실패 허용). block() 계열은 non-blocking 전용 스케줄러에서 예외를 던지므로[17] 리액티브 체인 내부 금지 — MVC 서빙 스레드(virtual thread)에서 최종 1회만. VT는 blocking에서 carrier를 해제하므로[19] 이 대기가 저렴하다.
운영 주의토스는 WebClient 요청이 cancel될 때 응답 바디의 Netty buffer reference count가 해제되지 않아 direct buffer native memory leak이 발생한 운영 사례를 공개했다[22]. .cache() 등으로 응답 Mono를 재사용할 때 cancel 경로를 특히 조심할 것.

RESILIENCE

회복탄력성 — retry · 지터 · 서킷브레이커 · fallback

외부 연동을 자주 하는 서비스의 회복탄력성은 한 라이브러리로 일관되게 — 공급사별 인스턴스를 분리해 한 공급사의 장애가 다른 공급사 호출로 번지지 않게 한다.

추천Resilience4j(resilience4j-spring-boot3) 단일 채택. 공급사 어댑터 경계에는 어노테이션(@CircuitBreaker + @Retry + fallbackMethod), WebClient fan-out 내부에는 Reactor 자체 Retry.backoff(지수 백오프 + 지터 기본 내장) 또는 resilience4j-reactor 연산자를 조합하는 하이브리드. 공급사별 CircuitBreaker/Retry 인스턴스 분리가 부분 실패 허용의 핵심이다[31].

왜 지터인가

지수 백오프만 쓰면 실패한 클라이언트들이 같은 시각에 재시도를 반복한다(재시도 폭주). AWS Architecture Blog의 시뮬레이션 결론은 "해법은 백오프를 빼는 게 아니라 지터를 더하는 것"이며, Full Jitter는 총 호출량(서버 부하)을 가장 줄이고, 지터를 적용한 백오프가 원격 클라이언트의 표준 접근으로 권장된다[25]. AWS Well-Architected도 "재시도는 횟수 제한 + 백오프 + 지터"를 공식 베스트 프랙티스로 명시한다[26]. WebClient 체인에서는 Reactor의 Retry.backoff가 기본으로 지터(jitter factor 0.5 — 계산된 지연의 최대 50%)를 포함하므로[33] 이것만으로 지터 요건이 충족된다.

설정에서 알아야 할 것

공식 기본값: failureRateThreshold 50%, slidingWindowSize 100, minimumNumberOfCalls 100, waitDurationInOpenState 60초, 느린 호출(slow call)도 장애로 집계 가능[28]. Retry는 maxAttempts 3(최초 호출 포함) · waitDuration 500ms이 기본이고 retryExceptions로 재시도 대상을 제한한다 — 5xx·타임아웃만 재시도하고 4xx는 제외하는 설계가 여기서 나온다[27].

기본값 함정minimumNumberOfCalls=100이면 호출이 100번 쌓이기 전까지 실패율을 계산하지 않는다. 트래픽이 적은 데모 환경에서는 서킷이 영원히 열리지 않으므로 반드시 낮춰 잡는다.

어노테이션(AOP) 방식의 데코레이터 기본 순서는 Retry(CircuitBreaker(RateLimiter(TimeLimiter(Bulkhead(Function))))) — Retry가 최외곽이라 각 재시도가 서킷브레이커를 통과하고, OPEN이면 재시도도 즉시 차단된다. 순서 변경은 aspectOrder 프로퍼티, 정밀 제어는 Decorators 함수형 체이닝[29]. Reactor 체인에는 transformDeferred(CircuitBreakerOperator.of(cb)) 형태로 끼운다[30].

Netflix Hystrix는 공식 README가 maintenance mode(신규 개발·릴리스 중단)를 선언하고 신규 프로젝트에 Resilience4j를 권장하므로 후보에서 제외했다[36]. 국내 실전 사례로 우아한형제들은 CallNotPermittedException 전용 fallback과 상태 전이 이벤트 로깅·메트릭 대시보드까지를 적용 범위로 보여주고[37], 올리브영은 예외 유형별 fallback 오버로딩으로 Redis 장애 시 RDB로 자동 우회하는 대체 경로 설계를 공개했다[38].

확인 못 한 것지수+무작위를 결합한 IntervalFunction의 정확한 API명(ofExponentialRandomBackoff 여부)과 yml 프로퍼티명은 공식 문서 원문으로 확정하지 못했다 — 구현 시 라이브러리 소스로 재확인. (공식 문서에서 확정된 것은 ofExponentialBackoff()·ofRandomized()까지[27].)
4

RATE LIMIT

공급사 rate limit 대응

공급사 호출량 한도는 클라이언트 측 rate limiter로 선제 관리하고, 429 응답은 검색 경로에서 기다리지 않는다 — 해당 공급사만 빼고 부분 결과를 돌려준다.

추천Resilience4j RateLimiter — 3장의 CircuitBreaker·Retry와 같은 라이브러리라 의존성·설정·메트릭 체계가 하나로 통일되고, Reactor 어댑터로 WebClient 파이프라인에 끼울 수 있다[39]. 단일 인스턴스 시작이므로 Bucket4j의 분산 백엔드는 현재 YAGNI.

단, Resilience4j의 알고리즘은 엄밀한 토큰 버킷이 아니라 "각 주기 시작 시 허가 수를 limitForPeriod로 리셋"하는 고정 윈도 방식이다[39]. 윈도 경계에서 순간 버스트(최대 2×limit)가 가능하므로, 공급사가 초당 집계를 엄격히 한다면 limitRefreshPeriod를 잘게 쪼개 보정한다. 매끄러운 토큰 리필이 실제로 필요해지면 그때 Bucket4j(정통 토큰 버킷, 분산 백엔드 제공[40])로 교체하는 편이 낫다.

429 / Retry-After 처리 관행

표준부터: RFC 6585이 429를 rate limiting 상태로 정의하고 Retry-After 헤더를 포함할 수 있다(MAY)고 규정하며[44], RFC 9110 §10.2.3에 따라 Retry-After 값은 초 단위 정수 또는 HTTP-date 두 형식이므로 클라이언트는 둘 다 파싱해야 한다[45][46]. 재시도 관행은 3장과 동일 원전 — 지수 백오프 + 지터, 서버가 Retry-After를 주면 계산된 백오프보다 우선, 재시도 횟수·총량에 반드시 상한[25][26].

stay-link 연결점: 검색은 사용자가 대기 중인 동기 경로이므로 긴 Retry-After를 그대로 기다리는 것은 부적절하다. 429를 받은 공급사는 그 요청에서 제외하고 부분 결과를 반환하며, 429 관측치는 자체 rate limiter 임계를 보정하는 신호로 쓴다. 429를 서킷브레이커 실패로 집계할지는 3장 설정과 함께 결정할 문제다. 참고로 Stripe는 실서비스 API에 토큰 버킷 기반 rate limiter를 사용한다고 공개했고[48], Cloudflare는 슬라이딩 윈도 카운터(이전·현재 윈도 가중 평균)로 오차 0.003%의 근사 집계를 실측했다[49] — 공급사 측이 어떤 방식으로 집계할지 가늠하는 배경지식이 된다.

rate limit 때문에 캐싱이 필요해지는 판단 기준

Amazon Builders' Library가 원전이다 — "의존 대상이 throttling을 시작하거나 예상 부하를 감당하지 못할 것으로 판단될 때"가 캐시 도입 사유이며, 판단 기준은 세 가지다[47]:

  • 재사용성(히트율) — 응답이 여러 요청에 걸쳐 재사용되는가. stay-link에선 인기 목적지·날짜 조합 검색이 반복되는가가 관건.
  • 신선도 허용치 — 재고·가격의 stale 허용 TTL을 정의할 수 있는가.
  • 캐시 불능 시 동작 — cold start·캐시 장애 시 트래픽이 그대로 공급사로 향해도 견디는가.
도입 판정식(예상 공급사 호출률 × 안전 마진 > 공급사 한도) AND (히트율 유의미) AND (stale 허용 TTL 정의 가능) — 셋 다 참일 때만 호출 절감용 캐시를 도입한다. 하나라도 거짓이면 rate limiter + fan-out 동시성 제한만으로 시작한다. 캐싱 전략 상세는 5장.

CACHING

캐싱 전략 — 스탬피드와 비소유 데이터

캐시할 데이터가 우리 것이 아니라는 사실이 전략을 결정한다 — 쓰기가 공급사 쪽에서 일어나므로 write-through는 원천 불가능하고, cache-aside + TTL이 구조적으로 유일한 기본기다.

추천Caffeine을 Spring Cache 추상화 없이 직접 사용(AsyncLoadingCache)하고, expireAfterWrite(하드 TTL) + refreshAfterWrite(더 짧은 소프트 TTL) 조합으로 stale-while-revalidate 계열 정책을 구성한다. 단일 인스턴스에서 Redis는 유일한 이점(서버 간 공유)이 없어 순수 비용 — YAGNI.

캐시 스탬피드 방지 — "하나가 조회하는 동안 나머지는 기다린다"

Caffeine의 AsyncCache는 키에 대한 매핑을 CompletableFuture로 즉시 만들어, 같은 키의 동시 miss가 진행 중(in-flight) future를 공유하게 한다 — 공식 FAQ가 이를 "protecting against a cache stampede"라고 직접 서술한다[51]. 별도의 락·플래그 구현 없이 요청 병합(single-flight)이 라이브러리에 내장돼 있다는 뜻이다. 같은 계열의 대규모 원전으로, Facebook은 memcache에 lease 토큰을 도입해 thundering herd를 해결하며 DB 피크 질의율 17K/s → 1.3K/s를 실측했고[57], Instagram은 값 대신 promise를 캐싱해 동시 miss를 백엔드 1회 호출로 병합하는 동일 구조의 패턴을 공개했다[58].

비소유(공급사) 데이터의 stale 정책

정답 TTL은 없다 — AWS 캐싱 백서도 cache-aside/write-through 모두 "무엇을 얼마나 캐싱할지는 애플리케이션 책임"으로 규정한다[59]. 대신 RFC 5861의 어휘를 내부 정책으로 차용하면 stale 허용 범위가 3구간으로 정리된다[55]:

  • fresh 구간 — 무조건 캐시로 서빙.
  • stale-while-revalidate 구간 — stale을 서빙하되 백그라운드 갱신. Caffeine 매핑: refreshAfterWrite가 이 경계[50]. Cloudflare도 CDN 레벨에서 "만료된 응답을 즉시 stale로 서빙하며 백그라운드에서 갱신"하는 같은 구조를 상용 적용한다[62].
  • stale-if-error 구간 — 공급사 장애 시에만 서빙. "refresh 실패 시 기존 값 유지"라는 Caffeine 기본 동작과 사실상 일치.

무효화 선택지는 (a) TTL 만료 — 공급사가 변경 이벤트를 주지 않으면 사실상 유일한 수단, (b) 공급사 웹훅 수신 시 명시적 evict, (c) 버전 키 — 올리브영이 로컬 캐시 키에 버전 번호를 넣어 최신 버전만 로드하게 한 방식[60], (d) TTL + Redis Pub/Sub 브로드캐스트 — 카카오페이 방식[61]. (c)·(d)는 다중 인스턴스 대비책이므로 단일 인스턴스 현 단계에서는 (a) + 가능 시 (b)만 해당한다. 로컬 캐시의 적용 기준으로 카카오페이는 "최종적 일관성을 허용할 수 있는 조회용 데이터"를 제시하는데[61], 같은 논리로 검색·목록 경로는 캐시 대상이지만 가격·재고를 '확정'하는 경로는 캐시를 우회해 공급사를 재확인하는 판단이 도출된다.

AGGREGATOR CASES

멀티 채널 집계 아키텍처 사례

여러 제공자 API를 fan-out 조회해 정규화 · 집계하는 시스템은 공개된 원형과 실사례가 모두 있다 — 그리고 실사례들은 하나같이 실측된 문제(QPS 한도)가 생긴 뒤에야 구조를 바꿨다.

추천요청 시 동기 병렬 fan-out(Scatter-Gather / Gateway Aggregation) + 전체 타임아웃 예산 + 부분 응답 반환. 사전 수집(배치 ingest)이 정당화되는 조건은 "공급사 QPS 한도 < 자사 검색 트래픽"인데, 이 문제의식이 현 규모에는 존재하지 않는다 — YAGNI.

패턴 원전이 규정하는 부분 실패 관행

요구사항(한 번의 검색 → 여러 공급사 병렬 조회 → 정규화 → 집계, 부분 실패 허용)은 Azure의 Gateway Aggregation 패턴 문서가 기술하는 시나리오와 일치하며, 그 문서가 부분 실패 처리를 직접 규정한다: "일부 호출이 너무 오래 걸리면 타임아웃 후 부분 데이터 집합을 반환하는 것이 허용될 수 있다", "실패 대비 failover로 캐시된 데이터 반환을 고려하라", 그리고 "부분 응답을 줄지 전체 실패로 처리할지를 정책으로 명시해 클라이언트가 예측 가능하게 하라"[63]. EIP Scatter-Gather는 집계의 완료 조건이 하나가 아님을 보여준다 — "전부 대기 / 첫 응답(First Best) / 시간 초과" 중 선택하는 것[64]. MSA 맥락의 같은 구조는 API Composition(호출 결과의 in-memory join) 패턴으로 정식화되어 있다[65].

타임아웃·재시도의 원칙은 AWS Builders' Library가 원전이다: 모든 원격 호출에 connection 타임아웃과 request 타임아웃을 함께 설정하고, 재시도는 하류 부하를 증폭시키므로 capped exponential backoff + 지터로 제한한다[71]. fan-out에서 타임아웃 예산이 필수인 이론적 근거는 The Tail at Scale이다 — fan-out 시스템에서는 드문 꼬리 지연도 전체 요청의 상당 비율에 전파되며, p95 초과 시에만 보조 요청을 보내는 hedged request는 추가 부하 약 5%로 꼬리 지연을 크게 단축한다[72].

실사례가 보여주는 진화 경로

Agoda는 "공급사별 허용 QPS가 검색 트래픽을 결코 감당하지 못한다"는 실측된 제약 때문에 캐시 우선 조회 구조(PriceAggregator)를 만들었고[66], 이후 남는 QPS를 예산처럼 배분해 공급사에 선제 요청을 보내는 사전 수집(SmartScheduler)으로 진화했다[67] — 이 시스템은 학술 논문으로도 공개된 실재 시스템이다[68]. Skyscanner는 검색 세션 시작 시 오퍼를 조회해 ElasticSearch에 비정규화 색인하고, 이후 정렬·필터 요청은 색인으로 처리하는 하이브리드(Bellboy)를 택했다[69]. 공급사 연동 계층 자체에 대해서는, Agoda가 벤더 API를 소비해 자사 시스템용으로 정규화하는 connector 모듈을 두고 신규 벤더를 플러그인식으로 추가하는 구조를 공개했는데[70], 이는 1장의 어댑터 구조와 같은 결론이다.

설계 함의모든 실사례가 동기 fan-out에서 출발해, QPS 한도라는 실측된 문제가 생긴 뒤에 캐시 우선 → 사전 수집 또는 세션 인덱싱으로 이동했다. 동기 fan-out이 잃는 것(지연이 가장 느린 공급사에 종속, 호출량 = 검색량)이 실제로 닥쳤을 때의 진화 경로가 공개되어 있으므로, 지금은 가장 단순한 구조로 시작하고 이 로드맵을 설계 문서에 근거로 남긴다.
확인 못 한 것Expedia·Booking.com 엔지니어링 블로그 차원의 집계 아키텍처 해설 글은 검색으로 찾지 못했다(공식 개발자 제품 문서만 확인됨) — 지어내지 않고 비워둔다. Agoda·Skyscanner의 Medium 글 본문은 직접 열람이 차단되어(403) 검색 결과와 학술 논문 교차 확인으로 검증했다.
