DECISIONS

확정 사항 요약

목록 API 통합 범위에서 확정된 결정은 다섯 가지다.

#결정내용
D1저장 범위목록 응답에서 저장하는 것은 매핑(식별자)과 이름뿐. 요금·재고 원본은 저장하지 않는다
D2테이블 구조property / room 2테이블 — 숙소 / 숙소+객실 유형(room)의 2단계 매핑
D3네이밍hotel이 아닌 property — 호텔 외 숙박 종류 포함. 객실 유형 테이블은 room — 처음엔 물리 객실 오독을 피하려 room_type으로 잡았으나 Java에서 enum처럼 읽혀 room으로 개명(F1 D-F1-10, 2026-09-04). 의미는 그대로 공급사의 판매 단위(객실 유형)이며 물리 객실이 아니다. name 컬럼은 property_name·room_name으로 prefix 부여
D4식별자 원칙내부 식별자는 공급사 비종속. 같은 공급사 상품은 언제나 같은 내부 식별자 — UNIQUE 제약으로 보장
D5병합 안 함두 공급사가 같은 실제 숙소를 취급해도 각각 별도 property 행. 공통 키가 없으므로 추정 병합은 하지 않는다 (선택 구현으로 남김)
2

DATA FLOW

데이터 흐름

공급사별 목록 응답 → 어댑터가 번역 → 표준 목록 모델 → 매핑 upsert.

목록 API는 자주 바뀌지 않는 정적 콘텐츠이므로 검색 경로와 분리된 사전/주기 트랙에서 돈다. 어댑터가 필드명 번역과 B의 data 봉투 해체를 끝낸 뒤에는, 저장 로직이 공급사별 표현을 전혀 모른다.

upsert 규칙응답의 각 항목에 대해 (supplier, 공급사 코드)로 조회 → 있으면 기존 내부 id 유지(이름만 갱신), 없으면 새 id 발급. 이 규칙과 UNIQUE 제약의 조합이 "같은 상품은 항상 같은 내부 식별자" 불변식을 지킨다. 목록에서 사라진 상품의 삭제 정책은 목록 갱신 주기와 함께 사전작업 5에서 결정한다.

SCHEMA

저장 스키마

테이블 2개, 컬럼 4개씩. UNIQUE 제약이 곧 도메인 불변식이다.

schema.sql (H2) 
CREATE TABLE property (
    id                       BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    supplier                 VARCHAR(16)  NOT NULL,   -- 'A' | 'B'
    supplier_property_code   VARCHAR(64)  NOT NULL,   -- hotelCode / propertyId
    property_name            VARCHAR(255) NOT NULL,
    CONSTRAINT uq_property_supplier_code
        UNIQUE (supplier, supplier_property_code)      -- D4: 같은 상품 = 같은 내부 id
);

CREATE TABLE room (
    id                        BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    property_id               BIGINT       NOT NULL REFERENCES property(id),
    supplier_room_code   VARCHAR(64)  NOT NULL,   -- roomTypeCode / roomId
    room_name            VARCHAR(255) NOT NULL,
    CONSTRAINT uq_room_property_code
        UNIQUE (property_id, supplier_room_code)  -- 객실 코드는 숙소 안에서만 유일
);

제약이 담는 도메인 규칙

① 객실 타입 식별은 3값이 필요하다. roomTypeCode/roomId는 해당 숙소 안에서만 유일하다 — 다른 숙소에 같은 코드가 존재할 수 있다. property_id가 이미 (supplier, 숙소 코드)를 대표하므로, UNIQUE(property_id, supplier_room_code) 2컬럼으로 (공급사, 숙소 코드, 객실 타입 코드) 3값 제약이 충족된다. supplier 컬럼을 room에 중복으로 두지 않는 이유다.

② 내부 id는 공급사 코드와 독립이다. IDENTITY로 발급된 내부 id는 공급사 코드 체계와 아무 관계가 없으므로, 나중에 병합 계층을 얹거나 공급사가 코드 체계를 바꿔도 내부 식별자는 흔들리지 않는다.

5

NOT STORED

저장하지 않는 것

뺀 것에도 근거가 있다 — 고민 후 제외한 세 가지.

항목왜 안 넣나대신
maxOccupancy상세 조회 요청이 숙소 코드 단위라 객실별 값으로 걸러낼 수 있는 건 "모든 객실이 인원 미달인 숙소"뿐 — 절감 효과 미미. 공급사가 이미 요청 인원 수용 가능한 객실만 반환하므로 정확성 기여 0, 목록 갱신 주기만큼 낡은 값으로 잘못 거를 위험만 추가상세 응답의 값을 그대로 사용
요금·재고호출마다 변하는 동적 데이터. 원본이 외부에 있으므로 쌓아둘 필요 없음 (D1)검색 시 실시간 조회
병합 관계같은 실제 숙소임을 알려주는 공통 키가 없어 추정 병합은 오류 위험. 기본 동작은 공급사별 별도 노출 (D5)필요 시 이 테이블 위에 병합 계층 추가
