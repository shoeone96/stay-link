SCOPE

확정된 범위

F3(클라이언트)과 F4(목록 어댑터·포트)를 하나로 한다. F3 혼자서는 A의 실패 본문을 어떻게 받을지 정할 수 없고, 그 소비자가 D12이기 때문이다. 재고·요금(F5)은 묶음 분할과 부분 실패 값 형태라는 자기만의 어려운 결정이 있어 뗐다.

LAYOUT

구성도 — 무엇이 어디에 생기는가

위 레인이 core.application, 아래 레인이 supplier-client다. 파란 실선이 F3이 새로 만드는 것, 회색 실선은 F3a가 이미 설계한 것, 회색 점선은 다른 feature 것이다. 아래 레인은 패키지 네 줄로 나뉜다 — 공통은 PR #7이 쓴 com.stay.property.infrastructure 그대로이고, 공급사 하나가 폴더 하나라는 F2의 교훈대로 공급사별 네 가지만 하위 패키지로 뺀다.

패키지PR #7이 F3a 클래스 8개를 com.stay.property.infrastructure에 두었다(module-split 파일 트리를 따른 것). F3의 공통(어댑터·분류기·Fetcher 인터페이스)도 같은 패키지에 두고, 공급사별 네 가지(Fetcher·번역기·Api·DTO)만 …infrastructure.supplier.a / …supplier.b로 뺀다. 나누는 축은 "역할"이 아니라 "어느 공급사의 지식인가"다 — A 계약이 바뀌면 supplier.a 한 폴더만 열면 된다(F2 D-F2-1과 같은 기준). 공통 클래스가 늘어 한 폴더가 답답해지면 그때 .supplier로 내리는 것을 검토한다(PAT-2).

DECISION

D-F3-1 포트 시그니처 — 확정: 안 A fetchAll()

F3a의 조합기는 여러 호출을 한꺼번에 받도록 만들어졌다. 그래서 목록 포트도 fetchAll()이 자연스러워 보이지만, 목록 수집은 검색과 달리 지연이 중요하지 않고 호출자(F6 배치)는 공급사마다 따로 트랜잭션을 연다. 누가 병렬을 갖는지가 갈림길이다. PR #7이 더한 계약 5(같은 공급사가 여러 건)는 F5의 묶음 분할용이며, 목록 호출은 공급사당 1건이라 여기에는 걸리지 않는다.

확정 — 안 A (사용자 결정 2026-09-07)fetchAll() 한 번. 처음 추천은 안 B였으나 다시 검토에서 근거 셋이 전부 약했다 — "공급사별 트랜잭션 일치"는 fetchAll 뒤에 공급사별 트랜잭션을 열어도 성립하고(HTTP가 트랜잭션 밖으로 나가 오히려 낫다), "F11 재사용"은 선택 기능을 위해 지금 모양을 정하는 것이며, "수집은 지연이 요건이 아니다"는 직렬로 부를 이유가 못 된다. 안 A의 진짜 이점은 공급사가 늘어도 F6이 바뀌지 않는다는 것 — 대상은 등록된 Fetcher(EnumMap)가 정의하고 F6은 공급사를 모른다. F3a 조합기를 만든 이유(동시 호출·상한)가 첫 호출자에서 그대로 쓰인다. F11이 생기면 그때 fetch(Supplier)를 더한다(D-F1-8).
4

DECISION

D-F3-2 포트 결과 형태 — 확정: 안 A sealed 값

F4가 미결로 남긴 항목이다. F3a는 조합기 안에서 "실패는 Failed 값"으로 닫았지만 그건 supplier-client 안의 얘기이고, 포트가 core에 무엇을 돌려주는가는 여기서 처음 정한다.

확정 — 안 A (사용자 결정 2026-09-07)sealed 값. 사용자 요구 "요청마다 성공·실패를 알고 처리"가 곧 이 모양이다. B가 실패해도 B의 매핑은 지워지지 않는다 — Failed(B)는 빈 목록이 아니므로 F6의 "사라진 상품" 비교가 B에 대해 실행되지 않는다(README F6 "실패 시 기존 매핑 유지"). F3a 포트 계약 2("공급사 쪽 실패는 예외가 아니라 값")를 core 경계에서도 같은 원칙으로 잇는다. Outcome과 별개 타입인 이유는 층이 달라서다 — Outcome.Failed는 Throwable을 들고 supplier-client 안에만 있고, SupplierCatalogResult.Failed는 D12 유형을 들고 core로 나간다. 우리 코드 버그(F3a hardStop 도달 등)는 값으로 포장하지 않고 예외 그대로 전파한다(F3a D-F3A와 같은 기준, CLN-6).
5

DECISION

D-F3-3 실패는 어디서 유형이 되는가 — 확정: 안 A · 유형 8개

A는 HTTP 상태로, B는 200 안의 resultCode로, 타임아웃은 Throwable로 실패를 말한다. 세 모양을 D12 유형 하나로 만드는 자리가 한 곳인지 세 곳인지가 갈림길이다.

확정 — 안 A · 유형 8개 (사용자 결정 2026-09-07)규칙은 한 문장이다 — 조합기 앞에서는 전부 Throwable, 조합기 뒤 FailureClassifier 한 곳에서만 유형이 된다. ①~④ 어디서 나든 예외 신호는 onErrorResume 한 줄로 내려와 Failed가 되므로 ⑤가 전부 받는다. 번역기의 책임은 "봉투를 해체하고, 성공이 아니면 던진다"까지다. A 실패는 프록시 기본 동작(4xx/5xx → WebClientResponseException)을 그대로 쓰므로 상태 핸들러를 따로 짜지 않는다. 보장이 성립하는 조건 둘: ① Fetcher의 call()은 Mono.defer로 모든 작업을 Mono 안에 넣는다 — Mono를 만드는 동안 던진 예외는 조합기 밖이라 못 잡는다(리뷰 확인 항목). ② 분류기는 getCause() 사슬을 따라간다 — 연결 실패·소켓 타임아웃은 WebClientRequestException 안에 감싸여 온다. 분류기가 못 보는 것 하나: ④의 방어망 block(hardStop)이 터지는 경우는 공급사 실패가 아니라 우리 결함이라 F3a 설계대로 예외 그대로 올라온다.
고를 것유형을 8개로 갈지, README의 5개로 갈지는 이 카드에서 함께 정한다. 8개를 추천하는 이유 — ① F9가 재시도 대상을 고를 때 503·429·TIMEOUT은 재시도하고 500은 판단이 갈리므로 500과 503이 한 값이면 F9가 못 가른다 ② INVALID_RESPONSE는 공급사 장애가 아니라 계약 불일치라 운영자가 봐야 할 곳이 다르다 ③ UNEXPECTED는 우리 버그 후보다. 값이 늘어 F8 reason이 길어지는 것 말고 비용은 없다.
6

DECISION

D-F3-4 ErrorCode 인터페이스 처분 — 확정: 유지, 독립 enum SupplierErrorCode

F0은 "ErrorCode의 두 번째 구현체가 F4에서 오는지 보고, 안 오면 인터페이스를 없앤다"고 적어 뒀다. 답은 안 온다다 — SupplierErrorCode는 자사 API 응답 코드가 아니라 suppliers[].reason 값이라 성격이 다르다. 처음엔 "그러면 언제 없애느냐"로 세 안을 그렸는데, 협의에서 질문 자체가 잘못 세워졌다는 것이 드러났다.

확정 — 셋 다 아님 (사용자 결정 2026-09-07)ErrorCode는 그대로, 실패 유형은 독립 enum. 처음 추천은 안 A(지금 제거)였다. 사용자가 "클라이언트에서 ErrorCode를 쓰려 해서 생긴 문제 아니냐, 근본 이름은 도메인 모듈 것"이라고 짚었고, 다시 보니 ErrorCode는 이미 core에 있고 supplier-client 참조가 0건이다. D-F0-6이 도메인 모듈 인터페이스의 존폐를 외부 경계 타입의 구현 여부에 건 것이 범주 착오였고, 그 조건 발동을 근거로 한 제거 추천도 같은 착오라 철회했다. 결론: F0 결정(인터페이스 유지)은 불변, D-F0-6의 조건 문언만 "컨텍스트 domain의 코드 enum이 두 번째 구현체 후보"로 정정, 지금은 동작하는 전체 기능이 우선이라 SupplierErrorCode를 상속 없는 enum으로 만들고 네이밍·관계 정리는 컨텍스트 전용 응답 코드가 처음 필요한 feature(F7 후보)에서 한 번에 한다. F3의 ErrorCode 관련 코드 변경은 0.
7

DECISION

D-F3-5 실제 소켓을 여는 테스트 — 확정: 만들지 않는다

F3a는 웹 서버 없이 테스트 더블로 끝났다. F3은 다르다 — 그룹 등록 프록시가 진짜 HTTP로 DTO를 받아 오는지, 503·지연·무응답에서 예측된 실패 값이 나오는지는 소켓을 열어야 보인다. supplier-client에는 서버 스택이 없다.

확정 — 소켓 테스트 서버 없음 (사용자 결정 2026-09-07)추천은 안 A(JDK HttpServer, 의존성 0)였고 클래스패스에 이미 있는 reactor-netty HttpServer도 후보로 들었다. 사용자 결정은 공급사는 자동 테스트에서 무조건 테스트 더블로 응답을 설정해 검증하고, 실제 HTTP·타임아웃·503 경로는 api-app + F2 모의 서버를 띄운 뒤 k6로 우리 시나리오를 돌려 확인한다는 것. 더블만으로는 그룹 등록 프록시의 DTO 디코딩과 read-timeout 발동이 자동 검증되지 않으므로 그 두 항목은 md 5.2 k6 검증 계획에 명시했다. F3에는 fetchAll() 호출자가 없어 k6 실행 시점은 F6이다. 타임아웃 초기값 실측도 같은 방법으로 한다.
8

DECISION

D-F3-6 검색과 수집의 시간 예산 — 확정: 수집용 조합기 빈을 하나 더

PR #7의 FanOutExecutor는 생성자에서 정책 한 벌(supplier.fan-out.*: max-concurrent 2 · per-call 2s · budget 5s, 자리표시자)을 받고 빈 하나로 등록된다. 그런데 이번에 처음 생기는 실제 호출자(목록 수집)는 검색과 요건이 다르다 — 검색은 사용자가 기다리고, 수집은 배치가 기다린다. 같은 3초로 둘 다를 재면 하나는 반드시 틀린다.

확정 — 안 B, 빈 둘 형태 (사용자 결정 2026-09-07)수집용 정책을 따로 두되 F3a 코드는 건드리지 않는다. 처음엔 runAll(calls, policy) 오버로드로 그렸으나 코드를 다시 보니 정책이 private 메서드 다섯 곳에 퍼져 있었다. 조합기는 "정책 한 벌을 든 인스턴스"로 설계돼 있으므로 supplier.catalog.fan-out.*을 읽는 CatalogFanOutProperties로 FanOutExecutor 빈을 하나 더 만들고 어댑터가 이름으로 받는다. 초기값(근거는 외부 문헌이 아니라 자사 응답 목표): 그룹 connect 1s · read 45s(뒷그물 — 두 용도 중 긴 쪽보다 커야 소켓이 조합기보다 먼저 끊지 않는다) / 검색 supplier.fan-out 2 · 4s · 5s(사용자가 2s는 짧다고 해 per-call을 budget 바로 아래로, 캐싱 전제, F5 재산정) / 수집 supplier.catalog.fan-out 2 · 30s · 40s(오래 걸려도 다 받는 것이 중요, 사용자가 늘림 허용). 전부 설정이지 결정이 아니며 k6로 실측 후 바꾼다. 재시도는 F9에서 부등식과 함께.

SEQUENCE

확정 시퀀스 — fetchAll() 에서 A는 성공, B는 200 + E503

카드 1~3이 확정된 모양으로 호출 1건은 이렇게 흐른다. 실패가 값이 되는 자리(④)와 유형이 되는 자리(⑤)가 다르다는 것, 그리고 Mono가 어댑터를 넘어가지 않는다는 것을 볼 것. A의 정상 경로와 B의 실패 경로가 같은 runAll 안에서 나란히 흐르고, 결과 두 칸이 요청 순서로 돌아온다.
