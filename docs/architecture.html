MODULE MAP

전체 지도 — 모듈 여섯 개와 의존 방향

실행되는 것은 api-app 하나뿐이고, 나머지는 그 안으로 합류하는 라이브러리이거나 아예 다른 프로세스입니다.

모듈을 넷으로 쪼갠 목적은 파일 정리가 아니라 의존 방향을 컴파일러가 지키게 만드는 것입니다. api-app은 persistence·supplier-client를 runtimeOnly로만 잡습니다. 그래서 부팅할 때 구현체는 클래스패스에서 발견되지만, 코드가 그 구체 클래스를 import하는 순간 컴파일이 깨집니다. 경계가 규율이 아니라 빌드 설정으로 강제됩니다.

이 배치가 실제로 막는 것core는 jakarta.persistence와 spring-context·spring-tx만 씁니다. domain 패키지는 그중 아무것도 쓰지 않고, application 패키지만 @Service·@Transactional을 위해 spring-context를 씁니다. WebClient도 JPA도 core에서는 이름조차 보이지 않습니다.
모의 서버를 둘로 쪼갠 이유한 프로세스에 포트만 둘로 낸 첫 시도는 커밋 전에 버렸습니다. "A만 내렸을 때 B는 정상"을 재현하려면 프로세스가 실제로 둘이어야 하고, 공유 모듈이 하나라도 있으면 두 공급사의 계약이 서서히 같아지기 때문입니다. 두 모듈은 서로 의존하지 않으며 공유 프로젝트도 없습니다.

CALL PATH

목록 수집 경로 — 한 줄기 전체

지금 끝에서 끝까지 이어져 있는 유일한 줄기입니다. 포트 하나를 부르면 공급사 전부가 동시에 불리고, 성공도 실패도 값 하나로 돌아옵니다.

줄기 전체에서 지켜지는 성질이 셋 있습니다. 첫째, Mono는 supplier-client 밖으로 나가지 않습니다 — 리액티브 타입이 등장하는 마지막 자리가 SupplierCall이고 포트는 평범한 List를 돌려줍니다. 둘째, 공급사 실패는 예외가 아니라 값입니다. 셋째, 결과를 고르는 열쇠는 공급사가 아니라 호출 자리(인덱스)입니다.

단계별로 무엇을 하는가

단계하는 일왜 여기인가
SupplierCatalogPort fetchAll() 하나뿐. 공급사를 하나씩 부르는 메서드가 없다 공급사가 늘어도 호출자 불변
SupplierCatalogAdapter Fetcher 전부를 SupplierCall로 감싸 조합기에 한 번에 넣고, 돌아온 Outcome을 포트 결과로 옮긴다 리액티브 타입의 종착지
EnumMap 색인 같은 공급사가 둘이면, 또는 빠진 공급사가 있으면 기동을 실패시킨다 조용히 사라지는 것을 막음
SupplierXCatalogFetcher 프록시 호출과 번역을 Mono.defer 안에 넣어 동기 예외까지 error 신호로 만든다 구현이 곧 수집 대상 등록
SupplierXApi HTTP Interface. base-url·타임아웃·헤더는 코드가 아니라 그룹 설정에서 온다 공급사 계약의 선언 자리
FanOutExecutor 동시 구독 상한·호출당 상한·전체 예산을 걸고 결과를 값으로 모은다 바깥 호출에 상한을 두는 곳
계약 하나Fetcher.call()은 본문에서 블로킹하면 안 됩니다. Mono가 만들어지기 전에 막히면 .timeout(perCall)이 붙을 자리 자체가 없어 어떤 장치도 그 호출을 자르지 못합니다. 그래서 두 Fetcher 모두 프록시 호출까지 Mono.defer 안에 넣습니다.
왜 공급사가 아니라 자리로 식별하나한 요청에 담을 수 있는 코드 수는 공급사 API의 제약이라, 앞으로 어댑터가 묶음을 나눠 같은 공급사를 여러 번 호출하게 됩니다. 그때 결과를 공급사 값으로 골라내면 두 건 중 한 건만 도착해도 나머지를 도착한 것으로 착각합니다. Outcome이 공급사를 들고 있어도 그것은 표시용이지 열쇠가 아닙니다.

OUTBOUND WIRING

바깥으로 나가는 배선 — 그룹 · 프록시 · 필터

공급사마다 그룹을 따로 둡니다. 그래야 커넥터가 갈리고, 타임아웃과 기본 헤더를 공급사별로 다르게 줄 수 있습니다.

Spring Boot 4.1의 @ImportHttpServices가 그룹 단위로 HTTP Interface를 등록하면, 등록기가 인터페이스마다 빈을 하나씩 만들어 줍니다. 쓰는 쪽은 타입으로 주입받아 메서드를 부르면 끝이고, 주소·상한·헤더는 코드가 아니라 spring.http.serviceclient.<group>.*에서 옵니다. 이 그룹 분리가 Boot 4.x로 올린 실질적인 이유이기도 합니다 — 3.5의 전역 설정으로는 공급사별 차등이 성립하지 않습니다.

구성 요소 셋

클래스책임핵심 판단
SupplierHttpClientConfig 그룹 2개 등록 · 검색용 FanOutPolicy/FanOutExecutor 빈 · 필터 부착 배선만, 공급사 지식 없음
SupplierAApi / SupplierBApi 공급사 계약을 타입으로 선언. A는 AHotelsResponse, B는 봉투 BPropertiesResponse 실패 표현이 달라 별개
MaskingExchangeFilter 나간 호출 1건마다 시작·완료·실패 로그. 자격 증명 헤더는 값을 지우고, 쿼리는 이름만 남기고 값을 전부 지운다 목록 방식이면 새는 이름이 생김
이 필터가 못 보는 것호출당 상한이나 전체 예산이 걸리면 상류가 취소되므로 오류 신호가 오지 않아 doOnError가 불리지 않습니다. 그래서 잘린 호출의 기록은 조합기가 남깁니다 — 취소 이유(상한인지 예산인지)를 아는 층이 거기이기 때문입니다. 두 층의 로그를 합쳐야 한 호출의 전말이 나옵니다.

BACK PRESSURE

상한을 거는 곳 — FanOutExecutor

이 클래스의 존재 이유는 호출을 편하게 하는 것이 아니라 바깥으로 나가는 호출에 상한을 두는 것입니다. 연산자마다 역할이 정확히 하나씩입니다.

<T> runAll(List<SupplierCall<T>> calls) : List<Outcome<T>>BLOCKING
계약내용기대는 쪽
1돌려주는 리스트 크기는 언제나 요청한 호출 수와 같다 — 예산에 잘린 자리도 실패 값으로 채운다어댑터
2공급사 쪽 실패는 예외가 아니라 Outcome.Failed 값이다분류기
3한 곳이 실패해도 나머지 결과는 그대로 돌아온다부분 실패 응답
4돌려주는 순서는 요청한 호출 순서와 같다 — i번째 결과가 i번째 호출의 것묶음 분할 호출
5같은 공급사가 호출 목록에 여러 번 들어올 수 있다코드 상한 대응

정책이 두 벌인 이유

검색은 사용자가 기다리고 수집은 배치가 기다립니다. 정책 한 벌을 나눠 쓰면 어느 한쪽은 반드시 틀리므로, 같은 조합기 클래스를 정책만 다르게 준 빈 두 개로 올렸습니다. 조합기 코드는 한 줄도 바뀌지 않습니다.

용도prefix / 값성격
검색supplier.fan-out — 2 · 4s · 5s사람이 기다림
수집supplier.catalog.fan-out — 2 · 30s · 40s다 받는 것이 중요
기동 시점에 막는 것바인딩 지점에서 강제하는 것은 최소 조건 budget > per-call 하나입니다. 기동 시점에는 공급사가 몇 곳인지 알 수 없기 때문입니다. F9(2026-09-07)에서 max-concurrent 를 프로퍼티째 삭제하고 요청마다 호출 수만큼 동시에 보내기로 해 웨이브가 항상 1이 되었으므로, 지켜야 하는 부등식도 budget > per-call 하나로 줄었습니다. 재시도는 per-call 안에서 도는 2단 상한이라 우변에 곱해지지 않고, 시도별 상한이 (per-call − 백오프 합) ÷ 시도 수로 유도됩니다. 실제 동시 호출 상한은 커넥션 풀 하나가 맡습니다.
아직 실측 전지금 설정에 적힌 1s · 45s · 2 · 4s · 5s · 2 · 30s · 40s는 전부 자리표시자입니다. 값을 정할 근거(모의 서버 + k6 실측)가 아직 없어 자리만 잡아 두었습니다. 호출자가 생기는 시점에 재서 채웁니다.

TRANSLATION

번역 — 원본 DTO에서 표준 모델로

공급사별 필드 이름은 번역기를 지나면서 사라집니다. 표준 모델을 받는 쪽은 어느 공급사에서 왔는지 몰라도 됩니다.

A는 본문이 곧 데이터이고 B는 resultCode / resultMessage / data 봉투를 씌웁니다. 봉투를 벗기는 일, 계약 필수 필드를 확인하는 일, 필드를 대응시키는 일 — 번역기가 하는 것은 이 셋뿐이고 그 이상은 하지 않습니다.

표준 모델공급사 A공급사 B
CatalogProperty.codehotelCodepropertyId
CatalogProperty.namehotelNamepropertyName
CatalogProperty.roomsroomTypes[]rooms[]
CatalogRoom.coderoomTypeCoderoomId
CatalogRoom.nameroomTypeNameroomName
목록 배열items[] (본문 최상위)data.items[] (봉투 안)
실패 판정HTTP 상태HTTP 200 + resultCode ≠ 0000

필수 필드를 공급사 이름으로 검사하는 이유

번역기의 검증 메시지는 propertyId is missing처럼 공급사 계약의 이름을 씁니다. 어긋난 응답을 계약 문서와 대조하는 사람이 읽는 메시지이기 때문입니다. 자사 모델 이름(code)으로 적으면 그 사람이 다시 번역해야 합니다.

표준 모델이 자기 검증에서 던지는 범용 IllegalArgumentException도 InvalidSupplierResponseException으로 감싸 올립니다. 전용 타입을 두는 목적은 이 타입만 INVALID_RESPONSE로 분류되게 하는 것입니다 — 범용 예외를 그대로 분류하면 무관한 버그까지 같은 유형이 되어 UNEXPECTED의 신호 기능이 죽습니다.

객실 0개는 통과시키되 세어 둔다roomTypes/rooms가 없으면 예외로 막지 않고 공급사 단위로 집계해 warn을 남깁니다. 계약 문서에 "객실 없는 숙소"라는 표현이 없어 막을 근거가 없고, 계약이 바뀌면 전 숙소가 한꺼번에 0개가 되어 이 로그로 드러나기 때문입니다. 예외로 바꿀지는 실측 뒤에 정합니다.

FAILURE

실패가 값이 되는 길

A는 HTTP 상태로, B는 본문 코드로 실패를 알립니다. 두 표현이 합류하는 지점이 딱 한 곳 있습니다.

Reactor와 WebClient는 원인을 여러 겹으로 감싸기 때문에 맨 바깥 타입만 보면 대부분 "분류표에 없는 예외"로 보입니다. 그래서 분류기는 cause 사슬을 바깥부터 따라가며 처음 맞는 규칙으로 유형을 정합니다.

유형A (HTTP 상태) / B (resultCode)볼 사람
INVALID_REQUEST400 / E400우리 요청
UNAUTHORIZED401 / E401키 설정
RATE_LIMITED429 / E429호출량
SUPPLIER_ERROR500 / E500공급사
UNAVAILABLE503 / E503 · 연결 거부 · 이름 해석 실패공급사
TIMEOUTperCall 초과 · 소켓 read timeout · 예산 초과상한 값
INVALID_RESPONSE디코딩 실패 · 계약 필수 필드 누락 · B의 미지 코드공급사 계약
UNEXPECTED분류표에 없는 예외 · 계약에 없는 HTTP 상태우리 코드
두 유형을 굳이 갈라 둔 이유INVALID_RESPONSE는 응답이 계약과 어긋난 것(공급사 쪽을 볼 일)이고, UNEXPECTED는 분류표에 없는 예외가 온 것(우리 쪽을 볼 일)입니다. 보는 사람이 달라서 따로 둡니다. UNEXPECTED일 때 남기는 ERROR 로그는 catch-all이 아니라 "분류표를 고쳐야 한다"는 신호입니다.
로그에 예외를 통째로 싣지 않는 이유HTTP 오류 예외의 메시지에는 요청 URL이 통째로 들어 있고, 거기에 쿼리로 실린 자격 증명이 그대로 로그에 남습니다. 그래서 조합기는 원인의 타입만 싣고, 원인 전체는 값(Outcome.Failed)으로 넘겨 분류에만 씁니다.

STORAGE & CONTRACT

저장 모델과 자사 응답 계약

테이블은 둘, 포트 메서드는 save 하나. 조회는 아직 없습니다 — 부를 사람이 없기 때문입니다.

테이블컬럼제약
propertyid · supplier · supplier_property_code · property_nameUNIQUE(supplier, code)
roomid · property_id · supplier_room_code · room_nameUNIQUE(property_id, code)

room은 supplier 컬럼을 갖지 않습니다. 비정규화 컬럼을 두는 안은 검토 후 기각했고, 공급사는 property를 경유해 얻습니다. 객실 코드의 유일성이 공급사 전체가 아니라 소속 숙소 안에서만 성립하기 때문에 UNIQUE도 property_id 기준입니다.

포트에 조회가 없는 이유upsert 규칙과 조회 메서드는 호출자가 생기는 시점으로 미뤘습니다. 쿼리 패턴을 모르는 채 만든 조회 메서드는 실제 사용처가 생기면 어차피 다시 쓰게 되기 때문입니다. 수집 배치가 "공급사 단위로 전부 모아 메모리에서 비교하고 한꺼번에 저장"하는 형태로 정해졌으므로, 그 모양에 맞는 메서드를 그때 추가합니다.

자사 API 응답 계약
