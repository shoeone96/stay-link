VERDICT

결론 — 무엇이 응답을 바꾸는가

응답을 흔들 수 있는 축은 넷뿐입니다. 셋은 완전히 결정적이고, 나머지 하나는 조작자가 명시적으로 켰을 때만 무작위가 됩니다.

축무엇이 정하나결정적인가실측
요청 파라미터 hotelCodes/propertyIds · checkIn/checkOut · adults+children 예 — 같은 입력이면 같은 출력 같은 요청 20회 반복 → 응답 해시 1종 (A·B 모두)
조회한 날짜 그 날짜가 금·토인지(할증), 매월 며칠인지(품절일) 예 — 벽시계가 아니라 요청한 날짜만 본다 09-11(금)·09-12(토)만 할증, 10-02만 재고 0
조작자가 넣은 상태 POST /control/mode 로 켠 고장, 카탈로그 DB의 내용(/control/** 또는 직접 SQL로 바꾼다) 예 — 건드린 적이 없으면 시드 그대로다 고장 미설정 상태로 200회 호출 → 비200 응답 0건
rate (확률) 조작자가 rate<1.0 을 직접 넘겼을 때만 ThreadLocalRandom 아니오 — 유일한 무작위 지점 (기본값 1.0 = 전부 발동) rate=0.3 200회 → 503이 54회(27%)
한 줄 답모의 서버는 스스로 흔들리지 않습니다. 시드·요금·재고는 순수 함수로 계산되고, 지연·오류·무응답은 제어 API로 켜기 전까지 존재하지 않는 상태입니다. 자사 앱이 보는 공급사 동작은 전부 재현 가능합니다.

rate1.00.0 ~ 1.0 (벗어나면 거절)호출 1건당 발동 확률. 1.0이면 무작위 없음
errorCode503429 · 500 · 503 (그 밖의 값은 503으로)error 모드가 낼 실패 코드
delayMillis30000 이상 (음수는 거절)delay 모드가 붙잡을 시간
durationSeconds0 = 무기한정수지나면 자동으로 정상 복귀
endpointallall · list · availability고장을 걸 범위. 목록만 정상 / 재고·요금만 고장이 가능

지점동작왜 이렇게대처
고장 상태는 전역·무기한 durationSeconds 기본값이 0이라 한 번 켜면 끄기 전까지 계속 걸려 있다 수동 조작 중에 저절로 풀리면 관찰이 끊긴다 대본 끝에 value=normal 을 넣거나 처음부터 durationSeconds 를 준다
고장 판정이 인증보다 먼저 키가 틀려도 고장 중이면 401이 아니라 503이 나간다 무너진 서버는 요청을 읽어 보지 않는다 — 의도된 순서 인증 케이스는 고장이 꺼진 상태에서 확인한다
rate<1.0 은 재현 불가 같은 호출이 어떤 때는 성공, 어떤 때는 실패 (시드 고정 없음) 부분 장애를 흉내 내려면 무작위가 필요하다 결정적 회귀 확인에는 rate 를 건드리지 않는다 (기본 1.0)
카탈로그는 재기동해도 남는다 H2 파일 DB라 조작한 상태가 유지된다. 예전처럼 껐다 켠다고 시드로 돌아가지 않는다 지운 상태 위에서 이어서 실험할 수 있어야 한다 초기화는 data/ 폴더 삭제 후 재기동. 실측으로 시드 3행 복귀 확인
직접 SQL은 아무것도 검증하지 않는다 제어 API가 막는 값도 그대로 들어간다 — 음수 요금, 계약에 없는 코드 일부러 이상한 상태를 만들어 자사 앱 반응을 보는 것이 이 경로의 쓸모다 실측: net_rate=-5000 주입 → 응답에 nightlyRate: -5000. 자동 대본에는 제어 API를 쓴다
no-response 는 600초까지 남는다 정상으로 되돌려도 이미 붙잡힌 요청은 상한까지 매달려 있다 상한이 없으면 서버를 내리기 전까지 스레드가 돌아오지 않는다 가상 스레드라 부담은 없지만, 이어지는 대본에서 이전 요청이 살아 있을 수 있다
한 가지만 기억한다면이 서버가 이상하게 굴면 먼저 GET /control/state 를 보세요. mode 가 NORMAL 이 아니면 누군가(대개 직전 대본이) 켜 둔 것이고, NORMAL 인데 응답이 예상과 다르면 원인은 셋 중 하나입니다 — 요청 파라미터 · 조회한 날짜 · DB에 실제로 들어 있는 행. 마지막 것은 SELECT * FROM a_room 한 번이면 끝납니다. 그 밖에 응답을 바꿀 수 있는 것은 없습니다.
