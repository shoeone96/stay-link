1

배경

왜 나눴는가

F6(catalog-sync)이 API 서버 안에서 @Scheduled로 돌면, API 서버를 scale-out할 때 인스턴스 수만큼 중복 실행됩니다.

공급사 목록 API를 replica 수만큼 여러 번 호출하게 되고, F4가 이미 실패 유형으로 다루는 "한도 초과"를 스스로 유발할 수 있습니다. 그래서 batch를 API 서버와 별도 배포 단위로 떼어 replica 1(또는 외부 스케줄러 트리거)로 고정하기로 했습니다.

기존API 서버 안에서 스케줄

같은 프로세스가 API 서빙과 batch를 같이 함. scale-out하면 batch도 같이 늘어나 중복 실행됨.

지금별도 배포 단위(batch-app)

API 서버(api-app)와 batch(batch-app)가 서로 다른 jar. batch는 replica 1로 고정, API는 자유롭게 scale-out.

이 목표를 이루려면 domain 코드를 API 앱과 batch 앱 둘 다가 공유해야 하고, 그러려면 물리적으로 별도 Gradle 모듈이어야 합니다 — 패키지 경계만으로는 "서로 다른 jar"가 안 됩니다.

수정 (협의 결과 1)처음엔 DB 구현체와 WebClient 어댑터를 infrastructure 하나에 같이 뒀습니다(`coding-standard`의 LAY-5가 논리적으로 같은 레이어라고 적어놔서). 하지만 둘은 바뀌는 이유가 다릅니다 — DB 스키마 변경과 공급사 API 변경은 서로 무관한 축입니다. 테스트 방식도 다르고(`@DataJpaTest`+H2 vs 공급사 mock), "신규 공급사 추가 시 고칠 지점 1개"라는 원래 목표에도 둘을 분리하는 쪽이 더 정확히 맞습니다. 그래서 persistence(JPA)와 supplier-client(WebClient, F3·F4·F5가 채울 자리)로 나눕니다.

application(서비스)은 어디로 가나 — core로 domain과 통합

api-app·batch-app 둘 다 있어야 하는 건 persistence·supplier-client뿐 아니라 서비스/유스케이스(트랜잭션 경계, 포트 오케스트레이션)도 마찬가지입니다. 처음엔 이걸 별도 application 모듈로 더 쪼개려 했지만, 재검토 끝에 domain과 합쳐 하나의 core 모듈로 가기로 했습니다.

기각application을 별도 모듈로

domain "Spring 의존 0"(LAY-2)은 지키지만, 이 프로젝트는 F0~F2를 domain·application이 이미 한 모듈(패키지 구분만)인 채로 완성했고 그 규칙은 컨벤션만으로 잘 지켜졌다 — 물리적 벽이 검증된 필요는 아니었다. persistence·supplier-client 둘 다 어차피 항상 같이 쓰이는 소비자(api-app·batch-app)를 생각하면 모듈을 더 쪼갤 값어치가 작다.

채택domain＋application = core

카카오뱅크 메시지 허브 사례와 정확히 같은 모양 — 포트 인터페이스＋비즈니스 로직을 코어 모듈 하나에 두고, 진입점(그쪽은 api/data-api/loader/consumer 4개, 우리는 api-app·batch-app 2개)이 코어에 의존. DB·외부 연동은 코어 바깥의 어댑터(persistence·supplier-client)로 분리.

참고문헌카카오뱅크 기술블로그 — 유일한 멀티모듈 헥사고날 아키텍처: 메시지 허브 적용기
"코어 모듈은 포트 양쪽의 인터페이스와 실제 비즈니스 로직을 하나의 모듈로 구성했습니다" — 원문 인용, `reference-verifier` 검증 통과(PASS).
이름을 domain이 아니라 core로 부르는 이유이 모듈은 이제 두 레이어(domain＋application)를 담습니다 — 이름을 domain으로 두면 순수 도메인 전용이라고 오해하기 쉬워, 카카오뱅크와 같은 이름 core로 씁니다. LAY-2("domain 패키지는 Spring 의존 0")는 여전히 유효하지만 모듈 경계가 아니라 패키지 컨벤션(`com.stay.property.domain` vs `com.stay.property.application`)으로 지킵니다 — F0~F2와 같은 방식입니다.

4

유보

아직 안 만든 것 — batch-app

지금 settings.gradle.kts에는 batch-app이 없습니다.

이유F6(catalog-sync)이 아직 설계되지 않아 batch-app에 담을 코드가 없습니다. 빈 모듈을 미리 만드는 건 투기적이라, F6을 실제로 설계·구현하는 시점에 만들기로 했습니다.

F6 설계가 끝나면 이 자리에 batch-app 모듈이 생기고, 그림 1의 점선이 실선으로 바뀝니다.

결정 카드·참고문헌

ID결정근거 한 줄
D-MS-1domain+application만 통합(core), persistence·supplier-client는 분리소비자가 항상 셋을 같이 받아 전부 분리는 값어치 낮음 / persistence는 JPA 테스트 셋업이 여전히 달라 분리 유지
D-MS-2batch-app은 F6 설계 시 생성담을 코드 없는 빈 모듈은 투기적
D-MS-3모듈명 domain→core로 개명두 레이어(domain+application)를 담아 domain이라는 이름은 오해 소지
D-MS-4SupplierClient 포트는 application 패키지 소유Aggregate 불변식이 아니라 유스케이스 오케스트레이션(LAY-5)
D-MS-5api-app→persistence·supplier-client는 runtimeOnly구체 어댑터 클래스 오import를 컴파일 에러로 막음
D-MS-6api-app 자체의 data-jpa·webflux·mysql 의존 제거persistence·supplier-client의 implementation이 런타임 전이로 이미 공급(실측 확인)
