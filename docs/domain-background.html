BACKGROUND

배경 — 무엇이 문제인가

숙박 플랫폼(OTA)의 상품은 두 경로로 들어옵니다. 자사에 직접 등록된 숙소, 그리고 외부 공급사(Supplier)에서 연동해 오는 상품입니다.

국내 대형 숙박 플랫폼 앱을 떠올리면, 화면에 뜨는 모든 숙소가 그 플랫폼 회사와 직접 계약한 숙소처럼 보입니다. 실제로는 자사 직등록 상품 외에, 외부 공급사의 상품을 API로 끌어와 함께 판매합니다[1]. 이렇게 외부 판매 채널(공급사)과 상품·재고·요금을 주고받는 연동 계층이 이 시스템이 다루는 채널연동입니다. 공급사를 하나 붙일 때마다 팔 수 있는 숙소가 늘어나므로, 플랫폼 입장에서는 상품 커버리지를 넓히는 핵심 수단입니다.

문제의 본질 — 공급사마다 "언어"가 다르다

연동 자체보다, 공급사마다 API가 다르다는 점이 문제입니다. 요구사항 문서가 명시하는 이질성은 세 축입니다.

이질성 축Supplier A 방식Supplier B 방식
요금 단위날짜별 1박 단가 (dailyRates[].nightlyRate)숙박 전체 총액 (totalPrice)
세금별도(net) — taxAmount 필드로 따로 줌포함(gross) — taxIncluded: true만 알려줌
실패 표현HTTP 상태 코드 (400 / 401 / 429 / 500 / 503)항상 HTTP 200 + 본문 resultCode (E400~E503)

그 외에도 식별자 체계(hotelCode vs propertyId), 조식 포함 여부(같은 객실도 공급사마다 다름), 재고 표현(날짜별 잔여 객실 수) 등 표현 방식이 전부 제각각입니다. 요컨대 같은 "숙박 상품"을 서로 다른 언어로 말하는 두 상대와 동시에 대화해야 하는 상황입니다.

이 차이를 고객에게 그대로 노출할 수는 없다. 고객은 어느 공급사에서 온 상품인지와 무관하게, 동일한 형태의 검색 결과를 봐야 한다.

— 요구사항 문서 (요지)[1]

숨은 전제 — 조회는 두 단계다

숙박 시스템 기준으로 이 연동의 성격을 결정짓는 제약이 하나 더 있습니다. 공급사는 "서울 숙소 보여줘" 같은 지역 검색을 제공하지 않습니다. 공급사 API는 성격이 다른 두 개로 나뉩니다[1].

  • ① 숙소 목록 API — 공급사가 취급하는 숙소·객실 타입 전체 목록. 조건 파라미터 없음, 요금·재고 없음, 자주 안 바뀌는 정적 콘텐츠 사전
  • ② 재고·요금 조회 API — 숙소 코드 목록(최대 50개)을 넘겨 한 번에 조회. 호출할 때마다 값이 바뀌는 동적 데이터 실시간

즉 어떤 숙소를 물어볼지는 플랫폼이 미리 알고 있어야 합니다. ①로 목록을 미리 받아 자사 식별자와 매핑해 두고(조회의 전제), 고객 검색이 들어오면 그 매핑에서 코드를 꺼내 ②를 공급사별로 호출하는 구조입니다. "숙소 목록은 잘 안 바뀌고, 재고·요금은 매번 바뀐다"는 성격 차이가 설계 전체를 관통합니다.

핵심이 시스템은 결국 번역기 + 합성기입니다. 공급사별 방언(요금·세금·실패 표현)을 자사 표준 모델로 번역(정규화)하고, 여러 공급사의 결과를 하나의 검색 결과로 합성(병합)하되, 한 공급사가 죽어도 나머지로 응답하는(부분 실패 허용) 백엔드입니다.

USE CASE

등장인물과 유즈케이스

액터는 셋입니다. 검색하는 고객, 그리고 시스템 바깥의 외부 시스템인 Supplier A와 B. 유즈케이스는 "실시간 검색 계열 4개 + 사전 매핑 1개"로 정리됩니다.

각 유즈케이스가 놓인 상황

유즈케이스트리거 · 시점하는 일
숙소·객실 매핑 동기화앱 기동 시 / 주기적 (설계 판단)①숙소 목록 API로 공급사 코드를 받아 (공급사, 숙소 코드) → 내부 숙소 식별자, (공급사, 숙소 코드, 객실 코드) → 내부 객실 타입 식별자 매핑을 DB에 저장
통합 숙소 검색고객이 날짜·인원 입력GET /api/v1/stays/search — 자사가 보유한 전체 숙소 대상, 아래 3개를 포함해 실행
재고·요금 병렬 조회검색 내부매핑에서 공급사별 코드를 꺼내 50개씩 묶어 A·B ②API를 WebClient로 동시 호출
표준 모델 정규화응답 수신 직후공급사별 요금·세금·재고·실패 표현을 자사 표준 숙박 상품 모델로 변환
결과 병합정규화 후공급사별 결과를 하나로 합침. 한쪽이 실패해도 나머지로 응답하고 실패 사실을 드러냄

FLOW

연동 흐름 — 두 단계 조회

시간 축으로 보면 흐름은 정확히 두 페이즈입니다. 검색이 오기 전에 끝나 있어야 하는 "매핑 구축", 그리고 검색 1건마다 도는 "병렬 조회 → 정규화 → 병합"입니다.

참고요구사항 핵심 흐름 요약 — [사전] 공급사 숙소 목록 조회 → 매핑 저장. [검색] 고객 요청(날짜·인원) → 보유 숙소를 공급사별 코드로 묶음(50개씩) → A·B 병렬 조회 → 표준 모델 정규화 → 병합(한쪽 실패해도 응답) → 통합 결과 반환. 이 한 줄기가 끊김 없이 동작하는 것이 시스템의 최우선 목표입니다.
4

SUPPLIER A vs B

같은 방, 다른 언어

공급사 스펙 예시에서 A의 A-10023과 B의 B77120은 실제로 같은 숙소·같은 객실(Riverside Hotel Seoul · Deluxe Twin)입니다. 그런데 두 공급사가 말하는 방식은 이렇게 다릅니다.

식별자까지 다르다 — 매핑이 조회의 전제인 이유

객실 타입 코드는 해당 숙소 안에서만 유일합니다. 다른 숙소에 같은 roomTypeCode가 존재할 수 있으므로, 객실 하나를 유일하게 가리키려면 (공급사, 숙소 코드, 객실 타입 코드) 세 값이 필요합니다. 또 두 공급사가 같은 숙소를 취급해도 그 사실을 알려주는 공통 키는 없습니다 — A의 A-10023과 B의 B77120이 같은 건물이라는 걸 스펙 어디에도 적어 주지 않습니다. 그래서 기본 동작은 "공급사가 다르면 내부 식별자도 다르다"이고, 이를 하나로 합치는 중복 상품 병합은 선택 구현으로 분리되어 있습니다.

숙소 목록 정적 — 가끔 바뀜

이름·객실 구성 같은 콘텐츠. 미리 받아 매핑으로 저장해 두고, 언제 갱신할지(기동 시·주기적)는 설계 판단으로 남겨져 있습니다.

재고·요금 동적 — 매번 바뀜

날짜별 잔여 객실 수와 가격. 검색할 때마다 실시간으로 물어봐야 하며, 이 성격 차이를 설계에 어떻게 반영하는지가 관건입니다.

5

USER SCREEN

고객 화면에는 어떻게 보이는가

고객이 날짜(9/1–9/4)와 인원(성인 2)만 넣고 검색했을 때, 공급사 스펙의 예시 데이터가 화면에서 어떻게 표기되는지를 그대로 그려 보면 "동일한 형태" 요구가 무엇인지 선명해집니다.

화면 요소 ↔ 데이터의 대응

화면 요소원천 데이터정규화에서 하는 일
숙소명 · 객실명①숙소 목록 (매핑 시 확보)공급사 코드가 아닌 자사 내부 식별자 기준으로 노출
총 요금A: 날짜별 nightlyRate+taxAmount 합산 / B: totalPrice세금 포함 기준으로 통일해 비교 가능하게
조식 뱃지breakfastIncluded (②응답에만 있음)같은 방이라도 공급사마다 다르므로 상품 조건으로 노출
남은 객실 / 예약 불가날짜별 remainingRooms기간 전체 예약 가능 수로 환산, 0이면 예약 불가
일부 미표시 안내공급사 호출 실패 (타임아웃·5xx·E5xx)부분 실패 사실을 응답에 명시 → UI가 안내로 변환
핵심통합 검색 API 응답에는 출처 공급사가 필수로 담기지만, 이것이 "고객 화면에 A/B를 보여 주라"는 뜻은 아닙니다. 요구사항의 원칙이 "고객은 어느 공급사 상품인지와 무관하게 동일한 형태를 본다"이므로, 출처 필드는 운영·추적·정산 같은 내부 용도로 읽는 것이 자연스럽습니다.
6

MECE

상황의 MECE 분해

"검색 한 번에 일어날 수 있는 모든 경우"를 겹침 없이, 빠짐없이 나누면 세 개의 독립된 축이 나옵니다 — 요청 축, 상품 축, 출처 축입니다.

축 1 — 요청 레벨: 공급사 응답 조합 (2×2 → 3상태)

조합분류시스템의 응답
A ✓ · B ✓전체 성공두 공급사 상품을 병합해 정상 응답
A ✓ · B ✗ / A ✗ · B ✓부분 실패성공한 쪽 결과만으로 응답 + 실패 사실을 응답에 명시
A ✗ · B ✗전체 실패노출 상품 0 — 빈 결과로 줄지, 오류로 줄지는 설계 선택

축 2 — 상품 레벨: 성공 응답 안의 각 상품

상태판정 조건화면 표기
예약 가능요청 기간 모든 날짜의 잔여 객실 ≥ 1 (가능 수 = 기간 최솟값)가격·조식·남은 객실 수와 함께 카드 노출
예약 불가기간 중 하루라도 잔여 0"예약 불가" 표시 또는 목록에서 제외 (선택 + 근거)
응답에 없음adults+children > maxOccupancy — 공급사가 반환 안 함화면에 아예 등장하지 않음

축 3 — 출처 레벨: 한 상품은 어디서 왔는가

출처예시 (부록 A 데이터)화면에서의 모습
자사 직등록(존재하는 경로 — 이번 구현 범위 밖)동일 포맷의 카드
Supplier A만Namsan Garden Stay (A-10044)카드 1장
Supplier B만(예시엔 없음 — 구조상 존재 가능)카드 1장
A·B 모두 취급Riverside Hotel Seoul (A-10023 = B77120)기본은 카드 2장 — 병합은 선택 구현

보조 축 — "실패"의 형태 (내부적으로 하나로 통일해야 하는 것)

  • HTTP 오류형 — Supplier A: 4xx/5xx 상태 코드로 실패를 알림 A
  • 200 위장형 — Supplier B: 장애여도 HTTP 200 + 본문 resultCode E5xx. 본문을 안 보면 장애를 정상으로 처리하게 됨 B
  • 무응답형 — 연결은 되나 응답이 안 옴 → 타임아웃으로 끊어야 함 공통

이 세 형태는 표현만 다를 뿐 모두 "그 공급사 조회 실패"라는 같은 내부 상태로 수렴해야 하며, 그것이 요구사항이 말하는 실패 판정 통일입니다.

정리어떤 검색이든 결과는 축 1의 세 상태 중 정확히 하나에 속하고, 응답에 담긴 상품 각각은 축 2의 상태 중 정확히 하나, 출처는 축 3 중 정확히 하나에 속합니다. 세 축이 서로 독립이므로 겹침도, 빠짐도 없습니다.
