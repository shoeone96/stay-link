# tech-research

기술 설계 결정에 필요한 레퍼런스를 탐색·비교해 추천하고, 그 출처의 정확도를 별도 에이전트로 검증하는 스킬입니다. 이 파일이 출처 규칙·비교 조건·검사 조건의 **단일 원본**이며, 에이전트 호출 시 아래 규칙을 프롬프트로 전달합니다.

## 범위

- **다룬다**: 구현 기술 레퍼런스 — Spring/Reactor 사용 패턴, 동시성·연동 견고성(타임아웃·부분 실패 등), 스키마·아키텍처 설계 패턴, 라이브러리 비교, 기존 문서의 출처 재검증.
- **다루지 않는다**: 숙박 업계 관행·용어·정책 등 도메인 질문 — `domain-analysis` 스킬 소관이므로 그렇게 안내하고 이 스킬을 종료한다. 코드 작성·수정도 하지 않는다.

## 출처 tier 규칙 (단일 원본 — 에이전트에 그대로 전달)

1. **1차**: 공식 문서 / 공식 레퍼런스 / 표준 명세 (Spring·Reactor·Java 공식 docs, RFC 등)
2. **2차**: 기업 공식 기술블로그 — 글로벌 빅테크(AWS·Google·Meta·Netflix 등) + 한국 기업(우아한형제들·카카오·라인·네이버·토스·당근·쿠팡·채널톡·올리브영·컬리·무신사 등)
3. **예외**: 벤더 공식 문서가 원전으로 인용하는, 널리 인정된 패턴 카탈로그 (microservices.io 등). 임의 개인 도메인으로 확대 금지.
4. **Fallback**: 1·2차에서 도저히 못 찾을 때만, 널리 인정받는 다른 기업의 **공식** 기술블로그까지 허용.

공통 (절대):
- URL은 WebSearch/WebFetch로 **실재를 확인한 것만** 기재한다. "도메인 루트 + 그럴듯한 제목" 조합은 날조다.
- 확인하지 못한 출처는 지어내지 말고 비워두며 "확인 못 함"으로 표기한다.
- 개인 블로그·위키·요약 사이트·SEO 글은 인용하지 않는다.
- 이 프로젝트가 참조하는 국내 대형 숙박 플랫폼의 기술블로그는 기업명·URL 노출 금지 정책상 인용하지 않는다 (탐색 대상에서 제외).

## 비교 조건 (에이전트에 그대로 전달)

- 대안은 **3개 이상** 수집한다.
- **기준 축이 있는 비교표**를 필수로 작성한다. 기본 축: 구현 복잡도 / 확정 스택(Java 25 + Boot 3.5.x + MVC·Virtual Thread + WebClient) 적합성 / 운영 시 관리 포인트 / 문서·커뮤니티 성숙도. 질문 성격에 따라 축을 조정하되 축 없는 나열은 금지.
- 표 아래에 추천 1개 + 근거를 두괄식으로 제시한다. "이 상황에서 왜 이기는지"가 드러나야 한다.

## 검증 검사 조건 (에이전트에 그대로 전달)

출처 목록의 각 항목에 대해 3가지를 검사한다:

1. **실재**: URL이 실제로 열리고, 실제 문서 제목이 기재된 제목과 일치하는가
2. **내용 일치**: "이 출처가 뒷받침한다"고 주장한 내용이 실제 그 문서에 있는가 — 근거로 문서 요지를 짧게 인용
3. **tier 적합**: 위 출처 tier 규칙의 어느 단계에 해당하는가, 인용 불가 출처가 아닌가

판정은 항목별로 `PASS` / `FAIL`(사유 명시 — 실재하지 않음, 제목 불일치, 내용 불일치, tier 부적합) / `UNVERIFIED`(접근 불가 등 확인 불능). **FAIL·UNVERIFIED 출처는 최종 산출물에서 제외**하거나 "확인 못 함"으로만 표기한다.

## 워크플로우

1. **질문 분류** — 둘 중 하나로 판별한다:
   - (a) 레퍼런스 탐색·비교·추천: 기술 결정에 필요한 근거 조사
   - (b) 출처 재검증: 기존 문서(docs/ 등)에 이미 기재된 출처의 정확도 확인
2. **(a) 탐색** — `tech-reference-scout` 에이전트를 호출한다. 전달할 것: 질문, 프로젝트 확정 스택 제약(CLAUDE.md), 관련 설계 파일 경로, 위 「출처 tier 규칙」·「비교 조건」 전문.
3. **자동 검증 (생략 불가)** — scout가 반환한 출처 목록을 `reference-verifier` 에이전트에 위 「검증 검사 조건」과 함께 전달한다. 탐색자와 검증자의 분리가 이 스킬의 존재 이유이므로, 출처가 1개라도 있으면 검증을 건너뛰지 않는다.
4. **최종 응답 구성** — 두괄식으로: 추천 + 근거 → 비교표 → 검증을 **통과한** 출처만 기재 (FAIL·UNVERIFIED 처리 결과 명시).
5. **(b) 재검증** — `reference-verifier`만 단독 호출한다. 대상 문서에서 인용(제목·URL·뒷받침 주장)을 추출해 같은 검사 조건으로 판정 목록을 받는다.
6. **자동 기록** — 사용자가 요청하지 않아도 `docs/ai-history.md`에 기록한다: 질문 → 추천 요약 → 검증 결과(판정 통계) → 사용자의 결정(결정 전이면 "결정 대기"로 두고 다음 턴에 갱신).
7. **산출물 검사** — 결과가 docs/ 아래 파일로 남는 경우, 저장소 반입 전 금지 표현 검사를 거친다.

## 원칙

- 근거 없는 추천은 하지 않는다. 출처가 전부 FAIL이면 추천을 보류하고 그 사실을 보고한다.
- 정답이 없는 비교는 단정하지 않고, 각 대안이 무엇을 잃는 선택인지 드러낸다.
- 모든 응답은 존댓말.
