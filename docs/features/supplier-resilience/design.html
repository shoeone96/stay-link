COMPOSITION

어디에 무엇이 붙는가

F6이 병합되며 검색과 수집이 이미 별도 프로세스가 됐다. 이 사실 하나가 “정책 두 벌”과 “서킷 상태의 범위”를 동시에 결정한다.

프로세스 분리가 공짜로 주는 것 / 뺏는 것주는 것 — 검색용·수집용 정책 분리가 배선만으로 성립한다. 각 프로세스에 조합기가 이미 한 벌씩이므로 서킷도 같은 모양으로 한 벌씩 두면 된다.
뺏는 것 — 서킷 상태가 프로세스 로컬이다. 배치가 공급사를 무너뜨려도 검색 쪽 서킷은 그것을 모르고, api-app을 여러 대로 띄우면 인스턴스마다 서킷이 따로 논다. 상태를 공유하려면 분산 저장소가 필요한데 지금 없다 — 한계를 인정하고 결정 카드에 남긴다.

DECISION B

상한과 재시도의 배치

조합기가 timeout(per-call)을 어댑터가 넘긴 Mono 바깥에 건다. 그래서 어댑터가 재시도를 붙이면 재시도 전체가 상한 하나를 나눠 쓴다.

FanOutExecutor.toArrival() — 이미 있는 코드
Mono.defer(() ->
        call.mono()                            // ← 어댑터가 만들어 넘긴다. 재시도를 여기 붙이면
            .timeout(policy.perCall())        //   자동으로 이 상한 "안쪽"이 된다
            .<Outcome<T>>map(Success::new)
            .onErrorResume(c -> Mono.just(failed(...))))  // ← 실패를 값으로 흡수. 재시도는 반드시 이 앞
시도별 상한을 유도하는 식attempt = (per-call − 백오프 합) ÷ 최대 시도 수 — per-call 4s, 백오프 합 0.3s, 시도 2회면 1.85s다. 이렇게 두면 부등식이 구조적으로 성립하고 프로퍼티가 늘지 않는다. 시도 수를 3으로 올리면 시도별 상한이 저절로 1.23s로 줄어드는데, 이는 “정해진 예산 안에서 시도를 늘리면 시도마다 짧아진다”는 사실을 그대로 드러내는 것이라 오히려 정직하다.

위험 — 실제 공급사의 p99가 시도별 상한보다 크면 정상 응답을 자르기 시작한다. 모의 서버 분포(정상 1.3ms / 고장 5s)에서는 어떤 값이든 결과가 같아 이 위험이 드러나지 않는다. 바인딩 시점에 하한을 검사하고, 실제 공급사가 붙으면 재검토한다.

WHERE THE LIMIT LIVES

상한을 어디에 둘 것인가

부등식의 값을 잘 고르는 대신 좌변을 없앴다. 동시 상한을 요청마다 호출 수로 잡으면 웨이브가 항상 1이고, 부등식은 budget > per-call로 줄어든다 — 이미 기동 시 검사하고 있는 조건이다.

CIRCUIT

서킷의 단위·상태·전이

전제 — 이 절의 판정은 모두 “캐시가 없을 때”다서킷은 캐시 미스에만 반응한다. 캐시가 적중한 검색은 어댑터까지 내려오지 않아 공급사 호출이 없고, 따라서 표본도 상태 변화도 없다. F10 이 앞에 붙으면 ① 여는 판정이 캐시 적중률만큼 느려지고 ② 회복 전이가 캐시 미스를 기다리며(OPEN 은 호출이 깨우므로) ③ 서킷이 닫힌 뒤에도 TTL 동안 옛 실패가 응답에 남는다. 캐시를 서킷 앞에 둘지 뒤에 둘지가 셋을 한꺼번에 정하며, 그건 F10 의 결정이다 — 캐시 구조를 모르는 채 지금 정하면 틀린다.

서킷 설계에서 정할 것은 셋뿐이다 — ① 상태를 누가 갖는가(단위) ② 상태를 언제 바꾸는가(전이 4개) ③ 각 상태에서 호출자가 무엇을 받는가. 셋은 겹치지 않고, 셋을 정하면 더 정할 것이 없다.

① 단위 — 상태를 누가 갖는가

서킷은 공급사 단위다. 묶음 단위는 성립할 수 없다 — 묶음은 요청마다 생겼다 사라져 상태를 이어받을 주체가 없다.

채택공급사 단위 · 프로세스 로컬

api-app에 A·B 두 인스턴스, batch-app에 A·B 두 인스턴스. 프로세스가 이미 검색/수집으로 갈려 있어 “공급사 × 엔드포인트”가 자동으로 성립한다 — 검색 프로세스에는 재고·요금 호출밖에 없고 수집 프로세스에는 목록 호출밖에 없다.

기각묶음 단위 / 전역 단위

묶음 단위 — 묶음은 요청과 함께 사라지므로 통계가 쌓이지 않는다. 전역 단위 — A가 죽었는데 B 호출까지 막는다. 두 공급사는 독립이라 한쪽 장애가 다른 쪽을 끌고 갈 이유가 없다.

② ③ 전이와 상태 — 상태 기계 전체

상태는 셋, 전이는 넷이다. 3×3 중 나머지 다섯 칸(자기 자신으로 · CLOSED→HALF_OPEN · OPEN→CLOSED)은 존재하지 않는다 — 회복은 반드시 HALF_OPEN 을 거친다. 그림의 화살표 넷이 곧 정해야 할 판정 넷이다.

상태 셋 — 각각 무엇을 하고 어떻게 벗어나나

상태호출에 일어나는 일호출자가 받는 것벗어나는 유일한 길
CLOSED 공급사로 그대로 나간다. 결과(성공·실패)를 크기 10 창에 넣는다 정상 결과 또는 실제 실패 표본이 5건 이상 쌓인 뒤 실패율이 50% 이상이 되는 순간 → OPEN
OPEN 호출하지 않는다. CallNotPermittedException 을 즉시 던진다. 소켓·풀 슬롯·시도별 상한 어느 것도 쓰지 않는다 CIRCUIT_OPEN 실패 값 (D-F9-8) 60초가 지나고 그 뒤 호출이 도착해야 → HALF_OPEN. 타이머가 스스로 바꾸지 않는다
HALF_OPEN 앞의 2건만 공급사로 내보낸다. 3건째부터는 OPEN 과 똑같이 즉시 거부 탐침이면 실제 결과, 아니면 CIRCUIT_OPEN 탐침 2건의 결과가 모이면 즉시 판정 → 전부 성공이면 CLOSED, 하나라도 실패면 OPEN
“탐침”은 합성 호출이 아니라 진짜 검색이다이 절에서 탐침이라 부르는 것은 별도의 헬스체크가 아니라, HALF_OPEN 이 된 뒤 가장 먼저 도착해 자리를 얻은 실제 검색 요청이다. Resilience4j 에는 탐침을 만들어 보내는 기능이 없다 — CircuitBreakerOperator.of(cb) 는 Function<Publisher<T>, Publisher<T>> 라서 어댑터가 이미 만들어 넘긴 Mono 의 구독을 허용하거나 거부할 뿐이고, 공급사 API 를 참조하지도 스케줄러를 돌리지도 않는다.

따라오는 결과 셋. ① 탐침이 실패하면 그 손해는 실제 사용자가 받는다 — 허용 수 2면 회복 시도 한 번에 최대 두 명이 그 공급사에 대해 PARTIAL·FAILED 를 본다. 허용 수를 크게 잡지 않는 또 하나의 이유다. ② 탐침이 성공하면 그 결과는 버려지지 않고 그대로 응답에 실린다 — 검사용 호출이 아니라 원래 하려던 일이기 때문이다. ③ 트래픽이 없으면 회복도 없다 — automaticTransitionFromOpenToHalfOpenEnabled 를 켜도 상태만 바뀔 뿐 호출은 여전히 만들지 않는다.
이 표에서 놓치기 쉬운 두 가지OPEN 은 시간이 아니라 호출이 깨운다. 60초가 지나도 아무도 검색하지 않으면 상태는 OPEN 그대로다. 다음 호출이 tryAcquirePermission() 을 부르는 순간에야 전이가 일어난다. 그래서 새벽에 공급사가 살아나도 첫 검색이 올 때까지는 차단이 유지되며, 이것은 결함이 아니라 “부르지 않으면 알 수 없다”는 사실의 반영이다.

HALF_OPEN 의 거부는 대기가 아니다. 탐침 자리를 못 얻은 3건째 호출은 줄을 서지 않고 즉시 거부된다 — 공식 문서가 “Further calls are rejected with a CallNotPermittedException, until all permitted calls have completed” 라고 적는다. 회복 확인 중이라고 사용자가 더 기다리는 일은 없다.

failureRateThreshold 50
slidingWindowSize 10		 최소 호출 수가 크면 서킷이 죽은 코드가 된다 — 기본값 100은 “99건이 전부 실패해도 안 열린다”는 뜻이고 우리 트래픽에 100건은 오지 않는다. 작으면 우연 몇 건에 열린다
② OPEN→HALF_OPEN 마지막 전이로부터 60초 경과 그리고 호출 도착 waitDurationInOpenState 60s (기본값 유지) 크면 회복이 늦게 확인된다. 작으면 아직 아픈 공급사를 반복해 찌른다. 줄이지 않는 근거 — 차단 중 사용자는 호출당 4초를 기다리는 대신 즉시 부분 결과를 받으므로 길어도 손해가 아니다
③ HALF_OPEN→CLOSED 탐침 2건의 실패율 < 50% → 실질적으로 2건 모두 성공 permittedNumberOfCallsInHalfOpenState 2 크면 회복 확인에 그만큼의 검색이 필요하고 회복 중인 공급사에 한꺼번에 부하가 간다(기본값 10). 작으면(1) 우연 한 번이 판정을 지배한다
④ HALF_OPEN→OPEN 탐침 2건의 실패율 ≥ 50% → 실질적으로 1건이라도 실패 같은 두 값의 조합 (2 × 50%) 이 칸은 독립 파라미터가 없다 — ③과 임계를 공유한다. “하나라도 실패하면 되돌린다”를 재현하려고 탐침 수를 2로 고른 것이 이 칸의 실제 설계다
임계 하나가 두 전이를 지배한다 — 회피 불가능한 제약Resilience4j 는 failureRateThreshold 를 CLOSED 판정과 HALF_OPEN 판정에 함께 쓴다. “half-open 만 더 엄격하게” 두는 손잡이가 없다. Azure 문서의 의미론은 “If any request fails, … it reverts to the Open state” 인데 이것을 직접 표현할 수 없다.

그래서 탐침 수로 재현한다 — 2건 중 1건 실패 = 50% 이고 판정이 “이 비율 이상이면 OPEN” 이므로, 탐침 2 + 임계 50% 조합이 “하나라도 실패하면 되돌린다”와 같은 동작이 된다. 3으로 두면 1건 실패가 33%라 그냥 닫혀 버려 권고와 어긋난다.

전 과정 — 장애 한 번을 호출 단위로

위의 값 셋이 실제로 어떻게 맞물리는지는 한 번의 장애를 끝까지 따라가야 보인다. 아래는 공급사 A 가 죽었다가 살아나는 동안 각 호출에 무슨 일이 생기는지다.

표본 단위는 「시도」다 — 그런데 실패율은 왜곡되지 않는다재시도가 서킷 바깥에 있으므로(D-F9-4) 창에 들어가는 것은 논리 호출이 아니라 시도다. 논리 호출 1건이 표본 2건이 될 수 있다.

여기서 “표본이 부풀었으니 slidingWindowSize·minimumNumberOfCalls 를 환산하고 임계를 올려야 한다”는 생각이 나오지만 산술이 그것을 지지하지 않는다. 시도별 실패 확률 q, 최대 2시도일 때 표본 기댓값은 1+q, 실패 표본 기댓값은 q+q² 이므로 관측 실패율은 (q+q²)/(1+q) = q — 정확히 보존된다.

달라지는 것은 숫자의 뜻 하나다. 임계 50%는 “검색의 절반이 실패”가 아니라 “시도의 절반이 실패”이고, 그 시점의 논리 실패율은 25%다. 사용자 피해가 커지기 전에 열린다는 뜻이라 방향이 맞다. 창도 1+q 배로 빨리 차므로 장애가 심할수록 판정이 빨라진다. 값을 키울 이유가 없고 해석만 문서에 못박는다.
창은 COUNT_BASED — 시간 기반이면 영영 열리지 않는다 (D-F9-13)minimumNumberOfCalls 의 정의에 “(per sliding window period)” 가 붙어 있다. TIME_BASED 를 쓰면 창 기간 안에 최소 호출 수를 채워야 판정이 시작된다.

우리 호출은 검색 요청에 종속적이라 트래픽이 뜸한 시간대에는 그 수가 모이지 않는다. 그러면 공급사가 완전히 죽어 있어도 서킷이 열리지 않는다 — 서킷을 둔 목적이 통째로 사라지는 갈래다. COUNT_BASED 는 창을 시간이 아니라 마지막 N건으로 잡으므로 트래픽이 적어도 판정이 성립한다.

느린 호출 판정(slowCall*)을 쓰지 않는 것도 같은 종류의 판단이다 — 그 일은 시도별 상한이 이미 하고 있고, 상한에 걸린 호출은 TIMEOUT 실패로 창에 들어간다.
왜 토큰 버킷이 아니라 서킷인가AWS Builders' Library 는 서킷에 유보적이다 — “circuit breakers introduce modal behavior… We have found that we can mitigate this risk by limiting retries locally using a token bucket.” 그러나 그 권고는 재시도 증폭을 문제로 놓은 것이다 — 같은 단락이 “Even with a single layer of retries, traffic still significantly increases when errors start.” 로 문제를 세우고, “Circuit breakers … are widely promoted to solve this problem.” 로 서킷을 그 해법에 놓은 다음에 유보를 붙인다. AWS 가 재는 것은 재시도로 늘어난 부하다.

이 시스템에서 죽은 공급사가 물리는 비용은 재시도가 아니라 첫 호출이 검색을 시도별 상한 동안 붙드는 것이다. 재시도까지 하면 검색 1건이 약 3.9초를 기다린 뒤에야 부분 결과를 낸다. 토큰 버킷은 이 점유를 한 건도 줄이지 못한다 — 첫 호출은 재시도가 아니기 때문이다.

부하 실측이 이것을 확인했다 — 공급사 하나가 5초씩 지연되는 상태에서 VU 40 · 40초를 걸었더니 31,539 요청 중 타임아웃 비용을 낸 것은 3건뿐이고 p(95)가 101ms였다.

정정 — 여기 원래 “그 슬롯은 살아 있는 공급사가 써야 할 것”이라고 적었으나 사실이 아니다. reactor-netty 의 maxConnections 는 “(per connection pool)” 이고 풀은 원격 호스트별로 갈린다. 결론은 유지되지만 근거가 다르다.

유보론에 대한 대응 — ① 상태 전이를 로그로 남긴다 ② half-open 의 두 전이를 테스트로 못 박는다(AWS 가 “테스트하기 어렵다”고 한 그 부분이다) ③ waitDurationInOpenState 를 과하게 크게 잡지 않는다.

결정 B-2 — 재시도와 서킷 중 어느 쪽이 바깥인가

둘 다 Mono 체인의 연산자라 순서를 정해야 하고, 순서가 서킷 통계의 단위를 바꾼다.

시도별 상한을 서킷보다 안쪽에 두는 이유도 여기서 나온다 — 그래야 타임아웃이 서킷의 실패 표본이 되어 느린 공급사가 서킷을 열 수 있다.
7

HALF-OPEN

회복 중에 요청이 쏟아지면

“겨우 일어난 공급사에 요청이 한꺼번에 꽂혀 다시 쓰러지는 것”은 half-open이 구조적으로 막는다. 다만 우리 구조에는 그 보호를 갉아먹는 요소가 하나 있다.

허용 수는 2 — Azure 의 의미론을 재현하는 값Azure 문서가 half-open 을 “If any request fails, … it reverts to the Open state” 로 정의한다. 그런데 Resilience4j 는 half-open 도 실패율로 판정하고 failureRateThreshold 를 CLOSED 판정과 공유한다 — half-open 만 엄격하게 두는 손잡이가 없다.

허용 수 2가 그 의미론을 재현한다 — 임계 50%에서 2건 중 1건 실패는 50%이고 “이 비율 이상이면 OPEN”이므로 한 건만 실패해도 되돌아간다. 3이면 1건 실패가 33%라 닫혀 버려 권고와 어긋난다. 탐침이 이미 재시도를 안에 품고 있어 실패한 탐침은 이미 두 번 실패한 것이라는 점도 같은 방향이다.
허용 수를 「검색 수 × 묶음 수」로 잡는 안은 기각① 묶음 수는 런타임 값이라 정적 설정의 인수가 될 수 없다. ② 그 곱이 half-open 을 무력화한다 — “검색 3건 × 묶음 1개 = 9”면 회복 중인 공급사가 동시에 9건을 받는다. Azure 가 half-open 을 둔 이유가 “prevent a recovering service from suddenly being flooded with requests” 인데 그 flood 를 설정으로 재현하는 셈이다. 막으려던 것을 만들게 된다.

대신 최대 묶음 수 구간으로 판단한다 — 1이면 2 고정, 2~3이면 묶음 수와 같게, 4 이상이면 허용 수를 늘리지 말고 구조를 본다(max-codes·묶음 전략·서킷을 거는 층). 발동 조건은 숫자가 아니라 식이다 — ⌈코드 수 ÷ max-codes⌉ ≥ 2. max-codes 가 공급사별 값이라 “51곳”으로 적으면 한쪽 계약이 바뀌는 순간 틀려진다.
소스로 확정한 두 가지① 허용 수를 넘으면 즉시 거부다. HalfOpenState.tryAcquirePermission()이 카운터를 내리고 0이면 CallNotPermittedException을 던진다 — 대기 경로가 없다.
② maxWaitDurationInHalfOpenState는 0(무한)을 유지한다. 이 값이 막는 위험은 “허용된 호출이 영영 완료되지 않는 것”인데 우리 호출에는 상한이 이중으로 걸려 반드시 종료한다. 반대로 값을 주면 짝인 transitionToStateAfterWaitDuration의 기본값이 OPEN이라, 트래픽이 적을 때 탐침이 다 모이기 전에 다시 닫아걸어 회복이 늦어진다.
8

DECISION C

차단을 무엇으로 표기하나

“fallback으로 처리한다”는 수단이지 반환값이 아니다. fallback 안에서 무엇을 돌려줄지는 여전히 정해야 한다.

이 결정은 F7 병합으로 한 번 뒤집혔다처음에는 안 2(UNAVAILABLE 흡수) 로 닫았다. 근거는 “소비자가 아직 없다” — 그때는 reason 을 읽는 프로덕션 코드가 한 줄뿐이었고 FailedChunk.reason 은 아무도 읽지 않았다.

F7 이 병합되면서 SearchStaysUseCase 가 그 값을 읽어 요약 로그에 글자로 찍기 시작했다. 기록해 둔 되돌릴 조건은 “수집기가 붙으면” 이었고 수집기는 아직 없지만, 손해는 수집기가 아니라 로그 줄에서 이미 발생한다 — 그 줄을 읽는 사람이 자사 차단을 보고 공급사를 의심하게 된다. 조건의 글자가 아니라 조건이 지키려던 것을 따랐다.
9

FAILURE TYPES

재시도 대상과 서킷 기록 대상

두 판정은 다른 질문에 답한다. 재시도는 “다시 부르면 달라지나”, 서킷은 “공급사가 아픈가”를 묻는다.

구현할 때 걸릴 함정재시도 판정 predicate가 FailureClassifier.classify()를 부르면, 그 메서드가 분류표에 없는 예외에 ERROR 로그를 남기는 설계라 같은 예외에 로그가 여러 번 찍힌다. UNEXPECTED는 재시도 대상이 아니라 시도가 늘지는 않지만, predicate 1회 + 어댑터 1회 = 2회가 된다. 판정을 두 번 하지 않도록 구조를 잡거나, 중복을 허용하고 문서에 남기거나 둘 중 하나를 골라야 한다.
