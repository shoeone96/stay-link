공급사 클라이언트를 어떻게 만들고
어떻게 동시에 부르는가

공급사별 HTTP 클라이언트 인스턴스를 만드는 방식과, 여러 공급사를 한꺼번에 부를 때 쓸 조합 연산자를 정한다. 결론을 가른 것은 취향이 아니라 버전 사실 하나와 자바독 한 문장이다.

SUMMARY

결론 먼저

공급사별 @Bean 수동 배선 + flatMap(fn, concurrency) 조합. 둘 다 "더 좋아 보여서"가 아니라 다른 선택지가 막혀서 남은 답이다.

축결론이걸 정한 근거
클라이언트 생성공급사별 @Bean 수동 배선 — builder.clone() → WebClientAdapter → HttpServiceProxyFactoryBoot 3.5에 자동 등록이 없다
설정@ConfigurationProperties Map 바인딩으로 받고, 프록시는 공급사별 빈에서 꺼내 쓴다A·B의 인터페이스가 서로 다르다
fan-out 조합Flux.fromIterable(...).flatMap(fn, maxConcurrent).collectList()상한 인자를 가진 유일한 후보
호출당 체인.timeout() → .retryWhen() → .onErrorResume(값)요구 조건의 세 축이 한자리에 모인다
포트 배치포트는 domain, 구현은 supplier-client의존 역전 — 헥사고날 규범
핵심이 프로젝트에 주어진 조건이 지목한 세 축은 타임아웃 · 재시도 · 병렬 호출 제어다. 이 문서의 모든 판단 기준은 "그 셋이 코드에 드러나는가" 하나다. 동작하느냐가 아니다.
2

VERSION FACT

버전 사실 — 3.5에는 없다

Boot 3.5.x / Framework 6.2.x에는 HTTP Interface 클라이언트의 자동 등록·설정 기능이 없다. 전부 수동 배선이다.

이 사실을 먼저 못 박는 이유는, 검색으로 나오는 최신 글 상당수가 @ImportHttpServices나 spring.http.serviceclient.*를 전제로 쓰여 있기 때문이다. 그대로 따라가면 우리 버전에 존재하지 않는 API를 쓰게 된다.

기능어디부터 있나확인 방법
@ImportHttpServicesSpring Framework 7.0자바독 Since 필드가 7.0. 6.2.11 자바독의 같은 경로는 404[8]
spring.http.serviceclientSpring Boot 4.x3.5 「Calling REST Services」 전문에 문자열 0건[4]
레지스트리 계층Framework 7 / Boot 4Spring 공식 블로그가 직접 서술[7]
spring.http.reactiveclientBoot 3.5에 있음단 전역이라 공급사별 차등 타임아웃에는 못 쓴다[4]
주의마지막 행이 함정이다. spring.http.reactiveclient.connect-timeout은 존재하지만 전역이다. 공급사마다 다른 타임아웃을 주려면 이 프로퍼티가 아니라 공급사별 커넥터나 .timeout() 연산자로 표현해야 한다. 후자라야 그 축이 코드에 드러난다.
3

WIRING

클라이언트 생성 구조 4안

안내용판정
A공급사별 @Bean 수동 배선채택. 6.2 레퍼런스의 코드 예제 그대로[1]
BMap 순회 + 동적 빈 등록탈락 — 인터페이스가 갈려 루프로 못 찍는다
C단일 WebClient + 호출 시 절대 URI탈락 — 공급사별 타임아웃·인증을 둘 자리가 없다
D@ImportHttpServices 그룹탈락 — 스택 밖(Framework 7 필요)

B안을 탈락시킨 이유가 이 절의 핵심이다. "설정을 Map으로 받으니 인스턴스도 루프로 만들면 되지 않나"는 자연스러운 발상인데, 루프로 찍어내려면 만들어지는 타입이 같아야 한다. 공급사 A는 4xx·5xx로 실패를 알리고 B는 HTTP 200 본문의 코드로 알린다. 실패 표현이 다르면 @HttpExchange 인터페이스와 오류 해석 정책이 갈리고, 그러면 찍어낼 틀이 없다.

함정Boot 문서가 직접 경고한다 — "WebClient.Builder instances are stateful: Any change on the builder is reflected in all clients subsequently created with it." 같은 빌더를 두 번 커스터마이즈하면 A의 설정이 B에 샌다. 조용히 틀리는 종류의 버그다[4].

FAN-OUT

fan-out 조합 연산자 5종

동시 구독 상한을 인자로 줄 수 있는 연산자는 둘뿐이고, 그중 순서 제약이 없는 것은 하나다.

연산자동시 구독 상한하나가 오류 → 나머지빈 리스트
flatMap(fn, n)있음 — 생략 시 256취소함collectList → 빈 List
Mono.zip없음취소함 — 빈 완료도 취소 사유combinator 미호출 → block 시 null
Flux.merge(Iterable)없음 (256 고정)취소함빈 Flux
mergeSequential(…, n, p)있음취소함빈 Flux
Mono.zipDelayError없음취소 안 함빈 완료

기본 동시성 256은 Queues.SMALL_BUFFER_SIZE에서 온다[18]. 공급사가 둘뿐인 지금은 값 자체가 무의미하지만, 상한을 명시적으로 적는 행위 자체가 세 축 중 하나에 대한 답이다. 생략하면 "제한 없음"과 사실상 같은 상태로 남는다.

zip이 위험한 진짜 이유

An error or empty completion of any source will cause other sources to be cancelled and the resulting Mono to immediately error or complete, respectively.

— Mono 자바독, reactor-core 3.7.11[16]

Mono.zip은 빈 완료를 오류와 똑같이 취급해 나머지를 취소한다. 그런데 부분 실패를 흡수하려고 붙이는 것이 onErrorResume이다. 여기서 fallback을 Mono.empty()로 두면 — 실패를 흡수하려던 코드가 오히려 나머지 공급사 호출을 전부 취소시키고 전체를 빈 결과로 만든다.

채택안

fan-out 조합 — 형태만
// 호출 하나마다: 타임아웃 → 재시도 → 실패를 "값"으로 흡수
Flux.fromIterable(calls)
    .flatMap(Function.identity(), maxConcurrentCalls)   // 병렬 호출 제어
    .collectList()
    .block(fanOutBudget);                                // 경계에서 1회만
규약onErrorResume의 fallback은 반드시 값이다. Mono.empty()를 쓰면 flatMap에서는 그 공급사가 조용히 사라지고, zip에서는 전체가 취소된다. 그리고 개별 흡수와 delayError 변형을 같이 쓰면 후자가 죽은 코드가 된다 — 둘 중 하나만 고른다.

CLAIM CHECK

외부 조언 판정 3건

방향은 맞고, 수단 둘이 어긋난다.

주장 1 vthread pinning 리스크

근거가 낡았다. JEP 491(Status Closed / Delivered, Release 24)이 synchronized pinning을 제거했다[21]. 이 프로젝트는 Java 25다. vthread를 조합 수단으로 안 쓰는 이유는 pinning이 아니라 동시 호출 상한을 직접 만들어야 하고 제어 로직이 코드에 안 드러나서다.

주장 2 zip으로 묶으면 된다

부분적으로만 맞다. 동작은 하지만 전 오버로드에 concurrency 인자가 없어 병렬 호출 제어를 쓸 문법 자리가 없다[16]. 여기에 4장의 빈 완료 취소 문제가 겹친다.

주장 3"vthread + block()은 RestTemplate 멀티스레드와 로직상 동일하다" — 부분적으로 맞다. Spring 6.2 레퍼런스는 동기 사용을 정식으로 인정하되, 다중 호출은 개별 block이 아니라 조합 후 1회 대기를 권한다[14]. 실제 I/O가 호출 스레드가 아닌 이벤트 루프에서 돌기 때문에 병렬성 제어 지점이 스레드 수가 아니라 연산자다.

block()이 가상 스레드에서 carrier를 점유하는지는 확인하지 못했다. 공식 문서에 그 서술이 없어 추측하지 않는다. 이 결정에는 영향이 없다.

AGAINST US

정직하게 병기할 것

결론에 불리한 사실 셋. 감추면 리뷰에서 그대로 되돌아온다.

  • 공식 문서의 예시는 Mono.zip이다. 「Synchronous Use」 페이지에 flatMap도 concurrency도 언급이 없다. 다만 그 문서가 스스로 "merely one example"이라 한정하므로, "공식이 zip을 권장한다"가 아니라 "최소 예시로 zip을 보인다"가 정확하다[14].
  • 같은 페이지 마지막 문장은 "you should never have to block in a Spring MVC or Spring WebFlux controller"다. 우리는 컨트롤러가 아니라 인프라 어댑터에서 block하고 가상 스레드로 서빙한다. 그러나 이 긴장을 문서가 해소해 주지는 않는다 — 프로젝트 판단으로 적어야 한다[14].
  • "리액티브 타입을 인프라 모듈 안에만 둔다"를 직접 서술한 1·2차 출처는 없다. 의존 역전(포트는 domain, 구현은 supplier-client)은 뒷받침된다[10][12]. 하지만 리액티브 타입 차단은 별개 주장이므로 이 프로젝트의 규약으로 적고 출처를 붙이지 않는다.
