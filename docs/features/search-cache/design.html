1

SCOPE

범위와 전제

캐시 자리는 SearchStaysUseCase.search() 경계, 키는 StaySearchCommand 넷(checkIn·checkOut·adults·children)이다. TTL 은 30초 하나이고 정확성이 아니라 절감 배수로 정한 값이라 설정 키로 뺀다.

착수 전에 닫힌 것 (ai-history 89·90)

질문탈락한 안확정
저장소로컬 캐시(Caffeine) — 공급사 한도가 계정 단위라 인스턴스 수만큼 호출을 곱하고, 롤링 배포마다 비어 공급사에 몰린다Redis + JSON 직렬화
부분 실패 응답미캐시(장애 중 부하 증폭) · 짧은 TTL(항목별 만료가 수단을 묶음) · 3분 마지막 정상 값(판매 불가를 판매 가능처럼 노출)그대로 30초 저장
전원 실패서킷(F9)에 위임 — 인스턴스별·프로세스 로컬이라 N 개가 각자 실패를 겪어야 열린다30초 기억 → 호출 없이 즉시 502
수단@Cacheable(sync = true) — Redis 백엔드는 키 단위 single-flight 가 없고, 예외는 저장되지 않으며, 오류 우회 경로에서 유스케이스 예외가 Redis 예외로 바뀐다캐시 컴포넌트 직접
선행이 F9 인 이유재시도 없이 캐시가 먼저 들어가면 1회 타임아웃이 30초 동안 그 공급사의 미노출로 굳는다 — 도메인이 반대한 바로 그 경우다. 재시도를 거친 FAILED 는 그 시점의 사실이라 30초 저장이 거짓이 아니다.

제외 — 그대로 밖에 둔다

soft/hard 이중 TTL · 비동기 갱신 · 마지막 정상 값 fallback · 견적 시각 · 목록 대표 가격 · 분산 락 · 로컬 캐시 · 503 + Retry-After(전원 실패) · rate limiter(F9 가 넘긴 항목, 한도 초과가 여전히 관측되지 않는다) · 매핑 색인 캐시(사용자 결정 2026-09-07, 재검토 항목으로도 두지 않는다).

DDD 전술 패턴은 적용하지 않는다

불변식을 지키는 Aggregate 가 없다. F7 과 같이 유스케이스 + 캐시 컴포넌트 + 값 객체로 간다. core 에 새로 생기는 것은 컴포넌트 하나와 값 객체의 메서드 하나뿐이다.

STRUCTURE

확정 구조 — 구성도·클래스 확정

아래 두 그림은 결정 A~E 의 확정안을 조합한 모습이다. 캐시 서비스는 core.application 에, Redis 는 새 모듈 cache-redis 에 산다 — persistence·supplier-client 와 같은 모양이다.

3

DECISION A

캐시가 끼는 자리 확정 · 안 3

"컴포넌트를 직접 쓴다"까지는 닫혔다. 남은 것은 그 컴포넌트가 유스케이스와 어떤 관계로 서느냐다 — 유스케이스 안에 들어갈지, 유스케이스를 감쌀지, 유스케이스가 부를지.

사용자 확정 사항과의 관계"@Cacheable 말고 cache service 를 쓴다"는 확정은 세 안 모두 만족한다. 이 카드는 그 service 가 어디에 서느냐만 정한다.
4

DECISION B

저장소 접근 수단 확정 · 안 1

첫 그림은 Redis 설정을 api-app 에 두었다. 사용자가 "모듈을 따로 두는 것 아니었나"를 물어 다시 쟀고, 이 저장소의 관례(포트는 core.application, 어댑터는 별도 모듈)를 빠뜨렸던 것이 드러나 추천을 바꿨다. 갈리는 축은 core 가 무엇을 아느냐와 Redis 예외를 누가 잡느냐다.

포트 계약 두 줄find 는 저장소에 못 닿으면 SearchCacheUnavailableException 을 던진다. store 는 절대 던지지 않는다 — 실패는 구현이 WARN 한 줄로 남긴다. 이 비대칭이 결정 D 의 "읽기 실패는 503, 쓰기 실패는 결과 반환"을 계약으로 고정한다.
5

DECISION C

전원 실패를 어떻게 기억하나 확정 · 안 3

"30초 기억 → 즉시 502"는 닫혔다. 남은 것은 그 기억이 캐시 안에서 어떤 값이냐다. F7 은 전원 실패를 예외로 표현하는데, 예외는 캐시에 넣을 수 없다.

안 3 이 F7 에 요구하는 변경Collected.allFailed() 의 판정(빈 outcomes 는 false)을 StaySearchResult.allSuppliersFailed() 로 옮기고, fetch 는 ERROR 요약 로그만 남긴 채 결과를 돌려준다. 던지는 자리는 search() 하나다. F7 의 T-10(전원 실패 → 예외)은 그대로 통과한다 — 밖에서 보는 행동은 같다.
6

HAPPY PATH

정상 경로 — miss 와 hit

miss 는 F7 의 경로 앞뒤에 포트 호출 둘(Redis 왕복 둘)이 붙은 것이고, hit 는 Redis 왕복 하나로 끝난다. 그 사이에 DB 도 공급사도 없다.

hit 는 위 그림의 ①~② 만으로 끝난다. GET 이 값을 돌려주면 컴포넌트는 in-flight 도 loader 도 건드리지 않고 CachedSearch(result, HIT) 를 돌려주며, 유스케이스는 같은 판정(allSuppliersFailed())을 거쳐 200 또는 502 를 낸다. DB 조회 두 번도 이 경로에는 없다.

7

SINGLE-FLIGHT

동시 miss — 한 번만 부른다 확정 · JVM 로컬

같은 조건의 모든 사용자가 같은 키를 치므로, 만료 순간 동시에 들어온 요청은 전부 miss 다. 그대로 두면 30초마다 스탬피드다. 한 JVM 안에서는 첫 요청이 부르고 나머지는 그 결과를 기다린다.

분산 락을 두지 않는 근거얻는 것은 만료 순간 호출 수를 "인스턴스 수 → 1"로 줄이는 것이고, 치르는 값은 Redis 락의 만료·재진입·leader 사망 처리와 대기 방식이다. 인스턴스 수 × 키당 30초 1건이 공급사 한도에 닿는다는 관측이 나오기 전에는 넣지 않는다.
8

NEGATIVE CACHE

전원 실패 — 기억하고 즉시 502 확정 · 30초

결정 C 의 안 3 위에서 이 경로는 새 코드가 거의 없다. fetch 가 전원 FAILED 결과를 돌려주고, 컴포넌트는 그것을 여느 결과처럼 저장하며, 유스케이스는 hit 든 miss 든 같은 한 줄로 던진다.

복구 감지 지연 ≤ 30초공급사가 살아나도 기억이 만료될 때까지 이 키는 502 다. 서킷(F9)의 반개방 탐침과 달리 키마다 30초에 한 번은 miss 가 나므로 지연 상한이 TTL 로 고정된다. 503 + Retry-After 로 바꾸는 것은 클라이언트가 그 힌트를 읽게 될 때 재검토한다.
9

DECISION D

Redis 장애 처리 확정 · 안 2

처음 제안(우회)을 뒤집었다. 이 캐시는 있으면 좋은 최적화가 아니라 공급사 한도 안에 머무르기 위한 장치다. 그 장치가 빠졌을 때 트래픽을 그대로 흘리면, 적중률 0 에 인스턴스 수를 곱한 호출이 공급사로 간다.

안 2 의 세부

  • 잡는 자리는 cache-redis 의 어댑터다. 연결·타임아웃은 DataAccessException 계열이고 JSON 역직렬화 실패는 SerializationException 이라 이 둘만 잡아 SearchCacheUnavailableException 으로 바꾼다. 컴포넌트는 포트 계약만 믿는다LAY-8
  • store 실패는 503 이 아니다. 공급사를 이미 불렀으므로 결과를 버리는 것은 호출 낭비다. WARN 한 줄(연산·키·원인 클래스)을 남기고 결과를 돌려준다비대칭
  • advice 에 Redis 예외 핸들러는 두지 않는다. 컴포넌트가 다 잡으므로 올라올 일이 없고, 올라온다면 버그라 500 이 맞다 (D-F0-4)F0
  • 기동 시 Redis 가 없어도 앱은 뜬다(지연 연결). 그 상태의 검색은 전부 503 이며, 이것이 "조용히 캐시 없이 돈다"보다 낫다fail fast
  • 서킷은 넣지 않는다 — 어댑터가 Resilience4j 를 받을 수는 있지만 근거 없는 코드다. 즉시 거절 옵션이 끊김을, 타임아웃이 느림을 각각 상한한다. "타임아웃 503 이 반복 관측"되면 어댑터에 실패 후 N초 건너뛰기를 붙인다재검토
10

DECISION E

batch-app 기동 확정 · 안 1

batch-app 은 com.stay 전체를 스캔해 SearchStaysUseCase 를 이미 띄우고 있다. 컴포넌트가 SearchResultStore 빈을 요구하는 순간 배치가 기동에 실패한다. "batch-app 은 Redis 를 모른다"를 지키면서 푸는 세 안이다.

compose 부수 효과compose.yaml 에 redis 서비스를 넣으면 batch-app 의 bootRun 도 그 컨테이너를 띄운다 (compose 는 파일 전체를 올린다). 배치는 그 컨테이너에 연결하지 않으므로 낭비일 뿐 오류는 아니다. compose 프로파일로 가르는 것은 지금 하지 않는다.

설정

api-app/application.yaml (추가분) · 프로퍼티 클래스는 cache-redis
stay:
  search-cache:
    ttl: 30s              # 정확성이 아니라 절감 배수의 값. 실측 후 재조정
    enabled: true         # 테스트 프로필은 false → 모듈이 NoOp 을 등록한다
spring:
  data:
    redis:
      connect-timeout: 300ms
      timeout: 300ms      # 명령(read) 타임아웃. 503 은 이 안에 나간다
  # 접속 정보는 compose 자동 감지 (spring-boot-docker-compose)

키 이름 존재는 Boot 4.0.6 jar 메타데이터로 확인했고 4.1 은 구현 첫 사이클에서 다시 본다. compose.yaml 에는 redis 이미지 서비스 하나(포트 무작위 · redis-cli ping 헬스체크)가 붙는다.
