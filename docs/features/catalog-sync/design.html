01

SCOPE

이번에 만드는 것과 빼는 것

공급사가 파는 숙소·객실 유형의 목록을 자사 매핑 테이블과 맞추는 일만 합니다. 요금과 재고는 다루지 않습니다.

IN이번 범위

· 생명주기 ACTIVE/INACTIVE 도입
· 3-way diff (신규 · 되살림 · 사라짐)
· 공급사별 독립 트랜잭션
· batch-app 모듈 신설
· 0건 응답 가드

OUT빼는 것

· 요금·재고 수집
· 검색 중 발견한 미매핑 코드 (F11)
· 공급사 코드의 병합·대체
· 공급사 간 숙소 통합 식별(dedup)
· 증분 조회 · 유예 기간

이 배치가 하는 일의 정의 관측된 사실의 기록입니다. "공급사 목록에 있었는가"를 매일 확인해 매핑 행의 상태로 남깁니다. "계약이 끝났는가"를 판단하는 것이 아닙니다 — 그 둘을 같은 것으로 취급하면 시즌 휴업·리노베이션 같은 가역적 사유가 계약 종료와 구분되지 않습니다.
02

STRUCTURE

모듈과 클래스

batch-app이 새로 생깁니다. api-app과 같은 모양이며, 들어가는 것만 다릅니다 — 컨트롤러 대신 Job·Step 설정이 들어갑니다.

기동 클래스의 위치가 함정이다 기동 클래스는 com.stay 패키지에 둔다. com.stay.batch에 두면 자동설정 패키지가 그만큼 좁아져 com.stay.property.domain의 엔티티와 com.stay.property.infrastructure의 어댑터·리포지터리를 찾지 못한다. scanBasePackages만으로는 엔티티 스캔이 풀리지 않는다. Job·Tasklet 클래스만 com.stay.batch 아래 둔다.

도메인에 더해지는 것

읽기 접근자는 셋만 연다 diff 가 키로 쓰는 supplierPropertyCode(), propertyId(), supplierRoomCode() 뿐이다. lifecycle() 은 diff 에 필요 없다 — 상태 변경이 멱등이라 조건 없이 부르기 때문이다. F1 이 D-F1-8 로 "호출자가 생기는 F6 에 이관"해 둔 자리다.

04

TRANSACTION

실패를 어떻게 가두는가

"A 가 실패해도 B 는 갱신된다"가 F6 의 요건입니다. 그런데 순진하게 짜면 이 요건이 조용히 깨집니다.

Each call to a Tasklet is wrapped in a transaction.

Spring Batch Reference 6.0.5 — TaskletStep

Tasklet 이 이미 트랜잭션 안에서 돌기 때문에, 그 안에서 부른 @Transactional 서비스는 기본 전파(REQUIRED)로 같은 물리 트랜잭션에 합류합니다. 그러면 A 의 실패가 남긴 rollback-only 표시가 전체 커밋을 무너뜨립니다.

So a rollback-only marker set in the inner transaction scope does affect the outer transaction’s chance to actually commit. … A corresponding UnexpectedRollbackException is thrown at that point.

Spring Framework Reference 7.0.9 — Transaction Propagation
두 장치가 짝인 이유 REQUIRES_NEW 에는 문서화된 대가가 있습니다 — "The resources attached to the outer transaction will remain bound there while the inner transaction acquires its own resources such as a new database connection. This may lead to exhaustion of the connection pool…" 즉 보통은 커넥션을 두 배로 쥡니다. 그런데 스텝의 트랜잭션 매니저를 ResourcelessTransactionManager 로 두면 바깥이 붙들 DB 커넥션 자체가 없어 그 대가가 발생하지 않습니다. 마침 TaskletStep 은 트랜잭션 매니저를 지정하지 않으면 이것을 기본값으로 씁니다.
05

LIFECYCLE

생명주기와 사라짐

INACTIVE 는 레코드 무효가 아니다 숙소가 INACTIVE 여도 그 숙소의 기존 예약 조회·변경·취소·정산은 계속되어야 합니다. 정산은 체크아웃 이후까지 이어지므로 비활성 이후에도 수개월간 참조되는 것이 정상입니다. 조회 계층에 WHERE lifecycle = 'ACTIVE' 를 일괄 적용하면 진행 중인 예약이 사라집니다.

0건 응답이라는 구멍

F3 은 목록이 비어도 예외가 아니라 정상으로 취급합니다(T-04). F6 의 "응답에 없으면 비활성"과 합치면 다음이 됩니다.

임계치를 두지 않는 이유 "직전 대비 N% 이상 사라지면 보류" 같은 감소율 가드는 업계에도 있지만, 공식 문서 어디에도 구체 수치가 없습니다(large number 라고만 씁니다). 근거 없는 숫자를 코드에 박느니 0 이라는 단 하나의 임계만 쓰고, 나머지는 이연 항목으로 남깁니다. 일부만 온 응답은 공급사 쪽 문제로 인정하고 그대로 반영합니다 — 판단 근거가 없는 것에 대해 우리가 임의로 정한 숫자로 개입하지 않습니다.

건너뛴 공급사를 어떻게 알리는가

상황매핑로그잡 결과
Failed — 타임아웃 · 인증 오류 · 계약 위반 응답건드리지 않음WARN실패
Fetched 인데 0건건드리지 않음ERROR실패
Fetched, 건수 있음반영—성공
잡을 실패로 끝내면 알람 말고 하나를 더 얻는다 잡이 COMPLETED 로 끝나면 같은 날짜로 재실행할 때 JobInstanceAlreadyCompleteException 에 막힙니다. 실패로 끝내면 같은 JobInstance 의 새 실행이 되므로, 공급사가 복구된 뒤 그날 배치를 다시 돌릴 수 있습니다. 이미 커밋된 다른 공급사의 갱신은 공급사별 독립 트랜잭션이라 그대로 남습니다.

대가: 공급사가 자주 불안정하면 매일 알람이 울립니다. 그때는 Failed 를 알람 대상에서 빼는 조정을 실측 후에 판단합니다.
확정 · 가숙소가 사라졌을 때 그 밑 객실은 어떻게 하나

가쓰기 연쇄 · 확정

숙소가 빠지면 그 밑 객실 행에도 INACTIVE 를 직접 쓴다. 조회가 단순해진다. 다만 관측하지 않은 것을 기록하게 된다 — 숙소가 빠진 실행에서는 객실 정보가 아예 오지 않는다.

나읽기 파생 · 탈락

객실 행에는 자기 관측만 담고, 판매 가능 여부는 property.ACTIVE AND room.ACTIVE 로 계산한다. D-F1-9 로 조인이 이미 있어 실질 비용이 없다.

데이터 정확성은 양쪽이 같습니다. 숙소가 되살아날 때 저장된 상태를 복원하는 것이 아니라 돌아온 응답으로 전부 재판정하기 때문에, 리노베이션으로 객실 구성이 바뀌어도 둘 다 맞는 답을 냅니다. 차이는 모델링 정직성과, (나)에서 room 만 단독 조회하면 오답이 나온다는 점입니다. (가)로 확정했습니다 — 곧 F7 검색이 이 테이블을 읽으므로, 모델링 정직성보다 room 단독 조회의 함정을 남기지 않는 쪽을 택했습니다. 뒤집으려면 이 카드와 01-design.md §3 ③ · T-11 만 고치면 됩니다.

06

RUNTIME

배치 런타임 설정

여기서 정한 값들은 취향이 아니라 안 그러면 조용히 망가지는 것들입니다.

가장 위험했던 발견 spring-boot-starter-batch 만 넣으면 메타데이터가 저장되지 않습니다. 그 스타터의 의존은 spring-boot-starter 와 spring-boot-batch 둘뿐이고, JDBC JobRepository 를 만들어 주는 spring-boot-batch-jdbc 가 없습니다. 그러면 DefaultBatchConfiguration 의 ResourcelessJobRepository 가 떠서 — "This implementation does not use or store batch meta-data." — 같은 날짜로 재실행해도 막히지 않고, 재시작 이력도 남지 않습니다. 해결: spring-boot-starter-batch-jdbc (Boot BOM 이 버전 관리).
batch-app/src/main/resources/application.yaml 
spring:
  main:
    web-application-type: none      # 기본값이 없다 — 명시하지 않으면 classpath 로 자동 감지된다
  batch:
    jdbc:
      initialize-schema: never      # always 는 SQL 실패를 전부 삼킨다 — 아래 설명
  sql:
    init:
      mode: always
      schema-locations:
        - optional:classpath*:schema.sql   # persistence 모듈에서 온다
        - classpath:schema-batch.sql       # 이 모듈 것. optional 없음 = 없으면 기동 실패

# 수집용 조합기 상한은 F3 가 이미 배치를 전제로 잡아 둔 값을 그대로 옮긴다
supplier:
  catalog:
    fan-out:
      max-concurrent: 2
      per-call: 30s
      budget: 40s

왜 initialize-schema: always 가 아닌가

두 번째 기동에서 죽지는 않습니다. 그런데 죽지 않는 이유가 문제입니다.

사실근거
배포 스크립트에 IF NOT EXISTS 가 없다 spring-batch-core-6.0.5.jar 의 schema-mysql.sql — CREATE TABLE 9회, 0회
적용 이력·존재 검사가 없다 AbstractScriptDatabaseInitializer 가 mode 와 임베디드 여부만 본다
그래서 매 기동 9건이 실패한다 그런데 spring.batch.jdbc.continue-on-error 기본값이 true
실패가 전부 묻힌다 "all failures in SQL should be logged but not cause a failure"

"이미 있음"만 골라 삼키는 것이 아니라 SQL 실패 전부를 삼킵니다. 진짜 스키마 오류도 함께 묻힙니다. 반면 우리 spring.sql.init 경로는 continue-on-error 기본값이 false 라 시끄럽게 죽습니다 — 그게 맞는 동작입니다.

매일 실행을 어떻게 구성하나

incrementer 를 달면 안 된다 "If the job defines a JobParametersIncrementer, then the incrementer will be used to calculate the next parameters in the sequence and the provided parameters will be ignored." 즉 incrementer 를 붙이면 커맨드라인으로 넘긴 날짜가 경고 한 줄만 남기고 버려집니다. 둘 중 하나만 고를 수 있습니다.

공식 문서가 1일 1회 배치를 그대로 예시로 듭니다 — "there is one logical JobInstance per day… If the January 1st run fails the first time and is run again the next day, it is still the January 1st run." 이 서술이 가리키는 쪽은 날짜를 식별 파라미터로 넘기는 방식입니다.

외부 스케줄러가 실행하는 커맨드 
java -jar batch-app.jar syncDate=2026-09-07,java.time.LocalDate
#                       ↑ -- 를 붙이면 옵션 인자로 분류되어 통째로 무시된다
#                         = 가 없는 인자는 에러 없이 조용히 건너뛴다

표기는 name=value,type,identifying 이고, 타입을 주면 그 타입으로 변환됩니다. 토큰이 둘뿐이면 식별 파라미터로 취급됩니다. 날짜 형식이 어긋나면 JobParametersConversionException 으로 즉시 실패합니다 — 조용히 넘어가지 않습니다.

같은 날짜로 다시 돌리면 같은 JobInstance 의 새 실행이 되어 실패한 배치를 이어서 돌릴 수 있고, 이미 성공한 날짜를 다시 돌리면 JobInstanceAlreadyCompleteException 으로 막힙니다. 이 커맨드가 배치의 계약이므로, 날짜를 누가 만들어 넘기는지가 설계에 포함됩니다.

실행 시각 — 근거 없음을 밝힌다 1일 1회라는 주기에는 근거가 있습니다. 카탈로그는 요금·재고의 수익관리 속도가 아니라 계약·온보딩 속도로 움직이고, 전체 상태 대조라 하루를 놓쳐도 다음 실행이 같은 결과에 도달합니다. 그러나 하루 중 몇 시에 도는 것이 좋은지는 어떤 공식 문서에서도 근거를 찾지 못했습니다. 그 값은 근거 없이 정한 것임을 문서에 남깁니다.

DECISIONS

결정 카드 요약

전문과 탈락 사유는 01-design.md 에 있습니다. 여기서는 무엇을 정했는지만 봅니다. ID 는 01-design.md 의 카드 번호(D-F6-n)와 같습니다. § 로 시작하는 행은 카드가 아니라 그 절에 적어 둔 설계 제약입니다.

ID결정한 줄 근거
1Tasklet 채택3-way diff 는 집합 연산이라 item 단위 모델과 안 맞는다
2ACTIVE / INACTIVEDELISTED 는 주식 용어

5revive 는 매번 응답으로 재판정저장된 사유에 의존하지 않아 구성 변경도 정확

7-b일부만 온 응답은 그대로 반영판단 근거가 없어 임의 숫자로 개입하지 않는다

8유예 기간 이연완결성 게이트와 한 묶음이라 함께 지어야 한다
9조회에 lifecycle 필터 금지ACTIVE 만 읽으면 되살릴 것이 insert 로 가 UNIQUE 위반
10REQUIRES_NEW + Resourceless문서가 격리를 보장하는 유일한 안, 커넥션 대가는 짝이 상쇄
11포트 saveAll 은 어댑터가 다리를 놓는다가장 자연스러운 시그니처가 erasure 충돌로 컴파일 에러
12IDENTITY 유지 · batch_size 미설정IDENTITY 면 insert 배치가 비활성화되어 설정이 듣지 않는다
13기동 클래스는 com.stay더 깊이 두면 엔티티·어댑터를 못 찾는다
14starter-batch-jdbc · @EnableBatchProcessing 금지starter-batch 만으로는 메타데이터가 저장되지 않고, 어노테이션을 붙이면 두 자동설정이 모두 물러난다
15schema.sql 을 persistence 로기본 위치가 classpath* 와일드카드라 두 앱이 자동 수집
16배치 메타는 never + 자체 스크립트always 는 SQL 실패를 전부 삼킨다
17incrementer 금지 · 날짜 파라미터incrementer 를 달면 넘긴 파라미터가 폐기된다
