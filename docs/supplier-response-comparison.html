OVERVIEW

공통 규약과 핵심 차이

두 공급사 모두 "숙소 > 객실 타입" 2단계 구조에, 조회는 목록 API와 재고·요금 API로 나뉜다.

두 공급사가 동일하게 지키는 규약이 먼저다. 인증은 X-Api-Key 헤더, 날짜는 YYYY-MM-DD, 체크아웃일은 숙박일에 포함되지 않는다 (09-10 체크인 / 09-13 체크아웃 = 3박 = 숙박일 09-10·11·12). 인원은 요청 시 adults·children 분리, maxOccupancy는 성인+아동 합산 기준. 재고는 날짜별 잔여 객실 수(remainingRooms, 정수), 통화는 ISO 4217 코드, 금액은 통화의 최소 단위 정수(KRW는 원)다.

차이는 아래 다섯 가지가 전부이고, 이 다섯 가지가 곧 표준 모델이 흡수해야 할 대상이다.

관점Supplier ASupplier B
응답 골격본문이 바로 데이터 (items 루트)resultCode/resultMessage/data 봉투 안에 데이터
요금 표현날짜별 1박 단가 (nightlyRate)기간 전체 총액 (totalPrice) — 날짜별 분해 불가
세금별도 금액 명시 (net + taxAmount)총액에 포함 (gross), taxIncluded: true만 알려줌
실패 표현HTTP 상태 코드 (4xx/5xx) + error 본문항상 HTTP 200 + 본문 resultCode (E4xx/E5xx)
식별자 이름hotelCode / roomTypeCodepropertyId / roomId — 이름만 다르고 역할 동일
핵심식별자의 유일성 범위는 두 공급사가 같다 — 숙소 식별자는 공급사 안에서 유일, 객실 타입 식별자는 해당 숙소 안에서만 유일. 따라서 객실 타입 하나를 가리키려면 항상 (공급사, 숙소 코드, 객실 타입 코드) 세 값이 필요하다. 두 공급사가 같은 숙소를 취급해도 그 사실을 알려주는 공통 키는 없다.

LIST API

전체 조회 — 숙소 목록

공급사가 취급하는 숙소·객실 타입 전체 목록. 조건 파라미터 없음, 요금·재고 없음 — 매핑 구축의 재료다.

A는 GET /a/v1/hotels, B는 GET /b/api/properties. 둘 다 파라미터 없이 전체를 반환한다. 같은 "Haeundae Blue Hotel"이 양쪽에 있지만(A A-3201 / B P-88410) 이를 잇는 공통 키는 없고, "Gangnam City Stay"는 A에만 있다.

구조 차이내용물은 사실상 같다 — 숙소(코드·이름) 목록 + 각 숙소의 객실 타입(코드·이름·최대 인원) 목록. 다른 것은 ① 필드명(hotelCode↔propertyId, roomTypes↔rooms) ② B만 봉투(data)로 감싼다는 점 두 가지뿐이다. 이 응답이 (공급사 코드 ↔ 내부 식별자) 매핑 저장의 유일한 입력이 된다.

실패 응답 — 목록 조회

실패 표현 체계는 API와 무관하게 공급사 단위로 동일하다. A는 HTTP 상태 코드가 곧 실패이고, B는 실패해도 HTTP 200이라 본문을 열어봐야 안다.

A · HTTP 503 
// HTTP 상태 코드로 실패를 표현
HTTP/1.1 503 Service Unavailable

{
  "error": "SERVICE_UNAVAILABLE",
  "message": "temporarily unavailable"
}
B · HTTP 200 (!) 
// 장애인데도 HTTP는 200
HTTP/1.1 200 OK

{
  "resultCode": "E503",
  "resultMessage": "TEMPORARILY_UNAVAILABLE",
  "data": null              // 실패 시 null
}
주의B는 HTTP 상태만 보면 장애가 정상 응답으로 둔갑한다. HTTP 계층 성공 ≠ 업무 성공. 어댑터가 resultCode != "0000"을 A의 4xx/5xx와 같은 내부 실패 모델로 번역해야 한다.

AVAILABILITY API

상세 조회 — 재고·요금

숙소 코드 목록을 넘겨 한 번에(bulk) 조회한다. 호출할 때마다 값이 달라지는 동적 데이터 — 저장하지 않고 실시간으로 가져오는 쪽이다.

요청 형태는 거의 같다 — A는 GET /a/v1/availability?hotelCodes=A-3201,A-3305&checkIn=2026-09-10&checkOut=2026-09-13&adults=2&children=0, B는 GET /b/api/search?propertyIds=P-88410&checkIn=...&adults=2&children=0. 둘 다 코드 목록은 쉼표 구분 최대 50개이고, 요청 인원을 수용할 수 있는 객실 타입만 돌아온다. 결정적 차이는 응답의 요금 표현이다.

A · GET /a/v1/availability

      "currency": "KRW",

응답의 낱개 단위도 주목할 지점이다. 목록 API는 숙소 밑에 객실 타입이 중첩돼 있었지만, 상세 조회는 양쪽 모두 (숙소, 객실 타입) 조합당 1개의 평평한 항목으로 온다. 표준 모델의 검색 결과 단위와 자연스럽게 일치한다.

A 날짜별 net + 세금 별도

날짜마다 1박 단가와 세금이 따로 온다. 그날 결제액 = nightlyRate + taxAmount, 숙박 전체 금액 = 각 날짜 합산. 총액은 언제든 계산해 낼 수 있다 — 3박 합산 시 374,000 + 37,400 = 411,400원.

B 기간 총액 gross

요청 기간 전체의 세금 포함 총액 하나만 온다(415,800원). 날짜별 요금은 제공하지 않고, 세금 금액도 taxIncluded: true뿐 분해 불가. 총액 → 날짜별 복원은 원천적으로 불가능하다.

핵심변환은 한 방향만 가능하다 — A(날짜별 net) → 총액 gross는 계산 가능, B(총액 gross) → 날짜별은 불가능. 표준 요금 모델을 무엇으로 잡든 이 비대칭이 출발점이다. 또한 같은 객실이라도 조건이 다르다 — 이 예시에서 B는 조식 포함(breakfastIncluded: true), A는 미포함이라 단순 가격 비교가 성립하지 않는다.

실패 응답 — 재고·요금 조회

체계는 2장과 동일하고, 여기서는 양쪽의 실패 코드가 어떻게 대응되는지만 정리한다. 날짜 오류·코드 50개 초과 같은 요청 오류부터 한도 초과·장애까지, 의미는 1:1로 대응된다.

A · HTTP 400 
HTTP/1.1 400 Bad Request

{
  "error": "INVALID_DATE_RANGE",
  "message":
    "checkOut must be after checkIn"
}
B · HTTP 200 
HTTP/1.1 200 OK

{
  "resultCode": "E400",
  "resultMessage": "INVALID_REQUEST",
  "data": null
}

모델링 시사점

① 요금이 유일하게 어려운 결정이다. 나머지 필드는 이름 번역이면 끝나지만, 요금은 A→총액만 가능한 비가역 변환이 걸려 있다. 총액 gross로 통일하면 두 공급사를 정보 손실 없이 담을 수 있는 대신 A의 날짜별 정보를 버리는 선택이 되고, 날짜별을 유지하면 B를 표현할 수 없다. 무엇을 잃는 선택인지 명시하고 결정해야 한다.

② 재고 판정은 공통 공식이 성립한다. 양쪽 모두 날짜별 remainingRooms를 주므로, N박 요청의 예약 가능 객실 수 = 숙박일 전체에서의 최솟값. 하루라도 0이면 예약 불가다.

③ 실패 정규화는 어댑터 책임이다. B의 200 + resultCode와 A의 HTTP 상태를 어댑터 경계 안에서 같은 실패 유형(요청 오류 / 인증 / 한도 초과 / 장애)으로 번역해, 도메인과 검색 파이프라인은 공급사별 표현을 모르게 한다.

④ 봉투 해체도 어댑터 몫이다. B의 data 봉투는 구조적 차이일 뿐 정보 차이가 아니므로, 어댑터 밖으로는 봉투 없는 표준 형태만 나간다.

다음 결정표준 요금 모델의 통일 기준 — A안: 날짜별 net + 세금 별도 (A 원형 유지, B 표현 불가) vs B안: 기간 총액 gross (양쪽 수용, 날짜별 정보 포기). 이 결정이 저장 모델 확정(todolist 사전작업 1)의 첫 항목이다.
