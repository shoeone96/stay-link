DECISIONS

확정 사항 요약

목록 통합의 D1~D5에 이어, 검색 통합에서 확정된 결정은 일곱 가지다.

#결정내용
D6표준 요금기간 총액 gross — totalAmount + currency. A는 Σ(nightlyRate + taxAmount) 합산, B는 totalPrice 그대로. 날짜별 분해·세금 분리 표시는 버리는 선택 (README 명시)
D7재고 판정availableRooms = 숙박일 전체 remainingRooms의 최솟값 — 하루라도 안 되면 그 기간은 안 되니까
D8품절 노출예약 불가 상품도 응답에서 빼지 않고 availableRooms: 0 + soldOut: true로 노출 — 정보 보존, 품절 표시는 화면 몫
D9이름 필드검색 응답의 숙소명·객실 타입명은 DB 저장값이 아니라 공급사 응답 값 그대로 — 목록 갱신 주기만큼 낡은 이름 방지
D10부분 실패 표기aggregate 시 응답에 공급사별 결과 블록(suppliers[]: supplier + status + reason) — 성공/실패/사유가 응답만으로 해석 가능
D11미매핑 코드동기 경로에서는 해당 항목만 제외 + 로그. retry 없이 비동기로 매핑을 바로 수정(목록 재조회 → 갱신, 없으면 후처리) — 상세는 fallback 로직·갱신 주기 설계와 함께
D12실패 정규화A의 HTTP 상태 ↔ B의 resultCode를 내부 실패 유형으로 통일 — 유형 체계는 ErrorResponse 처리 로직 구현 시 확정 (이연)
2

SCENARIO

검색 시나리오 흐름

검색 1건 = 매핑 조회 → 공급사별 코드 묶음(≤50) → 병렬 호출 → 정규화 → aggregate.

고객은 날짜와 인원으로 검색하고, 대상은 자사가 보유한 숙소 전체다. 공급사는 지역·조건 검색을 제공하지 않으므로 매핑 테이블이 조회의 전제다 — 어떤 숙소를 물어볼지 우리가 먼저 알고 있어야 한다. 코드 목록은 공급사당 한 번에 최대 50개 제한이 있어 묶음으로 나눠 나가며, 지금 데이터로는 공급사당 1묶음이다.

핵심이 흐름 하나가 끊김 없이 동작하는 것이 최우선이다. 한쪽 실패 시 전체 실패로 번지지 않는 구조(개별 실패 흡수)가 aggregate 설계의 요건이고, 그래서 두 호출 결과를 하나로 합칠 때 실패를 값으로 취급한다 — 예외를 밖으로 던지는 묶음이 하나라도 있으면 전체가 죽는다.

FIELD MAPPING

필드 매칭 11쌍

앞 5쌍은 목록 통합의 번역을 재사용하고, 뒤 6쌍이 상세 전용이다.

#Supplier ASupplier B표준
1본문 바로 데이터data 봉투어댑터가 봉투 해체
2hotelCodepropertyId매핑 역방향 → 내부 property id
3hotelNamepropertyNamepropertyName — 응답 값 그대로 (D9)
4roomTypeCoderoomId매핑 역방향 → 내부 room id
5roomTypeNameroomNameroomName — 응답 값 그대로 (D9)

8currency (이름 동일)그대로 전달

응답의 낱개 단위는 양쪽 모두 (숙소, 객실 타입) 조합당 1개의 평면 항목이라, 표준 검색 결과의 단위와 그대로 일치한다 — 구조 변환 없이 필드 번역과 요금·재고 계산만 하면 된다.

4

NORMALIZATION

정규화 규칙

샘플 데이터로 세 규칙을 실제 값까지 검산해 둔다.

요금 — A는 합산, B는 그대로

요금 정규화 (3박: 09-10 ~ 09-13) 
// Supplier A: 날짜별 net + 세금 → 합산
totalAmount(A) = Σ(nightlyRate + taxAmount)
             = (110000+11000) + (143000+14300) + (143000+14300)
             = 435,600 KRW   // 정수 합산 — 반올림 오차 없음

// Supplier B: 기간 총액 gross → 그대로
totalAmount(B) = totalPrice = 453,600 KRW
// taxIncluded는 항상 true라 표준에 싣지 않는다 (정보가 아니라 소음)

재고 — 날짜별 최솟값

재고 정규화 
availableRooms = min(날짜별 remainingRooms)

// A OCN-DBL: [3, 1, 1] → 1  (09-11부터 병목)
// 어느 날짜든 0이면 → 0 = 품절. 그 날 안 되면 기간 전체가 안 되니까

soldOut = (availableRooms == 0)   // D8: 빼지 않고 노출 + 명시적 품절 표기
D8 근거공급사가 필터링해 주는 것은 인원뿐(수용 가능 객실 타입만 반환)이고, 재고 0은 응답에 그대로 온다. "예약 불가"는 우리가 min 계산으로 만드는 파생 판정이므로 노출 여부도 우리 결정이다 — 0을 버리면 복구 불가, 노출하면 품절 표시·필터링 모두 상위에서 선택 가능. 그래서 보존한다.

미매핑 코드 — 동기 제외, 비동기 수정

목록 갱신 주기 사이에 공급사가 객실 타입을 추가하면, 상세 응답에 우리 매핑에 없는 코드가 올 수 있다. 처리는 두 트랙으로 나눈다 (D11):

동기(검색 경로) — 해당 항목만 결과에서 제외하고 로그를 남긴다. 한 항목 때문에 검색 전체가 실패하지 않는다.
비동기(후처리) — retry 없이 매핑을 바로 수정한다: 목록 재조회 → 코드가 있으면 매핑 추가, 없으면 후처리(폐기 등 — response 내용에 따라 결정). 같은 코드에 대한 재조회 중복 방지를 포함해, 상세는 fallback 로직·목록 갱신 주기 설계와 함께 확정한다.

5

RESPONSE

통합 검색 응답 형태

results(상품) + suppliers(공급사별 결과 블록). 최소 계약의 8개 요구 정보가 모두 담긴다.

GET /api/v1/stays/search — 응답 (B 실패 예시) 
{
  "results": [
    {
      "propertyId": 1,                        // 내부 식별자 (매핑 결과)
      "propertyName": "Haeundae Blue Hotel",  // 응답 값 그대로 (D9)
      "roomId": 11,
      "roomName": "Ocean Double",
      "maxOccupancy": 2,
      "availableRooms": 1,                    // min(3,1,1) (D7)
      "soldOut": false,                       // 0이면 true, 빼지 않음 (D8)
      "totalAmount": 435600,                  // gross 합산 (D6)
      "currency": "KRW",
      "breakfastIncluded": false,
      "supplier": "A"                         // 출처 공급사
    }
    // ... A의 나머지 상품들 (B 상품은 이번 응답에 없음)
  ],
  "suppliers": [                              // 공급사별 결과 블록 (D10)
    { "supplier": "A", "status": "OK" },
    { "supplier": "B", "status": "FAILED",
      "reason": "TIMEOUT" }                   // 유형 값 체계는 D12에서 확정
  ]
}
해석 규칙이 응답만으로 클라이언트가 판단할 수 있어야 한다 — "결과가 완전한가"(suppliers 전원 OK인가), "누가 빠졌나"(FAILED인 공급사), "왜"(reason). 단순 플래그(partial: true)나 실패 목록만으로는 성공 공급사 집합을 역산할 수 없어 이 구조를 택했다. 뒤에 묶음이 여러 개로 늘면 한 공급사의 일부 묶음 실패는 status: "PARTIAL"로 확장한다.
