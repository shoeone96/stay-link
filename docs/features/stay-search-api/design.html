SCOPE

범위와 전제

이번 범위는 F7 + F8이다. 두 기능을 합치는 이유는 편의가 아니라, 나눠 두면 F7 구현이 전원 실패 경로에서 무엇을 해야 할지 모르는 채 코드를 쓰게 되기 때문이다.

제외 — 그대로 밖에 둔다

재시도·서킷(F9) · 캐시(F10) · 미매핑 코드 비동기 수정(F11) · 두 공급사 동일 숙소 병합(D5, 선택) · 페이지네이션·지역·키워드 검색.

DDD 전술 패턴은 적용하지 않는다

이 범위에 불변식을 지키는 Aggregate가 없다. 조회 조립이 전부이므로 Transaction Script(유스케이스 + 값 객체)로 간다. F3·F5와 같은 판단이다.

시드 값 불일치 — 먼저 정리하고 간다 전달받은 검증 기대값(A-10023 429,000 / B77120 452,000 / A-10044 Namsan Garden Stay)은 원본 명세의 예시 데이터이고, 우리 모의 서버(F2)는 자체 시드를 쓴다. 시나리오의 의도는 전부 같고 식별자와 금액만 다르다. 아래 대응표를 기준으로 삼는다.

CONTRACT

API 계약

요청 파라미터는 넷뿐이다. 지역·키워드·페이징·정렬 파라미터는 두지 않는다.

GET /api/v1/stays/search
# 요청 — 이 넷 외에는 받지 않는다
GET /api/v1/stays/search?checkIn=2026-09-10&checkOut=2026-09-13&adults=2&children=0

# 응답 (200) — 필수 정보 7개가 모두 담긴다
{
  "code": "SUCCESS", "message": "Success", "time": "2026-09-07T…Z",
  "data": {
    "results": [
      {
        "propertyId": 1,              // ① 내부 숙소 ID
        "propertyName": "Haeundae Blue Hotel",  // ② 숙소명 (공급사 응답 값, D9)
        "roomId": 11,                 // ③ 내부 객실 타입 ID
        "roomName": "Ocean Double",   // ④ 객실 타입명
        "maxOccupancy": 2,            // ⑤ 최대 수용 인원
        "bookableRooms": 1,           // ⑥ 예약 가능 객실 수 = 날짜별 최솟값 (D7)
        "soldOut": false,             //    bookableRooms == 0 파생 (D8)
        "totalAmount": 435600,        // ⑦ 요금 — 정수, KRW 원 단위
        "currency": "KRW",
        "breakfastIncluded": true,
        "supplier": "A"               // ⑧ 출처 공급사
      }
    ],
    "suppliers": [                    // ⑨ 부분 실패 사실 (D10 개정 — reason 없음)
      { "supplier": "A", "status": "OK" },
      { "supplier": "B", "status": "FAILED" }
    ]
  }
}

요청 검증

필드규칙수단
checkIn필수 · 오늘 이후@NotNull @FutureOrPresent
checkOut필수 · checkIn보다 뒤 (체크아웃일은 숙박일 아님)@NotNull + 클래스 레벨 @AssertTrue
adults1 이상@Min(1)
children0 이상@Min(0)
Clock을 넣지 않는 이유 "오늘"의 기준을 테스트가 고정하려면 주입이 필요하지만, 테스트는 기준을 알 필요가 없다 — 확인할 것은 "기준보다 이전이면 거부"이고 입력을 오늘-1로 상대적으로 주면 된다. 유일하게 흔들리는 「오늘은 통과」 경계는 테스트 리스트에서 뺀다. 대신 기준 시간대가 JVM 기본이 되므로 실행 설정의 TZ=Asia/Seoul로 못박는다.
구현 첫 사이클에서 실측할 것 쿼리 파라미터를 DTO로 묶어 @Valid를 걸 때 Spring이 던지는 예외가 MethodArgumentNotValidException인지 BindException인지에 따라 F0 핸들러가 잡느냐가 갈린다. 문서로 단정하지 않고 실제로 태워 확인하고, 후자면 핸들러를 하나 늘린다.

STRUCTURE

클래스 배치

컨트롤러는 api-app, 조립은 core의 application 패키지다 — domain 패키지가 아니다. domain은 Spring 의존이 0이어야 하고(LAY-2) @Transactional·@Service는 application에만 온다(LAY-3).

4

HAPPY PATH

정상 경로

유스케이스는 Reactor 연산자를 직접 쓰지 않는다. 병렬·타임아웃·예산은 전부 포트 안쪽(F3a 조합기)에서 처리되고, 유스케이스는 돌아온 공급사별 결과를 합치기만 한다.

이 갈래가 없으면 500이 나간다 (D-F7-15) 색인이 비어 있으면(ACTIVE 매핑 0건) 포트를 부르지 않고 빈 결과로 조기 반환한다. 그대로 부르면 F5의 AvailabilityQuery가 "propertyCodes는 비어 있을 수 없다"는 불변식으로 IllegalArgumentException을 던지고, 그것이 advice의 마지막 그물에 걸려 500으로 나간다. 그런데 매핑이 비어 있는 것은 앱을 처음 띄운 정상 상태다.

이때 suppliers도 빈 배열이다 — 아무도 부르지 않았으므로, 안 부른 곳을 OK로 쓰면 "물어봤는데 결과가 없다"는 거짓이 된다.

DECISION A

결과 순서 확정 · 안 A

요청에 정렬 파라미터를 두지 않는 것은 확정이다. 그래도 응답의 순서는 정해야 한다 — 조합기의 flatMap은 완료 순서대로 결과를 내보내므로, 아무것도 안 하면 같은 요청이 매번 다른 순서로 나간다. 테스트도 그 위에 못 선다.

이게 취향 문제가 아닌 이유 F5 설계 §3.5가 못박아 둔 것이 있다 — 조식 조건이 다른 두 항목의 totalAmount는 같은 축에서 비교되지 않는다. 업계 모델에서 판매 단위는 (객실 타입 × 요금제)이고 조식 포함 여부는 요금제의 조건이다. 우리 모델에는 요금제 축이 없다.

확정안 A — 식별 순서

결정적이고, 비교 불가능한 두 값을 같은 축에 세우지 않는다. 가격 비교가 성립하려면 요금제 축이 필요한데 우리 모델에 없다. 축을 만들기 전에는 가격을 기본 순서로 두지 않는다.

탈락안 B — 가격순

화면이 그대로 쓰기 좋다. 다만 위 편향을 응답 계약에 새겨 넣는 것이고, 나중에 요금제 축이 생겨도 순서가 이미 굳는다.

탈락시킨 세 번째 안sort 요청 파라미터 — 요구가 파라미터를 넷으로 못박고 있어 선택지가 아니다. 필요해지면 안 A 위에 얹는다.
6

DECISION B

매핑 조회와 역매핑 확정 · 안 1

검색은 매핑 테이블을 두 번 쓴다 — 나갈 때(어떤 코드를 물어볼지)와 들어올 때(공급사 코드를 내부 ID로 되돌릴 때). 이 둘을 어디에 두느냐가 F6과의 충돌 지점이기도 하다.

안 1로 확정한다. 병합 충돌은 F6이 먼저 들어오면 그 위에서 다시 잡으면 되는 일회성 비용이고, 두 메서드가 같은 인터페이스에 나란히 있는 편이 "이 테이블은 여기로 읽는다"를 지킨다. StayMappingIndex를 값 객체로 두는 근거는 클래스 수가 아니라 미매핑 판정이라는 규칙이 붙기 때문이다(OOP-8).

EXCLUSION

제외 규칙 — INACTIVE와 미매핑

항목이 결과에서 빠지는 경로는 셋이다. 셋 다 검색 전체를 실패시키지 않는다.

ACTIVE만 거르는 자리 db-schema.html이 "판매 목록 질의에서만 명시적으로 거른다"고 정해 두었다. 이번 범위에서 그 질의는 findAllSearchTargets()와 findAllSearchTargetsByPropertyIdIn() 둘뿐이다. F6의 동기화 경로는 lifecycle 필터 없이 전부 읽는다(D-F6-9) — 되살아날 INACTIVE 행이 "DB에 없음"으로 판정되면 insert로 가서 UNIQUE에 걸리기 때문이며, 그 판단과 검색의 판단은 별개다.

DECISION C

부분 실패와 전원 실패 확정 · 502

부분 실패는 200이다 — A가 무응답이어도 B 결과만으로 응답이 나가야 한다. 남은 것은 전원이 실패했을 때 하나다.

status 판정

F5가 준 결과status왜
failures 비어 있음OKoffers가 비어 있어도 OK — 공급사는 아는 코드만 돌려준다(계약 §8)
failures 있음 + offers 있음PARTIAL묶음 여러 개 중 일부만 실패
failures 있음 + offers 없음FAILED그 공급사 몫이 통째로 빠짐

B의 HTTP 200 + resultCode != "0000"은 F3의 SupplierBResultException과 FailureClassifier를 거쳐 A의 4xx/5xx와 같은 자리로 온다. 그래서 위 표 하나로 두 공급사가 동일하게 판정된다.

502를 고른 결정적 근거 — 동시 실패는 독립 사건이 아니다 A와 B는 서로 다른 회사의 서로 다른 시스템이다. 각각 죽는 것은 독립 사건이지만 동시에 죽는 것은 대개 공통 원인이고, 그 후보가 전부 우리 쪽이다 — 우리 네트워크·DNS, 설정 배포 사고, 조합기 예산이 짧게 잡힘, 커넥션 풀·스레드 고갈, 방금 나간 코드. 그러므로 이 사건은 우리 지표에 잡히는 것이 맞다. 다만 우리가 아는 사실은 "상류 호출이 전부 실패했다"까지이고 원인이 우리라는 것은 추론이므로, 관측된 사실에 맞는 502를 쓴다. 502는 상류 실패로 분류되어 우리 코드 예외(500)와 섞이지 않아 조사 시작점도 갈린다.

502를 만드는 자리는 유스케이스다. 전 공급사 FAILED이면 AllSuppliersFailedException을 던지고 F0의 advice가 상태로 옮긴다. 컨트롤러가 outcomes를 보고 분기하면 presentation에 판단이 생기고(LAY-4), F0이 세운 구조(예외 타입 = 오류 유형, advice가 상태 매핑)와도 어긋난다.

원인은 응답이 아니라 로그·지표로 간다

reason(SupplierErrorCode 8개 값)을 응답에서 빼는 대신, 검색 1건마다 요약 로그 한 줄을 남긴다. 갈래마다 흩뿌리지 않는 이유는 지표를 뽑을 때 파싱 대상이 하나여야 하기 때문이다.

지표 수집기는 이번에 넣지 않는다Micrometer·수집 백엔드를 붙이는 것은 sink와 소비자가 실재할 때 한다(DDD-8). F3a도 같은 판단으로 메트릭을 미뤘다. 이번에는 산출 가능한 형태의 로그까지가 범위이고, 지표 설계는 README에 문서로 남긴다.

RUNTIME

트랜잭션과 인덱스

유스케이스에 @Transactional을 붙이지 않는다. LAY-3이 "트랜잭션 경계는 application"이라고 한 것은 트랜잭션이 필요할 때의 자리를 말한 것이지, 조회 전용 유스케이스에도 붙이라는 뜻이 아니다.

인덱스 — 추가하지 않는다

검색이 새로 만드는 질의는 둘뿐이고, 둘 다 이미 있는 인덱스로 처리된다.

질의타는 인덱스판단
property WHERE lifecycle = 'ACTIVE'없음 (풀스캔)카디널리티 2이고 대부분 ACTIVE라 인덱스를 만들어도 옵티마이저가 안 쓴다
room WHERE property_id IN (…) AND lifecycle = 'ACTIVE'uq_room_property_code그 UNIQUE의 선두 컬럼이 property_id라 IN 조건이 그대로 탄다. 추가 불필요

이번 범위는 테이블·컬럼·제약을 바꾸지 않으므로 docs/db-schema.html은 갱신하지 않는다.

지속 탐구 항목 — lifecycle 인덱스 관측 중

"지금은 불필요"가 "영원히 불필요"가 아니다 F6은 목록에서 사라진 상품을 하드 삭제하지 않고 INACTIVE로만 바꾼다. 그러므로 INACTIVE 행은 단조 증가하고, 공급사 이탈·판매 중단이 잦아질수록 ACTIVE 비율은 계속 떨어진다. 인덱스가 안 쓰이는 이유는 카디널리티가 2여서가 아니라 지금 ACTIVE가 거의 전부이기 때문이며, 그 전제는 시간이 지나면 깨진다.

FAILURE PATH

검증 실패 경로

잘못된 요청은 공급사에 나가기 전에 경계에서 잘린다. 변환은 F0이 이미 만들어 둔 @RestControllerAdvice가 한다 — F7이 새로 만드는 핸들러는 없다.

문서화와 실측

API 문서는 손으로 쓰지 않고 테스트가 만든다. 그리고 목으로 대체된 자동 테스트가 못 잡는 것은 실제 소켓을 여는 실측으로 잡는다.

실측 — 자동 테스트가 못 잡는 것

확인할 것왜 실측인가수단
날짜가 YYYY-MM-DD로 나가는가F5에서 JVM 로케일 표기로 나가 모의 서버가 400으로 거절한 전례가 있다. 프록시를 목으로 대체하는 테스트는 이 경로를 타지 않는다k6/app-search.js
타임아웃 값의 근거현재 application.yaml이 "실측 전 자리표시자"라고 스스로 밝히고 있다모의 서버 지연 모드로 측정
A 무응답 시 B만으로 200, 예산 이내조합기의 예산이 실제로 지켜지는지는 소켓을 열어야 보인다모의 서버 무응답 모드
B의 E4xx/E5xx가 A의 5xx와 같은 status로 떨어지는가두 공급사의 실패 표현이 하나로 모이는 것이 F8의 핵심모의 서버 장애 모드

F6이 배치 쪽 실측을 하면서 재고·요금 호출의 실측을 이쪽으로 넘겼다 — 배치는 HTTP 엔드포인트가 없어 부하 도구로 태울 수 없기 때문이다. 그 몫을 여기서 받는다.

F6과의 병합 조정

  • 구현은 F6 병합 뒤에 시작한다. PropertyLifecycle이 없으면 ACTIVE 필터가 컴파일되지 않는다
  • 충돌 파일 4개 — PropertyRepository · RoomRepository와 각 JPA 구현. 나중에 병합하는 쪽(F7)이 푼다
  • 상태표는 F6도 같은 hunk를 고쳤다. 병합 후 F6 행을 완료(병합)으로 바꾸는 커밋을 F7이 낸다
  • 상태표 F8 행은 F7에 통합으로 적는다 (F4→F3 선례와 같은 표기)
